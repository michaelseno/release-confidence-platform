## Context

`infra/resources/s3.yml` (`RawResultsBucket`) has `VersioningConfiguration.Status: Enabled` and no `LifecycleConfiguration`. `infra/resources/dynamodb.yml` (`MetadataTable`) defines no TTL attribute. Confirmed by direct infrastructure inspection in both independent SDLC Verification Gate review passes (`docs/review/evidence_governance_baseline_v1_0_sdlc_verification_claude.md`, `..._opencode.md`): every audit's raw execution evidence (Phase 1/2), aggregates (Phase 4), intelligence (Phase 5), reports (Phase 6), and certificates (Phase 7) — every S3 object version and every DynamoDB record, regardless of which phase wrote it — is retained indefinitely today. This is the direct opposite of the Evidence Governance Baseline's default: evidence shall not outlive its authorized governance purpose.

`docs/product/evidence_governance_workstream_a_product_spec.md` (FR-A1-1 through FR-A1-6, AC-A1-1 through AC-A1-8) requires a technically enforced, automated custody-period disposal mechanism covering both storage systems, a legal hold override, a durable disposal record, and an externally supplied custody-period parameter (the duration value itself is explicitly out of scope for this ADR and for Workstream A).

Three design dimensions required explicit architectural resolution:

1. **Legal hold override mechanism.** Both S3 Lifecycle rules and DynamoDB TTL are unconditional, AWS-managed mechanisms — neither has a native per-object "pause" concept once a rule/attribute is configured. A hold must suspend disposal without disabling enforcement platform-wide.
2. **Disposal traceability.** DynamoDB TTL deletion is an asynchronous, best-effort AWS background process (documented as typically completing within 48 hours of expiry, not synchronously on expiry) and does not invoke any application hook at delete time. S3 Lifecycle expiration similarly runs as a daily batch process, not a synchronous per-object action. FR-A1-5 / AC-A1-6 require a durable, queryable disposal record; a design that assumes either mechanism fires a synchronous callback is not viable.
3. **Custody-period parameterization.** FR-A1-3 / AC-A1-5 require the custody-period duration to be external configuration, not a hardcoded value baked into the mechanism, and AC-A1-8 requires the design to explicitly state how the pre-Workstream-A evidence backlog is handled rather than leaving it undefined.

## Decision

### Decision 1: Two Independent, AWS-Native Enforcement Mechanisms — S3 Lifecycle for `RawResultsBucket`, DynamoDB TTL for `MetadataTable`

**Amendment note (post-A1.2 implementation):** an earlier revision of this Decision described enforcement as "an S3 `LifecycleConfiguration` rule" (singular) on `RawResultsBucket`. Read literally, "a single rule" would force one uniform custody-period value across every evidence class, since a CloudFormation `LifecycleRule` carries exactly one scalar `Days`/`NoncurrentDays` value — which would silently reintroduce Alternative 4 (rejected below) and directly contradict Decision 5's per-evidence-class parameterization (`custom.custodyPeriodDays.<class>.${stage}`, keyed by `raw_evidence`/`intelligence`/`report`/`certificate`). This was a wording gap, not a design ambiguity: Decision 5 already structurally requires one rule per evidence class, since each class's `Days` value is an independent configuration input. A1.2 implemented this correctly — **`RawResultsBucket`'s `LifecycleConfiguration` carries four rules, one per evidence class (`raw-results/`, `intelligence/`, `reports/`, `integrity/`), each independently tag-filtered on `rcp-legal-hold=false` and each referencing its own `custom.custodyPeriodDays.<class>.${stage}` value** — and QA independently confirmed no uniform default was substituted anywhere. The text below is corrected to say "rules" (plural, one per evidence class) wherever the prior revision said "rule" (singular) in a way that implied bucket-wide uniformity.

No new storage system, queue, or archival tier is introduced. Enforcement is added to the two existing resources using their respective AWS-native retention primitives: an S3 `LifecycleConfiguration` — one rule per evidence class, per the amendment above — on `RawResultsBucket`, and a TTL attribute (`ttl_disposal_at`) on `MetadataTable`. This preserves the "Coverage of all evidence classes... regardless of which phase wrote them" requirement (FR-A1-6) without introducing per-phase opt-in logic — both mechanisms apply uniformly, in the sense that every evidence class is covered by some rule and no phase needs to opt in, across the single bucket and single table already shared by every phase. "Uniform coverage" does not mean "one rule" or "one duration"; it means no evidence class is missed.

### Decision 2: Legal Hold via Object Tagging + Lifecycle Tag-Filter Inversion (S3), Not S3 Object Lock

S3 Object Lock is rejected as the legal-hold mechanism for `RawResultsBucket` (see Alternative 1) because Object Lock can only be enabled at bucket creation (or via an AWS Support-mediated exception process) — it cannot be retroactively enabled on the already-deployed, already-versioned `RawResultsBucket` through ordinary infrastructure-as-code deployment. Requiring bucket recreation to adopt Object Lock is operationally disruptive and out of proportion to what legal hold requires here.

Instead:

- Every object written to `RawResultsBucket` is tagged at write time with `rcp-legal-hold=false` and `rcp-evidence-class={class}` (`raw_evidence` | `intelligence` | `report` | `certificate`, mapped from the writing phase's S3 key prefix).
- Each of the four per-evidence-class Lifecycle rules' `Filter` matches on `Tag: {Key: rcp-legal-hold, Value: false}` (in addition to that rule's own evidence-class key prefix). S3 Lifecycle tag filters require an exact match; an object tagged `rcp-legal-hold=true` will not match any of the four rules' filters and is therefore excluded from both `Expiration` and `NoncurrentVersionExpiration` actions under all of them.
- Placing a legal hold flips the tag to `rcp-legal-hold=true` on **every extant version** of every object under the audit identity's S3 key prefixes, across all four evidence-class prefixes (current version and all noncurrent versions, since S3 object tags are versioned — a tag set on the current version does not retroactively apply to noncurrent versions). Releasing a hold flips the tag back to `false`.
- `Expiration.Days` (current-version disposal) is computed from each object's own creation timestamp — not a mutable clock — so no recomputation is needed on release for current versions: the very next daily lifecycle evaluation cycle picks up any current-version object whose age already exceeds the threshold, satisfying AC-A1-4 ("enforcement must resume, not silently skip the now-expired evidence") without any additional bookkeeping.
- `NoncurrentVersionExpiration.NoncurrentDays`, by contrast, is computed from **when a version became noncurrent** (i.e., when a newer version was written to the same key), not from the version's own original creation timestamp. This is a distinct clock from both `Expiration.Days` and from the DynamoDB-side `custody_expires_at` clock (`created_at + custody_period_seconds`). Under this platform's prevailing write pattern — every evidence artifact receives a unique, event-scoped S3 key (`write_raw_results_once` enforces write-once-per-key via an existence check before `put_object`; Phase 6/Phase 7 artifacts embed `report_job_id`/`certjob_id` in their key path, so force re-generation writes a *new* key rather than overwriting) — noncurrent versions are not expected to arise from ordinary evidence writes at all; they would only arise from a code path that re-`PutObject`s the *same* key (the one identified instance today is `S3StorageClient.write_json`'s `overwrite=True` parameter, used for configuration artifacts, not raw evidence). Where a noncurrent version does arise, its `NoncurrentDays`-based expiration timing is **an accepted, documented divergence** from the primary `custody_expires_at` clock for MVP scope, not a resolved parity guarantee — S3 Lifecycle does not support a per-object, creation-date-anchored noncurrent expiration; `NoncurrentDays` is a single rule-level value. AC-A1-7 is still satisfied in the sense that matters (noncurrent versions are guaranteed to expire via the daily lifecycle sweep and do not persist indefinitely), but the exact disposal instant for a noncurrent version does not track the same clock as the record's original custody-period computation.

### Decision 3: Legal Hold via TTL-Attribute Removal, Not TTL-Value Mutation (DynamoDB)

Every DynamoDB record subject to enforcement carries two distinct fields, deliberately separated:

- `custody_expires_at` (Number, epoch seconds) — the deterministic, always-computed expiry instant (`created_at + custody_period_seconds`). This field is never modified by hold state changes; it is the record's permanent "when would this expire absent any hold" fact.
- `ttl_disposal_at` (Number, epoch seconds) — the actual DynamoDB Time to Live attribute configured on `MetadataTable`. This is the only field DynamoDB's TTL sweep acts on.

**Amendment note (deployment-blocking correction):** the paragraph below described a one-time sweep only. It is retained as the description of the sweep's own responsibility, now explicitly scoped (Decision 9) to *pre-existing* records as of the moment a hold's authoritative state commits — it is not, and was never sufficient as, the complete mechanism. Every governed-record write (CREATE or regeneration) must independently condition its own `ttl_disposal_at` decision against the audit identity's *current* authoritative hold state at the moment that specific write commits, per Decision 9. Read this paragraph as "how already-existing records are brought into compliance when a hold is placed," not as "how legal hold is enforced," which is the union of this paragraph and Decision 9.

At write time, `ttl_disposal_at = custody_expires_at` **only if no hold is active for the record's audit identity at that moment** (Decision 9) — the unqualified statement in the original text of this Decision was the root cause of the deployment-blocking defect and must not be read as license to compute `ttl_disposal_at` without a fresh hold-state check on every write. Placing a legal hold issues `UpdateItem REMOVE ttl_disposal_at` across every item under the audit identity's partition (query `PK = CLIENT#{client_id}`, `SK begins_with AUDIT#{audit_id}`) that already exists at the moment the hold's authoritative state has committed — this is the sweep's scope, not the entire mechanism (Decision 9). A record with no `ttl_disposal_at` attribute is permanently exempt from DynamoDB TTL processing — this is standard, documented DynamoDB TTL behavior (items missing the configured TTL attribute are never targeted for deletion). Releasing a hold restores `ttl_disposal_at = MAX(custody_expires_at, now)`, clamping to "now" if the custody period already elapsed while the hold was active, so the record becomes immediately eligible rather than silently skipped (AC-A1-4).

### Decision 4: Disposal Record Triggered by DynamoDB Streams (TTL path) and S3 Event Notifications (Lifecycle path) — Never Assumed as a Synchronous Hook

Neither AWS mechanism offers a synchronous "disposal happened, here is your chance to react" callback. The disposal record (FR-A1-5, AC-A1-6) is therefore built as an asynchronous, event-driven side effect of each mechanism's own native event stream, using the standard AWS pattern for each:

- **DynamoDB path:** `MetadataTable` Streams is enabled (`StreamViewType: NEW_AND_OLD_IMAGES`). A new Lambda (`evidenceDisposalRecorder`) subscribes to the stream and filters for `REMOVE` events where the record's `userIdentity.principalId == "dynamodb.amazonaws.com"` — the documented DynamoDB Streams marker distinguishing TTL-driven deletions from ordinary application `DeleteItem` calls (which RCP does not currently perform, but the distinction is load-bearing for correctness going forward). Only TTL-attributed removals produce disposal records.
- **S3 path:** `RawResultsBucket` S3 Event Notifications are configured for `s3:LifecycleExpiration:*` events (covering both current-version `Delete` and, for the versioned bucket, `DeleteMarkerCreated`), routed through EventBridge to the same disposal-recording Lambda (or a sibling with an identical write path).

This is architecturally new infrastructure not present in any existing phase (see "Infrastructure Impact" below) — Phase 4's evidence lineage manifests and `aggregate_set_hash` establish the *pattern* of durable, queryable evidence-provenance records in the same single table, but no existing phase uses DynamoDB Streams or S3 Event Notifications. This ADR extends the established persistence pattern (a new immutable record type in `MetadataTable`, following the platform's Job-log convention) onto new event-driven infrastructure that the eventual-consistency constraint makes unavoidable.

The resulting `DisposalRecord` is written to `MetadataTable` under a new, non-colliding sort-key namespace (`#DISPOSAL#`) and is itself explicitly exempted from `ttl_disposal_at` assignment — a disposal record is a compliance/audit-trail artifact, not evidence subject to its own custody clock; auto-disposing the record of a disposal would defeat FR-A1-5's purpose. `DisposalRecord.recorded_at` (when RCP became aware) is modeled as distinct from `DisposalRecord.disposed_at` (AWS's own best-available deletion timestamp) to make the eventual-consistency window explicit rather than assumed away.

`#DISPOSAL#` is written exclusively by `evidenceDisposalRecorder`'s own repository code path. The hold-management repository code path (used by `RetentionService`, Decision 2/3) is a structurally separate class with its own SK-write guard asserting it may write only `#LEGALHOLD#` — mirroring the `_assert_phase7_sk` pattern already established in `audit_platform_integrity/repository.py:49`, which guards Phase 7's own writes against straying outside `#CERTJOB#`/`#CERT#`. This is a code-level, programming-error guard, not an IAM-enforced boundary: DynamoDB IAM fine-grained access control conditions on the partition key (`dynamodb:LeadingKeys`) but not on sort-key substrings, so IAM cannot itself restrict `PutItem` calls to items whose SK contains `#DISPOSAL#`. The exclusivity guarantee rests on the same code-structural discipline Phase 7 already relies on for its own namespace separation, applied symmetrically to both new A1 repository classes (see Technical Design §5.2, §6, §12).

### Decision 5: Custody Period as Externally Supplied, Per-Evidence-Class Stack Configuration

The custody-period duration is never hardcoded in application code or in any CloudFormation lifecycle rule literal. It is expressed as **one parameter per evidence class**, per stage, in `infra/serverless.yml`'s `custom.custodyPeriodDays.<class>.${stage}` section (mirroring the existing `logRetentionInDays` per-stage pattern already in that file — `raw_evidence`, `intelligence`, `report`, `certificate`, and, per this ADR's A1.3c.1 amendment, `aggregate_metadata`), consumed as follows:

- Directly by each of the **four S3-backed** evidence classes' rules in `resources/s3.yml`'s `LifecycleConfiguration.Days` / `NoncurrentDays` (CloudFormation-time) — the `raw_evidence` rule references `custom.custodyPeriodDays.raw_evidence.${stage}`, the `intelligence` rule references `custom.custodyPeriodDays.intelligence.${stage}`, and so on; each rule's `Days` is independently configurable and there is no shared or default value across rules. `aggregate_metadata` has no S3 presence (Phase 4 writes governed evidence to DynamoDB only, confirmed structurally — `AggregationRepository` takes no S3 client dependency) and therefore receives no corresponding S3 `LifecycleConfiguration` rule; the S3-side structure remains exactly four rules.
- As Lambda environment variables, consumed by application write paths (Phase 1/2/4/5/6/7 record-write call sites) to compute `custody_expires_at` at write time, keyed by the same evidence-class value — this is the **only** consumption path for `aggregate_metadata`'s parameter (`CUSTODY_PERIOD_DAYS_AGGREGATE_METADATA`), since it has no S3-side rule to feed.

No default value is defined by this ADR, for any evidence class. Per AC-A1-5, the mechanism must be fully designed and code-complete without a duration value; the actual numbers are a separate, lower-priority Product Strategy decision (SDLC Verification Gate §9 item 6), and may ultimately differ per evidence class or turn out identical — either way, the per-class structure accommodates both outcomes without a code change. Deployment of the S3 lifecycle rules is consequently gated on those values being supplied — each of the four S3-backed per-evidence-class `LifecycleConfiguration` rules requires its own concrete numeric `Days` value, so the infrastructure change can be written and reviewed now but cannot be deployed to any stage until all four S3-side parameters are populated. `aggregate_metadata`'s Lambda-environment-variable parameter is independently gated the same way — its Phase 4 write paths must fail closed (`CUSTODY_PERIOD_CONFIG_MISSING`) whenever `CUSTODY_PERIOD_DAYS_AGGREGATE_METADATA` is unset, empty, non-numeric, zero, negative, or otherwise not a positive integer, mirroring the existing `raw_evidence` write path's own established fail-closed pattern (`packages/storage/dynamodb_client.py::_resolve_custody_period_days_env`). A1.2's QA validation independently confirmed the S3-side fail-closed behavior: `sls print --stage dev` fails at variable-resolution time with eight "Value not found" errors (four `Days` + four `NoncurrentDays` references, one pair per evidence class), not a self-reported claim.

**Each evidence class's custody-period value is independently and exclusively authorized for that class.** No evidence class may inherit, default to, borrow, or otherwise reuse another class's configured duration — `aggregate_metadata` reusing `raw_evidence`'s value (or any other class's) would violate this Decision as directly as hardcoding a duration would, even though both classes may eventually receive numerically identical values as a separate, later Product Strategy decision. See new Non-Negotiable Invariant 26.

**Amendment (A1.3d.0 — consolidation onto one authoritative configuration source):** Phase 5, 6, and 7 (`intelligence`, `report`, `certificate`) are CLI-only (Decision 10) — there is no Lambda `environment:` block to bind a value to, unlike `raw_evidence`/`aggregate_metadata`. Introducing a second, independent configuration mechanism for these three classes (e.g., a standalone shell environment variable read directly by the CLI) would create a second source of truth that could drift from the same class's S3 Lifecycle duration, violating this Decision's own "no evidence class may inherit, default to, borrow, or otherwise reuse another class's configured duration" principle at the *mechanism* level even if each class's own value were kept distinct.

Decision 5 is therefore consolidated: **all five evidentiary custody classes — `raw_evidence`, `aggregate_metadata`, `intelligence`, `report`, `certificate` — are configured from one authoritative, checked-in, stage-indexed source: `config/custody_periods.json`**, keyed by evidence class and stage under the fixed schema Technical Design §20.3 defines, with no duration values present in this ADR or in the file until a separate, later Product Strategy decision populates them. Two consumers derive values from this one source, never from each other or from any independent source:

- **Serverless/infrastructure side**: the S3-backed evidence classes' `LifecycleConfiguration` rules and `infra/serverless.yml`'s Lambda `environment:` bindings (currently only `aggregate_metadata`, on `auditAggregation`) resolve their values from this file via Serverless Framework's native external-file reference syntax — not from hand-authored inline YAML. **`aggregate_metadata`'s existing A1.3c.1 inline entry must migrate to this same source** — this ADR does not authorize a permanent state where `aggregate_metadata` has one authority (inline `infra/serverless.yml`) while `intelligence`/`report`/`certificate` have a different one (the new file). **Exactly four evidentiary S3 Lifecycle rules exist today, already provisioned by A1.2, one each for `raw_evidence`, `intelligence`, `report`, and `certificate`** (`infra/resources/s3.yml`) — this amendment changes where each rule's `Days`/`NoncurrentDays` value is sourced from, not the rule count, which is unchanged. `aggregate_metadata` has no S3-backed rule and receives none (DynamoDB-only, per its A1.3c.1 amendment). A fifth, separately governed S3 Lifecycle rule exists for `retention-markers/` disposal (Invariant 22) — operational, not evidentiary, and outside this evidentiary-class enumeration.
- **CLI side**: Phase 5/6/7's write-capable commands resolve their class's value from the same source through the dedicated, command-scoped `CustodyPeriodConfigLoader` (Technical Design §20.4) — never through a standalone environment variable, and never added to the CLI's global required-configuration set (which would incorrectly gate every unrelated CLI command on a value only three commands need).

`retention_marker` is represented in the same physical file, under a schema-distinct, separately named section (Technical Design §20.3) for operational convenience — it is marker-disposal configuration, not evidentiary custody, and is never read by either consumer above as if it were a sixth evidentiary class.

Missing or invalid stage/class values preserve this Decision's existing fail-closed behavior on both sides: Serverless-side rendering/packaging/deployment fails at variable-resolution time (unchanged mechanism, now sourced from the external file instead of inline YAML); CLI-side resolution fails closed with `CUSTODY_PERIOD_CONFIG_MISSING` before any AWS-client construction (Invariant 30). No default or fallback value is introduced on either side by this amendment.

### Decision 6: Backlog Handling Is a Distinct, Explicitly Flagged Migration Decision (Not Silently Resolved)

See "Assumption Requiring Confirmation" below. This ADR does not decide backlog policy; it documents the recommended default and requires confirmation before implementation.

### Decision 7: Failure Destinations Are Mandatory on Both `evidenceDisposalRecorder` Event Source Mappings, With an Alarm on Dead-Letter Depth

`evidenceDisposalRecorder`'s two event sources (the `MetadataTable` DynamoDB Streams event source mapping, and the EventBridge rule delivering S3 `LifecycleExpiration` notifications) are each configured with an explicit failure destination — an SQS dead-letter queue (`evidenceDisposalRecorderDLQ`) — rather than relying on retry-then-silent-drop default behavior. The DynamoDB Streams mapping additionally sets `BisectBatchOnFunctionError: true` and a bounded `MaximumRetryAttempts`, so a single malformed record in a batch cannot indefinitely block or silently discard the rest of the batch. A CloudWatch alarm on the DLQ's `ApproximateNumberOfMessagesVisible` metric is provisioned so a dropped disposal-recording attempt is an observable, alerted condition, not a silent gap in FR-A1-5's durable-record guarantee. See Technical Design §6 and §13 for the concrete configuration.

### Decision 8: A Governed-Record Boundary — Only Two of Six Record Categories Ever Receive Custody Metadata

**Amendment (pre-A1.3, following A1.2 QA and an independent ground-truth investigation):** an independent investigation of the repository found the Technical Design's write-path inventory materially incomplete (7 rows documented versus 32 actual write call sites), and Product Strategy withheld A1.3 execution authorization pending correction. The fuller inventory exposed an ambiguity this ADR's original text did not resolve: FR-A1-6's "regardless of which phase wrote them" language, read literally against the corrected inventory, would appear to require `custody_expires_at`/`ttl_disposal_at` on every DynamoDB record sharing an audit partition — including `AuditMetadata` (the canonical audit anchor), `AggregationJob`/`IntelligenceJob`/`ReportJob`/`CertificationJob` (pipeline job logs), and `ScheduleOccurrenceClaim` (a pure duplicate-delivery guard) — none of which carry evidentiary content of their own and several of which other records' referential integrity structurally depends on remaining present.

This ADR is amended to state explicitly: **FR-A1-6's "uniform coverage" requirement means every governed-evidence and evidence-derived-artifact record is covered by the mechanism, not that every record sharing an audit partition is.** The Technical Design (§18.1, amended alongside this ADR) defines six categories — governed evidence, evidence-derived artifact, operational coordination metadata, governance metadata, configuration/input artifact, and explicitly excluded/separately governed — and only the first two ever receive `custody_expires_at`/`ttl_disposal_at`/`rcp-legal-hold`/`rcp-evidence-class`. This decision does not change any evidence-class scope already established by Decisions 1–7; it clarifies which DynamoDB *record types* fall within that scope, a distinction the original Decision text did not need to make because the original write-path inventory did not yet reveal how many non-evidentiary record types share the same audit partition.

A second correctness gap the fuller inventory exposed: three independent, previously undocumented regeneration mechanics exist for evidence-derived-artifact records (Phase 5 full-overwrite, Phase 6 partial-update, Phase 7 unconditional full-overwrite with no write condition at all), none of which had any defined behavior for `custody_expires_at`/`ttl_disposal_at` on regeneration. Left unresolved, this created a concrete risk that a force-regeneration of a report or certificate under an active legal hold could silently reintroduce `ttl_disposal_at` on a record that should remain exempt from disposal while held — the exact failure mode Decision 3 exists to prevent, just reached through a different code path (regeneration) than Decision 3's own text anticipated (initial write, hold placement, hold release). The Technical Design (§18.4) resolves this as one governed rule applying identically across all three phases; Non-Negotiable Invariant 8 below carries the rule's non-negotiable core forward into this ADR.

### Decision 9: Legal Hold Is a Continuously Authoritative, Versioned State — Not a Point-in-Time Sweep

**Amendment (deployment-blocking correction).** Decision 3's sweep (`UpdateItem REMOVE ttl_disposal_at` across existing items; `CustodySweepClient`, already merged) protects only records/objects that exist at the moment it runs. §18.4's regeneration rule likewise only specified "read hold status fresh, then decide" for regeneration writes — a plain read-then-decide, without a mechanism to detect the hold state changing between the read and the write's commit, which is the identical race class this Decision closes, just previously left unclosed for both CREATE and regeneration paths alike. Product Strategy's governing requirement: *"Once an audit is under active legal hold, every existing and subsequently created governed record or object associated with that audit must remain ineligible for automated disposal until the hold is released."* A sweep, however complete at the instant it runs, cannot satisfy "subsequently created" by itself — new writes arrive continuously across an audit's scheduled execution window (confirmed: RUN records via repeated scheduled invocations; Phase 4 aggregation triggering via finalization, which can itself fire more than once per audit through the finalization-retry path) and, until this Decision, computed their own custody fields with no awareness of hold state at all.

**The `LegalHold` record gains an authoritative, monotonically incrementing `hold_version` (Number), incremented on every write to the record — every `PLACE` and every `RELEASE`, with no exception — and a `sweep_status` field (`PENDING` \| `IN_PROGRESS` \| `COMPLETE` \| `FAILED`), tracked independently of `status` (`ACTIVE`/`RELEASED`).** `status` answers "is this audit currently held"; `sweep_status` answers "has the pre-existing-record sweep for the current hold episode finished" — conflating the two would let a caller treat an in-progress sweep as if it had already brought every pre-existing record into compliance. `hold_version` is the optimistic-concurrency token every governed-record write conditions against; it is deliberately a dedicated counter, not a reuse of `status`, because a `PLACE → RELEASE → PLACE` cycle can return to an identical `status` value while representing a materially different governance state, and a plain equality check on `status` would fail to detect that transition.

**Placement is effective before the sweep begins, not after or concurrently with it — this ordering was already correct in the existing design and is preserved, not changed:** `HoldRepository.upsert_hold` (status → `ACTIVE`, `hold_version` incremented, `sweep_status` → `PENDING`) is written and durably committed *before* `CustodySweepClient`'s sweep starts, exactly as Technical Design §10.4's existing sequence already shows (`HoldRepository` writes precede `CustodySweepClient` calls). This Decision makes that ordering load-bearing rather than incidental: it is the property that guarantees every write whose own hold-state read happens after the commit observes `ACTIVE`, regardless of whether the sweep covering pre-existing records has finished.

**Every Category 1/2 governed-record write — CREATE and regeneration alike, both per §18.4 as amended by this Decision — must read the current `LegalHold` state, compute its custody fields accordingly, and commit through a mechanism that atomically verifies `hold_version` has not changed since that read**, using DynamoDB `TransactWriteItems` (a `ConditionCheck` against the `LegalHold` item's `hold_version`, paired with the governed record's own `Put`/`Update` in the same transaction) — reusing this codebase's existing `TransactWriteItems` pattern (`AggregationRepository.put_records_once`) and its existing optimistic-concurrency idiom (`AuditMetadataRepository.append_lifecycle_transition`'s `lifecycle_state = :expected_state`), rather than inventing new infrastructure. A plain read-then-write, without this atomic condition, is insufficient and is not adopted (see Alternatives Considered) — it narrows the race window but does not close it, and Product Strategy's governing requirement admits no residual window.

**S3 has no equivalent transactional primitive spanning a DynamoDB item and an S3 object**, so S3 objects are protected by mechanisms that do not depend on cross-service transactionality:

**Amendment (Product Strategy directive, post-review of an earlier revision of this Decision):** an earlier revision made a Lambda-wall-clock-vs-`LastModified` buffer the *primary* mechanism closing the S3-side race, with a canary-marker approach documented only as a rejected-for-now, provably-tighter alternative. Product Strategy's reasoning: legal hold is a constitutional evidence-integrity control, and a known, avoidable, formally-unprovable uncertainty (undocumented cross-service clock skew between Lambda and S3) must not be the *primary* correctness mechanism for it merely because the more rigorous alternative requires more coordination — hold placement/release are low-frequency, operator-invoked, non-hot-path operations, so the additional coordination cost is justified. **The canary-marker mechanism is therefore the default, primary S3 coordination protocol, not an alternative.** A small governance-metadata marker object is written to a dedicated, non-evidence S3 prefix immediately after each hold transition's DynamoDB commit, and its own `LastModified` — read back via `HeadObject`, in S3's own clock domain — anchors the reconciliation pass's boundary, eliminating cross-service (Lambda-vs-S3) clock skew as a source of error. The 5-second buffer from the prior revision is retained, but only as defense-in-depth around the marker boundary (covering the marker-write's own small, characterizable latency plus `LastModified`'s second-granularity truncation) — not as the mechanism correctness depends on. Every S3 write still reads current hold state immediately before `PutObject` and tags accordingly (replacing today's hardcoded `rcp-legal-hold=false` tagging), using a `ConsistentRead` DynamoDB `GetItem` scoped specifically to these S3-side reads — not to the DynamoDB write path's own pre-transaction read, which remains at default consistency since `TransactWriteItems` already makes a stale read there harmless (a related, independently-identified and precisely-scoped fix: an eventually-consistent read has no transactional backstop on the S3 leg the way it does on the DynamoDB leg). This is not a best-effort "hope it catches everything" mechanism: the marker's scope is a specific, bounded time window anchored to a same-clock-domain reference with a specific, checkable completion condition (every object at or after the marker's confirmed timestamp carries the correct tag), not an open-ended reconciliation loop. Full protocol: Technical Design §19.5.

**Amendment (Product Strategy directive, new required correction — release-side race):** the same marker-plus-reconciliation mechanism applies symmetrically to `RELEASE`, not only `PLACE`. An earlier revision of this ADR's companion Technical Design reasoned that release needed no reconciliation pass, on the basis that "fresh reads after release commits produce the correct result." That reasoning addressed only writes reading *after* release; it did not address a write that read `ACTIVE` *before* release committed but whose `PutObject` completes *after* the release-sweep has already run — such a write is never touched by anything afterward and remains tagged held indefinitely. This is the identical structural race this whole Decision exists to close, reached from the opposite direction, with an over-retention rather than under-protection failure mode (satisfying Non-Negotiable Invariant 14's bias toward retention in the narrow technical sense, but not a reason to leave it open — indefinite unintended over-retention is its own real defect). `RELEASE` now performs the identical marker-write, marker-confirmation, and marker-anchored reconciliation steps `PLACE` does. Full protocol: Technical Design §19.3, §19.5.

**Amendment (Product Strategy directive, real concrete defect found — marker key collision between `PLACE` and `RELEASE`):** the marker key format in the prior revision (`retention-markers/{client_id}/{audit_id}/{hold_id}.marker`) did not structurally guarantee `PLACE` and `RELEASE` produce distinct keys — its non-collision argument rested entirely on `hold_id` being freshly generated per transition, a property that was true (verified directly against the already-merged `HoldRepository.write_hold_event`'s conditional-once write semantics: a per-episode, shared `hold_id` would make every `RELEASE`'s event-log write collide with its paired `PLACE`'s already-written event) but was asserted rather than structurally reinforced in the marker key itself. **The corrected key format at the time, `retention-markers/{client_id}/{audit_id}/{hold_id}/{hold_version}-{transition}.marker`, was reasoned to derive non-collision from two independent, differently-sourced components** — freshly-generated `hold_id` and monotonically-incremented `hold_version` (Invariant 12) — rather than from a single identifier's semantics alone, per Invariant 21 as originally worded. **This reasoning is corrected below — the key format itself is unchanged, but the non-collision proof and the `hold_id` freshness premise it rested on are superseded.** Full original proof: Technical Design §19.5.2 (original form).

**Correction (Product Strategy — required identity correction, superseding this amendment's original reasoning above): the claim that non-collision rested on `hold_id` being freshly generated per transition is not accepted as the identity model.** `hold_id` identifies one legal-hold episode from `PLACE` through `RELEASE` and must remain constant across that pair (Invariant 21, corrected). The original reasoning was directionally right about a real code-level risk — `HoldRepository.write_hold_event`'s existing SK (`AUDIT#{audit_id}#LEGALHOLD#{hold_id}`) does collide across a `PLACE`/`RELEASE` pair if `hold_id` is shared, exactly as originally described — but the fix is not to make `hold_id` fresh per transition; it is to make `LegalHoldEvent`'s own SK transition-safe by incorporating `hold_version` (new Invariant 25), the same discriminator the marker key already uses. Full detail: Technical Design §19.5.1's "Required consequence," §19.5.2.

**Amendment (Product Strategy directive — purpose-limited marker retention, not indefinite):** the prior revision justified indefinite marker retention by analogy to `LegalHoldEvent`/`DisposalRecord`'s own permanent retention (Category 4 precedent, Invariant 8). Product Strategy's correction: the locked Evidence Retention and Disposal Policy applies purpose limitation independent of S3 prefix — living outside the four evidence-class prefixes is not itself a basis for indefinite retention. The marker's governance purpose is narrower than `LegalHoldEvent`/`DisposalRecord`'s (a purely operational bootstrapping artifact, not the durable compliance record itself) and ends once `sweep_status = COMPLETE` is recorded for its own transition; disposal thereafter is via a dedicated, deferred-duration S3 Lifecycle rule on the `retention-markers/` prefix, per new Non-Negotiable Invariant 22. `LegalHoldEvent`'s own permanent retention is unaffected by this correction and remains the durable record of the transition's occurrence, timing, and outcome. Full protocol: Technical Design §19.5.8.

**Every ambiguous or race-uncertain outcome resolves toward retention, never toward disposal eligibility** — stated once here as a named principle because it recurs throughout the mechanism's design (a `TransactWriteItems` failure forces a retry rather than a fallback write without the condition; an S3 write racing a hold's commit is, at worst, over-tagged `true` and corrected by reconciliation, never under-tagged `false`). This is the same governing bias the Product Constitution already states for this workstream ("Trust Before Convenience"), applied specifically to the concurrency boundary this Decision closes.

## Rationale

### Why tag-filter inversion instead of Object Lock

Object Lock is the AWS-idiomatic mechanism for true legal hold (`s3:PutObjectLegalHold`), but it is a bucket-creation-time property. `RawResultsBucket` is already deployed with versioning enabled and in active use; retrofitting Object Lock would require either an AWS Support-mediated bucket-level exception (not guaranteed to be granted, not something this platform can depend on) or a bucket migration (create new bucket, copy all objects and versions, cut over, decommission old bucket) — a materially larger, riskier, and slower change than what FR-A1-4 requires. The tag-filter inversion pattern is a documented, supported AWS approach for conditional lifecycle exclusion and works on the bucket as it exists today.

### Why TTL-attribute removal instead of TTL-value mutation

Setting `ttl_disposal_at` to a far-future sentinel value on hold would work but conflates "held" with "expires very late," which is fragile (a bug or misconfigured sentinel could silently un-hold evidence) and loses the clean distinction between "the custody clock" and "the AWS deletion trigger." Removing the TTL attribute entirely is the more defensible design: DynamoDB's own TTL semantics guarantee an item with no TTL attribute is never a deletion candidate, so the hold is enforced by DynamoDB itself, not by trusting a computed future date to remain correct.

### Why event-driven disposal recording rather than a polling reconciliation job

A cron-style Lambda that periodically diffs the table/bucket against a "what should still exist" expectation was considered and rejected (see Alternative 3): it requires maintaining a separate durable inventory to diff against — which duplicates exactly the tracking problem the disposal record is meant to solve — and introduces a detection lag bounded only by the poll interval. Subscribing directly to each AWS mechanism's own change-event stream is lower-latency, requires no separate inventory, and is the standard, documented pattern for reacting to DynamoDB TTL deletions specifically.

### Why the same disposal record schema for both S3 and DynamoDB disposals

A single `DisposalRecord` type (differentiated only by `disposal_mechanism` and `disposed_identity_ref` shape) keeps the compliance-facing query surface ("show me everything disposed for this audit identity") to one record type and one sort-key namespace, consistent with the platform's existing convention of one queryable record type per concern rather than parallel per-source schemas.

### Why a canary marker rather than relying on the buffer alone

A 5-second Lambda-wall-clock-vs-`LastModified` buffer, standing alone, is a real narrowing of the S3-side race window but rests on an open-ended, AWS-undocumented quantity (cross-service clock skew) as its correctness argument — structurally the same category of gap as Alternative 6's plain read-then-write for DynamoDB, just smaller in practice. Legal hold is a constitutional evidence-integrity control; Product Strategy's judgment is that a known, avoidable, formally-unprovable uncertainty must not be the primary mechanism protecting it when hold placement/release are infrequent, operator-invoked, non-hot-path operations for which additional coordination cost is cheap to absorb. Writing a small marker object and reading back its own `LastModified` moves the reconciliation boundary into the same clock domain as the evidence it protects, converting the correctness argument from "bounded by an unknowable inter-service skew" to "bounded by a single S3 API round-trip's own latency" — a categorically stronger argument, evaluable against a concrete, boundable quantity. The buffer is not discarded; it is demoted from primary mechanism to defense-in-depth around a now-much-narrower risk.

### Why a dedicated `hold_version` counter and `TransactWriteItems`, not a simpler read-then-write

A plain read-then-write ("read `LegalHold.status`, then `PutItem`/`UpdateItem` the governed record accordingly") was considered as the minimal fix and rejected (see Alternative 6). It narrows the race window versus today's no-check-at-all behavior but does not close it: the hold state can still change in the interval between the read and the write's commit, and nothing detects that it did. Product Strategy's governing requirement — "must remain ineligible for automated disposal until the hold is released" — has no tolerance for a residual window, however narrow. `TransactWriteItems` with a `ConditionCheck` is the only mechanism in this codebase's existing toolkit that makes the read-then-write atomic against a concurrent change to the exact state being read, which is what a residual-window-free guarantee requires. A dedicated `hold_version` counter, rather than conditioning on `status` directly, closes the specific edge case where a `PLACE → RELEASE → PLACE` cycle returns to a previously-observed `status` value without the concurrency check detecting that anything happened in between.

### Why a mandatory dead-letter queue rather than relying on structured-log-and-retry alone

FR-A1-5 requires disposal to produce a *durable, queryable* record — not merely a best-effort attempt. Lambda event source mappings retry a bounded number of times by default and then, absent an explicit failure destination, simply drop the failed batch with only a CloudWatch Logs trace as evidence anything went wrong. For a compliance-facing guarantee, "the record might exist, check the logs" is not durable in the sense FR-A1-5 requires. An explicit DLQ turns a dropped disposal-recording attempt into a queryable, alertable artifact in its own right, and the CloudWatch alarm ensures an operator is notified rather than discovering the gap only during an after-the-fact compliance audit.

## Consequences

### What This Architecture Enables

- Evidence in both `RawResultsBucket` and `MetadataTable` is disposed of automatically once its custody period elapses, with no scheduled operator task required — closing the "operator-discipline-only" gap both SDLC review passes identified.
- Legal hold is a genuine technical override, not a configuration flag that disables enforcement platform-wide; only the held audit identity's evidence is exempted.
- **Legal hold protection now covers the full lifetime of an active hold, not only the instant it was placed, and now covers both `PLACE` and `RELEASE` symmetrically** — governed records and objects created at any point while a hold is active, including those written concurrently with a placement or release transition itself, are correctly protected (Decision 9). **The closure is not identical in kind on the two legs, and this is stated precisely rather than glossed over:** the DynamoDB leg is closed provably, to zero residual window — `TransactWriteItems`' `ConditionCheck` makes the hold-state read and the governed write's commit atomic against each other, and no timing condition can defeat it (Technical Design §19.4). The S3 leg is now closed via the canary-marker mechanism — a same-clock-domain timestamp reference, eliminating cross-service (Lambda-vs-S3) clock skew as an error source — bounded by a small, characterizable window (single-marker-write latency plus `LastModified` truncation, with a 5-second buffer retained as defense-in-depth), materially tighter and more rigorously argued than the empirically-reasoned, open-ended-clock-skew bound the S3 leg previously rested on (Technical Design §19.5). This is a substantially stronger closure than before, evaluable against a concrete, boundable quantity (S3 API latency) rather than an unknowable one (inter-service clock drift) — but it is still not identical in kind to the DynamoDB leg's zero-timing-dependency guarantee, and this document does not claim otherwise. Both legs, and both transition directions, now satisfy the deployment-blocking defect Product Strategy identified; the DynamoDB leg satisfies it with a formal proof of closure, the S3 leg with a tightly-bounded, same-clock-domain closure that is materially stronger than, but not identical to, a formal proof.
- Every disposal action produces a durable, queryable record, satisfying the Evidence Principle that disposal itself must not become an unaccountable action.
- The custody-period value remains a pure configuration input; Product Strategy can set or later change it without any code change.

### Constraints This Architecture Creates

- **Legal hold placement/release on S3 is not instantaneous for large evidence sets.** Because tags are per-version and must be set on every extant version under an audit identity's key prefixes, placing a hold on an audit with a large evidence footprint requires enumerating and re-tagging potentially many object versions. This is an operational latency characteristic that must be surfaced to operators (see Technical Design, Reliability section), not a correctness gap — the hold record itself (`LegalHold` DynamoDB item) is written atomically and immediately; the S3 re-tagging sweep is the part that takes wall-clock time proportional to evidence volume.
- **Disposal records lag actual disposal by an unspecified, eventually-consistent window.** DynamoDB TTL deletion is best-effort within ~48 hours of expiry; S3 Lifecycle evaluation runs once per day. `DisposalRecord.recorded_at` will therefore trail the true evidence age at disposal by a variable amount. Any compliance report built on `DisposalRecord` data must treat "disposed by" as approximate, not exact-to-the-second.
- **This ADR introduces new infrastructure (DynamoDB Streams, EventBridge S3 notifications, a new Lambda, a dead-letter queue) that does not exist in any current phase.** This is a genuine infrastructure expansion, not a reuse of an existing pattern, and must be reviewed accordingly (see Non-Negotiable Invariants and Traceability).
- **`#DISPOSAL#` write-exclusivity is a code-level guarantee, not an IAM-level one.** DynamoDB IAM policies cannot condition `PutItem` on sort-key substrings (only on the partition key, via `dynamodb:LeadingKeys`), so the guarantee that only `evidenceDisposalRecorder` writes `#DISPOSAL#` items rests on the same per-repository-class SK-write assertion pattern Phase 7 already relies on for its own namespace separation — a defense against programming error, not a hard security boundary. This is an accepted, documented limitation of DynamoDB's access-control model, not unique to this design.
- **The mechanism cannot be operationally activated (none of the four per-evidence-class lifecycle rules can deploy) until Product Strategy supplies the custody-period value(s) — one per evidence class, potentially all identical or all different.** The code and infrastructure templates can be complete and reviewed without those values; the deployment step is gated on all four being populated, confirmed by A1.2 QA as genuine fail-closed behavior (`sls print` variable-resolution failure), not self-reported.
- **Retroactive restoration of already-disposed evidence is impossible.** A legal hold placed after evidence has already been disposed cannot undo the disposal; this is a hard AWS-mechanism limitation (deletion is deletion), not a gap in this design, and must be stated explicitly to operators rather than discovered operationally (per the Product Spec's own Edge Cases section).
- **Every Category 1/2 governed-record write becomes a `TransactWriteItems` call instead of a plain `PutItem`/`UpdateItem` (Decision 9).** This roughly doubles the write-capacity cost of each such write (DynamoDB prices transactional writes at 2x the throughput of standard writes) and adds a new `dynamodb:TransactWriteItems` IAM requirement to every Category 1/2 write path's execution role. This is an accepted, bounded cost given audit evidence write volume is not extreme, and is the mechanism Product Strategy's governing requirement specifically demands (see Decision 9 rationale) — a plain read-then-write would avoid this cost but does not satisfy the requirement (Alternative 6).
- **Cross-store (DynamoDB/S3) atomicity is not attempted and is not required.** A `RunMetadata` record and its sibling raw-evidence S3 object may each independently observe a hold-state change at a slightly different moment (they are separate writes, at different points in the execution sequence, to different stores with no shared transaction). This is acceptable because each store achieves correctness independently, via its own coordination mechanism (Decision 9) — the governing requirement is "no store ever incorrectly resolves toward disposal eligibility," not "both stores observe the hold state at the identical instant."

## Alternatives Considered

### Alternative 1: Enable S3 Object Lock on `RawResultsBucket` for Legal Hold

Rejected. Object Lock cannot be retroactively enabled on the existing, already-versioned, already-populated `RawResultsBucket` without an AWS Support-mediated exception or a full bucket migration. Both paths are materially riskier and slower than the tag-filter inversion approach, for a workstream explicitly scoped to correction, not re-platforming.

### Alternative 2: Set `ttl_disposal_at` to a Far-Future Sentinel Value to Represent "Held"

Rejected. Conflates hold state with a computed date, is fragile against sentinel-value bugs, and loses the clean separation between "the evidence's real expiry" and "the value DynamoDB acts on." TTL-attribute removal is a stronger, AWS-semantics-backed guarantee.

### Alternative 3: Polling Reconciliation Job Instead of Stream/Event-Driven Disposal Recording

Rejected. Requires maintaining a separate durable "expected inventory" to diff against, which duplicates the very tracking problem the disposal record exists to solve, and introduces detection latency bounded by poll interval rather than by AWS's own event delivery latency. DynamoDB Streams and S3 Event Notifications are the standard, purpose-built mechanisms for this exact problem.

### Alternative 4: A Single Combined Custody-Period Value for All Evidence Classes

Rejected as the mandated design. The Product Spec's Constraints section is explicit: "Must not assume a single, uniform custody period across all evidence classes unless Product Strategy explicitly confirms that assumption." The per-evidence-class parameterization in Decision 5 keeps this option open without foreclosing a future uniform-value decision — a uniform value can always be supplied as the same number for every class; the reverse (retrofitting per-class granularity onto a hardcoded uniform value) would require a code change. A1.2 implemented Decision 5 as four independent `LifecycleConfiguration` rules on `RawResultsBucket` (Decision 1 amendment) rather than one bucket-wide rule with a shared `Days` value — confirming this alternative was correctly avoided at the infrastructure level, not merely at the configuration-schema level.

### Alternative 5: Retroactively Apply the Full Custody Period to Pre-Existing Evidence, Clocked From Original `created_at`

Rejected as the recommended default (see Assumption below). This would cause a mass, simultaneous disposal event across the entire pre-Workstream-A evidence backlog the moment the mechanism activates in a given stage — an operationally dangerous "big bang" deletion with no operator control over timing or blast radius.

### Alternative 6: Plain Read-Then-Write of Hold State, No Transactional Conditioning

A governed-record write would call `HoldRepository.get_legal_hold(...)`, decide whether to include `ttl_disposal_at` based on the observed `status`, and then perform its existing `PutItem`/`UpdateItem` unchanged — no new transaction, no new IAM permission, no new `hold_version` field.

**Rejected.** This is a real narrowing of the race window versus today's behavior (which performs no hold-state read at all) but does not close it: `LegalHold.status` can change between the read and the subsequent write's commit, and this design has no way to detect that it did. Product Strategy's governing requirement is explicit that "subsequently created" records must remain protected with no stated tolerance for a residual race window, however small. This alternative would also leave the exact same class of defect that motivated this Decision — a write silently computing incorrect custody fields because it observed stale hold state — merely with a smaller probability of occurrence, not a structural guarantee against it. Smaller-probability-but-still-possible is not what "must remain ineligible... until the hold is released" specifies.

### Alternative 7: DynamoDB Streams Reactive Catch-Up Instead of Write-Time Coordination

A governed-record write would proceed unconditionally, exactly as today, with no hold-state read at all. A separate consumer of `MetadataTable`'s existing DynamoDB Streams would react to every new-item event, check current hold state, and retroactively remove `ttl_disposal_at` from any newly-created record that should have been protected.

**Rejected.** Stream delivery has inherent, non-zero, AWS-documented latency between an item's write and a consumer observing the corresponding stream event — this reintroduces the identical structural defect Decision 9 exists to close, just shifted from "sweep runs once, at an arbitrary point after placement" to "catch-up runs once, at an arbitrary point after each write," with the same category of window in between during which a newly-written record is visible (to any reader, including the S3/DynamoDB Lifecycle mechanisms themselves) with an incorrect `ttl_disposal_at` value. A record created and then disposed by DynamoDB's own TTL sweep before the streams-based catch-up consumer ever processes its creation event is not a bounded, no-worse-than-accepted risk the way the S3 reconciliation pass's clock-skew buffer is (Decision 9, Technical Design §19.5) — it is an unbounded window with no upper bound on stream-processing lag under load or partial outage. This alternative was considered specifically because DynamoDB Streams already exists in this design for disposal recording (Decision 4) and reusing it here would avoid new infrastructure — but reduces to strictly worse race-safety than the `TransactWriteItems` mechanism actually adopted, for no corresponding benefit, and is rejected on that basis alone.

### Alternative 8: 5-Second Lambda-Wall-Clock Buffer as the Sole/Primary S3 Coordination Mechanism, No Canary Marker

The S3 leg's correctness would rest on comparing `LastModified` against a Lambda-wall-clock timestamp (`sweep_started_at`) captured by the orchestrating process, widened by a reasoned, conservative buffer (5 seconds) to absorb cross-service clock skew and `LastModified` truncation — no marker object, no additional S3 write, no `ConsistentRead` requirement. This was this ADR's own prior position (superseded here) and is documented as a rejected alternative for traceability, not silently dropped.

**Rejected, on Product Strategy's explicit direction, not on a newly-discovered correctness flaw.** The buffer, properly sized, is a legitimate, reasoned bound — the architecture + security review that required it found it sufficient as *a* closure. Product Strategy's objection is categorical, not a claim the buffer is unsound: legal hold is a constitutional evidence-integrity control, and resting its *primary* correctness argument on an open-ended, AWS-undocumented cross-service clock-skew quantity — however conservatively bounded — is not acceptable when a more rigorous, same-clock-domain alternative exists and the operations in question (hold placement/release) are infrequent enough that its added coordination cost is immaterial. This alternative is not rejected because it fails to work; it is rejected because a stronger, still-practical mechanism exists and the stakes justify using it as the default rather than treating it as unnecessary extra rigor. The buffer is retained under the adopted design (Decision 9), demoted to defense-in-depth around the marker boundary rather than eliminated.

### Decision 10: Phase 5–7 Remain CLI-Only — No Lambda Infrastructure Introduced by Evidence Retention Enforcement

Verified directly ahead of A1.3d: `IntelligenceRepository`, `ReportRepository`, and `CertificationRepository` (and their corresponding engines and publishers) are constructed exclusively in `operator_cli/main.py`. Zero references exist anywhere under `apps/` (the Lambda handlers directory), and `infra/serverless.yml` defines no `functions:` entry for intelligence generation, report generation, or certification. Phase 5 and Phase 6's own locked designs establish operator-CLI invocation as the current, authoritative architecture; Phase 7's certification-independence decision (an operator-invoked, on-demand certification action, deliberately not an automated pipeline stage) preserves the same invocation model.

**This ADR does not introduce Lambda entry points, event-driven triggers, Serverless function definitions, dedicated IAM roles, packaging rules, concurrency configuration, or timeout configuration for Phase 5, 6, or 7 as part of Evidence Retention Enforcement.** Wiring these phases to legal-hold coordination and custody-field computation (A1.3d) is achievable entirely within the existing CLI invocation model — it does not require, and this Decision does not authorize, changing how these phases are invoked. A future decision to add Lambda-based, event-driven, or automated-pipeline invocation for Phase 5–7 (should product requirements ever call for it) is a distinct architecture decision, out of scope for this ADR and not implied by anything in this amendment.

**Consequence for custody-configuration design (Decision 5):** because no Lambda `environment:` block exists for these phases, the Lambda-environment-variable consumption pattern already established for `raw_evidence`/`aggregate_metadata` does not apply to `intelligence`/`report`/`certificate`. See Decision 5's A1.3d.0 amendment and Non-Negotiable Invariants 29–30 for the CLI-appropriate resolution mechanism this requires instead.

### Decision 11: A Three-Mode Construction Boundary for Phase 5–7 Repository and Publisher Classes — Governance Dependencies Are Constructor-Optional, Write-Method-Mandatory

**Correction to the prior A1.3d.0 revision.** The A1.3d.0 constructor boundary (Technical Design §20.4/§20.6–§20.8, as originally drafted) made `hold_repository` and `custody_period_days` mandatory, non-defaulted constructor parameters on `IntelligenceRepository` and its Publisher counterpart. A read-only investigation of `operator_cli/main.py` (A1.3d.2) found this incompatible with current code: `IntelligenceRepository`/`IntelligencePublisher` are constructed at two independent dispatch branches — `retrieve intelligence-*` (read-only retrieval, `main.py:226-230`) and `generate intelligence` (write-capable generation and its `--dry-run` write-free mode, `main.py:335-341`) — sharing the same classes. The same shared-construction pattern is confirmed for Phase 6 (`ReportRepository`/`ReportPublisher`: `retrieve report-*` at `main.py:260-262` versus `generate report` at `main.py:387-388`) and Phase 7 (`CertificationRepository`/`CertificationPublisher`: `retrieve cert-*` at `main.py:288-294` versus `certify audit` at `main.py:431-437`). A mandatory, non-defaulted constructor parameter would force every read-only or write-free invocation to resolve a write-only custody duration and construct an unused `HoldRepository`, contradicting this ADR's own existing principle (Invariant 30; and, before it, the reason `StageConfigLoader.REQUIRED_FIELDS` never gates commands that do not need a given field) that no CLI command resolves configuration it does not use.

**This ADR already has a proven, unmodified precedent for the correct shape**: `AggregationRepository.__init__` (`aggregation/repository.py:148-153`, A1.3c.1) declares `hold_repository: HoldRepository | None = None` — optional, defaulting to `None` — and `put_lineage_page_once` (`aggregation/repository.py:222-225`) guards its own write with `if self._hold_repository is None: raise StorageError("Hold coordination is not configured", "HOLD_COORDINATION_NOT_CONFIGURED")` as its first action, before any hold-state read, transaction-item construction, or AWS request. Decision 11 generalizes this exact, already-working pattern to Phase 5, 6, and 7: construction-time optionality exists solely to accommodate a class shared between write-capable and non-write-capable CLI commands; it is not a general relaxation of constructor validation, and it does not permit a governed write to proceed without both dependencies fully resolved and valid. See Non-Negotiable Invariant 31.

## Non-Negotiable Invariants

These invariants govern the A1 disposal mechanism and are carried forward into the Technical Design and any future implementation:

1. A `DisposalRecord` must never itself carry a `ttl_disposal_at` attribute; disposal records are compliance artifacts exempt from the custody-period mechanism they document.
2. A legal hold, once active, must exempt the held audit identity's evidence from disposal regardless of elapsed custody period, until explicitly released.
3. The custody-period duration must never be hardcoded in application code or in CloudFormation resource literals; it is sourced exclusively from stage/evidence-class configuration.
4. Disposal recording must never assume a synchronous callback from either AWS mechanism; it must be built as a consumer of each mechanism's own asynchronous event stream (DynamoDB Streams for TTL; S3 Event Notifications for Lifecycle).
5. Retroactive restoration of disposed evidence is not a supported operation; a legal hold placed after disposal has occurred has no retroactive effect.
6. `#DISPOSAL#` sort-key items must be written exclusively by `evidenceDisposalRecorder`'s own repository code path; the hold-management repository code path used by `RetentionService` must carry an explicit SK-write guard preventing it from ever constructing a `#DISPOSAL#`-shaped write, mirroring `_assert_phase7_sk` in `audit_platform_integrity/repository.py`.
7. Both `evidenceDisposalRecorder` event source mappings (DynamoDB Streams and the S3-notification EventBridge rule) must configure an explicit failure destination (dead-letter queue); a dropped disposal-recording attempt must be an observable, alertable condition, never a silent no-op.
8. `custody_expires_at` and `ttl_disposal_at` must never be set on a record classified as operational coordination metadata, governance metadata, a configuration/input artifact, or explicitly excluded/separately governed (Technical Design §18.1) — only governed-evidence and evidence-derived-artifact records may carry either field. A write path for any other category that begins setting either field is a governance defect, not a scope expansion, regardless of how the change was introduced.
9. On regeneration of any evidence-derived-artifact record (full-overwrite or partial-update, any phase), `ttl_disposal_at` must be set or omitted based on the audit identity's legal-hold status read fresh at regeneration time — never carried forward, and never set unconditionally — such that a regeneration can never silently reintroduce disposal eligibility on evidence currently under an active legal hold. `custody_expires_at` on regeneration reflects the regeneration event's own timestamp, not the prior generation's, since regeneration produces genuinely new evidence content at a new, never-reused storage key.
10. `CustodySweepClient` (or any future cross-phase custody-field sweep mechanism) is permitted to operate without a per-record-type allowlist only because Invariant 8 guarantees, at every write path, that no ineligible record category ever carries the fields such a sweep acts on. If Invariant 8 is ever relaxed or found violated, any allowlist-free sweep mechanism must be re-evaluated before continued use.
11. No Category 1/2 governed-record write (CREATE or regeneration, any phase) may compute or commit `ttl_disposal_at` without first reading the audit identity's current `LegalHold.hold_version` and committing through a mechanism that atomically verifies that version has not changed since the read. A plain read-then-write, without an atomic version check, does not satisfy this invariant regardless of how narrow the resulting window appears.
12. `LegalHold.hold_version` must be incremented on every write to the record — every `PLACE` and every `RELEASE` — with no exception, and must never be reused, reset, or derived from `status` alone.
13. A legal hold's `status` transition to `ACTIVE` must be durably committed before `CustodySweepClient`'s corresponding sweep begins; a sweep must never be permitted to start, or be treated as authoritative, before the hold state it is meant to enforce has itself been committed.
14. Every ambiguous or race-uncertain outcome in the legal-hold coordination mechanism (DynamoDB transactional retry, S3 write-versus-hold-commit ordering, reconciliation-pass boundary conditions) must resolve toward retention (omit `ttl_disposal_at`, tag `rcp-legal-hold=true`), never toward disposal eligibility. A mechanism that could, under any documented race, silently resolve toward disposal eligibility does not satisfy this invariant.
15. The S3 leg's reconciliation boundary must be anchored to a same-clock-domain (S3-side) timestamp reference — a confirmed canary marker — as its primary mechanism; a cross-service clock comparison (e.g., an orchestrating Lambda's own wall clock) may be retained only as defense-in-depth around that boundary, never as the sole or primary correctness argument.
16. The canary-marker mechanism applies symmetrically to `PLACE` and `RELEASE`. A future change must not reintroduce an asymmetric design that protects one transition direction's S3 writes but not the other's, on the reasoning that one direction's failure mode is "merely" over-retention rather than under-protection — indefinite unintended over-retention is itself a governance defect, not an excused outcome.
17. Every `HoldRepository.get_legal_hold()` read performed as part of a Category 1/2 **S3** write's custody-field computation must use a strongly consistent (`ConsistentRead: true`) `GetItem` — an eventually-consistent read has no transactional backstop on the S3 leg the way it does on the DynamoDB leg. `ConsistentRead` is deliberately *not* required on the DynamoDB write path's own pre-transaction read: `TransactWriteItems`' `ConditionCheck` re-verifies state at commit time regardless of read staleness, making a stale preceding read harmless there (costs an extra retry, never an incorrect commit) — requiring `ConsistentRead` on that path would double read-capacity cost for no corresponding correctness benefit.
18. No Category 1/2 write, on any write path including the raw-evidence write path on Phase 1's critical execution path, may proceed to completion when the audit identity's legal-hold state (DynamoDB) or the transition boundary (S3 marker) cannot be deterministically resolved within the bounded retry count. Fail-closed applies uniformly, with no exception for execution-critical-path writes, no "degrade gracefully" branch, and no partial governed record or object ever represented to a caller as successfully persisted.
19. A canary marker (§19.5.1) must be created via an atomic, first-write-wins conditional write (S3 `PutObject` with `If-None-Match: *`), never via a `HeadObject`-then-`PutObject` check-then-write sequence, regardless of how the resulting marker is subsequently used. This applies identically to the initial write of any marker and to resuming an interrupted sweep for an already-existing `(hold_id, hold_version, transition)`.
20. Every marker-write and marker-read operation must be preceded by a code-level structural guard asserting the target S3 key is exactly `retention-markers/{client_id}/{audit_id}/{hold_id}/{hold_version}-{transition}.marker` for the identity tuple and transition supplied by the caller — mirroring `_assert_retention_sk`/`_assert_disposal_sk`/`_assert_custody_field_only_update`. No write-capable component in this mechanism is exempt from having an equivalent structural guard.
21. `hold_id` identifies one legal-hold episode from its `PLACE` through its eventual `RELEASE` and must remain constant across that pair — it must never be regenerated per transition. Non-collision of any two transitions' canary marker keys (`PLACE`/`RELEASE` of the same episode, or any two transitions across different episodes) must be provable from `hold_version`'s monotonicity alone (Invariant 12), independent of whether `hold_id` differs between them. A key format, or a supporting proof, that relies on `hold_id` changing per transition for non-collision does not satisfy this invariant.
22. A canary marker is purpose-limited, not indefinitely retained. Its governance purpose (transition idempotency, reconciliation/retry, failure recovery, legal-hold verification during the transition's own execution) ends once `sweep_status = COMPLETE` is durably recorded for its own transition; from that point the marker object is eligible for disposal via a dedicated, deferred-duration S3 Lifecycle rule on the `retention-markers/` prefix (no tag-filter condition, since a marker is never itself subject to legal hold). Disposal of the marker object must never remove the durable record that the transition occurred, when, and its outcome — that information must remain permanently available via `LegalHoldEvent` independent of the marker object's own lifecycle.
23. A hold-placement or hold-release invocation observing `sweep_status = COMPLETE` for the current episode must treat that as a terminal, no-further-action state: it must return without writing, re-writing, or reconfirming any canary marker, without re-running the sweep or reconciliation pass, and without modifying any field on the corresponding `LegalHoldEvent`. A stale re-invocation must never be permitted to reach the marker-establishment step merely because the underlying hold's `status` still matches an active or resumable value — `sweep_status`, not `status` alone, gates whether there is anything left to resume.
24. Once a transition's `LegalHoldEvent.marker_status` has been durably recorded as `CONFIRMED`, that record's `marker_confirmed_last_modified` value is authoritative and immutable for the life of that transition. No later invocation may overwrite it, and no later invocation may attempt a new S3 marker write for that transition, regardless of whether the original marker object still exists in S3. Any reconfirmation must read the value from `LegalHoldEvent`, never re-derive it from a fresh S3 write — a mechanism that would silently succeed at re-establishing a marker whose object has been disposed or has aged out does not satisfy this invariant.
25. `LegalHoldEvent`'s sort key must uniquely discriminate every transition of a given `hold_id` — `hold_id` alone is insufficient once Invariant 21 holds it constant across an episode's `PLACE` and `RELEASE`. The sort key (or an equivalent conditional-write discriminator) must incorporate `hold_version` so that no two transitions of the same episode can ever collide on the same `LegalHoldEvent` write, mirroring the identical requirement Invariant 21 imposes on the S3 marker key.
26. Every Category 1 or Category 2 write path that computes custody metadata must resolve its custody period from the authoritative configuration channel for its assigned evidence class. Missing or invalid class-specific configuration fails closed. No evidence class may inherit, default to, or reuse another class's custody period without a separately reviewed governance decision.
27. `IntelligenceJob`, `ReportJob`, and `CertificationJob` are Category 3 operational coordination metadata (Decision 8) and must never receive `custody_expires_at`, `ttl_disposal_at`, `evidence_class`, an evidence-class S3 tag, or A1.LH1 hold-version transactional coordination — extending Invariant 8's general rule with an explicit, named application to these three record types specifically, since Invariant 8 predates A1.LH1/A1.LH2 and did not enumerate evidence-class tags or hold coordination among the governance mechanisms a Category 3 record must never receive. Any implementation introducing hold coordination for Phase 5, 6, or 7 must include negative regression tests proving these three record types remain excluded; the absence of such a test is itself a governance defect, not merely a coverage gap.
28. No Lambda handler, event-driven trigger, Serverless function definition, dedicated IAM role, packaging rule, concurrency configuration, or timeout configuration may be introduced for Phase 5, 6, or 7 as part of Evidence Retention Enforcement (Decision 10). Wiring these phases to legal-hold coordination and custody-field computation must be achieved entirely within the existing operator-CLI invocation model.
29. All five evidentiary custody classes (`raw_evidence`, `aggregate_metadata`, `intelligence`, `report`, `certificate`) must be configured from exactly one checked-in, stage-indexed configuration source. Serverless and runtime consumers must derive the same class/stage value from the same authoritative file and fixed schema, apply equivalent positive-integer validation, and provide no fallback or cross-class reuse — never from two independent sources for different classes, and never from a standalone shell environment variable read directly by a CLI command. `retention_marker` may share the same physical file for operational convenience but remains a logically distinct, non-evidentiary configuration entry and must never be treated as a sixth evidentiary class by either consumer.
30. A CLI command that performs a Category 1 or Category 2 write for Phase 5, 6, or 7 must resolve its evidence class's custody-period configuration in this exact order, before any of the steps that follow it: (1) after argument and stage validation; (2) before AWS client construction; (3) before any AWS call of any kind; (4) before `HoldRepository` construction or any hold-state read; (5) before Job-record creation; (6) before any Category 1 or Category 2 write. Missing, empty, non-integer, zero, or negative configuration must raise `CUSTODY_PERIOD_CONFIG_MISSING` at step (1)'s resolution point, before step (2) ever begins — no environment-variable fallback is permitted for these CLI-only paths, and no unused, never-consumed environment-variable-name constant (e.g. a `CUSTODY_PERIOD_DAYS_INTELLIGENCE` constant with no corresponding read) may be introduced as a placeholder for a mechanism this Invariant already forecloses.
31. Whenever a Phase 5, 6, or 7 repository or publisher class is constructed by more than one CLI command, and at least one of those commands is read-only retrieval or a proven write-free dry run (Decision 11), that class's constructor must accept `hold_repository` (repository and publisher) and `custody_period_days` (repository only) as optional, defaulting to `None` — never a non-`None` default, sentinel, or fallback value. Only the write-capable command's construction path (Invariant 30) may supply non-`None` values for either. This optionality applies to construction only: every governed write method on such a class — `put_intelligence_metadata_once`, `update_intelligence_metadata`, `IntelligencePublisher.write_artifact`, and their Phase 6/Phase 7 equivalents alike — must complete a deterministic governance-dependency preflight before any hold-state read, transaction-item construction, S3 publication, or other AWS mutation, verifying that `hold_repository` is present, that (for repositories) `custody_period_days` is present, and that `custody_period_days` is a positive, non-Boolean integer — never a default duration, a zero or sentinel value, a cross-class fallback, or a duration re-resolved at write-method-call time from configuration or environment; the only source of a non-`None` `custody_period_days` remains the one-time, command-scoped `CustodyPeriodConfigLoader` resolution Invariant 30 already requires. This mirrors `AggregationRepository.put_lineage_page_once`'s existing `if self._hold_repository is None: raise StorageError("Hold coordination is not configured", "HOLD_COORDINATION_NOT_CONFIGURED")` guard exactly, extended with the equivalent duration presence-and-validity checks. Pure validation of caller-supplied input (such as a forbidden-field rejection on a caller-supplied update dictionary) may precede this governance-dependency preflight, provided that validation step itself performs no AWS call — but no hold-state read, transaction construction, or other AWS mutation may ever precede the preflight. This Invariant narrows how a shared-construction class must be built; it does not relax Invariant 30's resolution-ordering requirement for write-capable commands, and it does not permit a read-only or write-free command to resolve custody configuration it will never use.
