(2) "Indefinite retention by default" for markers was wrong — markers are now purpose-limited (§19.5.8): governance purpose ends at `sweep_status = COMPLETE`, disposal via a dedicated, deferred-duration S3 Lifecycle rule on `retention-markers/`, with `LegalHoldEvent` (unaffected, still permanent) confirmed sufficient to preserve all durable transition history independent of the marker object's own lifecycle. **Governance note (Product Strategy — required identity correction, not accepted as previously stated): `hold_id` identifies one legal-hold episode from `PLACE` through `RELEASE`, constant across that pair — it is never regenerated per transition.** The claim in the note directly above — that non-collision rested in part on `hold_id` being freshly generated per transition — is corrected: non-collision is proved by `hold_version`'s monotonicity alone (§19.5.2, revised; ADR Invariant 21, revised); `hold_id` groups a `PLACE`/`RELEASE` pair for traceability, not uniqueness. This surfaced one required, additive consequence for already-merged code: `HoldRepository`'s `LegalHoldEvent` SK (currently keyed by `hold_id` alone) must gain `hold_version` as a per-transition discriminator, or `RELEASE`'s event write would collide with its paired `PLACE`'s at the identical key (§19.5.1's "Required consequence," §19.5.2; ADR Invariant 25, new) — scoped into Legal-Hold Correction B1's "transition-safe `LegalHoldEvent` persistence" deliverable (§19.10), not implemented here. QA items 15 and 18 (§19.11) are revised to match. ## 1. Feature Overview

A1 replaces today's unconditional, indefinite retention of everything in `RawResultsBucket` (S3) and `MetadataTable` (DynamoDB) with a technically enforced custody-period disposal mechanism, a legal-hold override, and a durable disposal record — closing a confirmed conflict between already-shipped Phase 1–7 behavior and the Evidence Governance Baseline's default ("evidence shall not outlive its authorized governance purpose").

A1 is a correction to existing infrastructure and a new, cross-cutting enforcement layer — it is not owned by, and does not modify, any existing phase's business logic. It introduces one new package (`evidence_retention/`), four new DynamoDB record types, two new S3/DynamoDB infrastructure primitives (Lifecycle configuration, TTL + Streams), and one new Lambda.

## 4. Technical Scope

### Current Technical Scope

- `infra/resources/s3.yml`: add `LifecycleConfiguration` to `RawResultsBucket` — **four independent rules, one per evidence class** (`raw-results/`, `intelligence/`, `reports/`, `integrity/`), each tag-filtered `Expiration` + `NoncurrentVersionExpiration` scoped to `rcp-legal-hold=false` and its own evidence-class key prefix, each consuming its own `custom.custodyPeriodDays.<class>.${stage}` value (implemented in A1.2 — see §3, §12); add S3 Event Notification configuration for `s3:LifecycleExpiration:*` routed to EventBridge.
- `infra/resources/dynamodb.yml`: add `TimeToLiveSpecification` (attribute `ttl_disposal_at`) and `StreamSpecification` (`NEW_AND_OLD_IMAGES`) to `MetadataTable`.
- `infra/serverless.yml`: new `evidenceDisposalRecorder` Lambda function (DynamoDB Streams + EventBridge S3-notification triggers); new `custom.custodyPeriodDays` per-evidence-class, per-stage configuration block (value left unset — see Section 15).
- New package `src/release_confidence_platform/evidence_retention/`: `models.py` (Pydantic models for `LegalHold`, `LegalHoldEvent`, `DisposalRecord`), `hold_repository.py` (`HoldRepository` — DynamoDB access for `LegalHold`/`LegalHoldEvent` only, SK-guarded to `#LEGALHOLD#`; **A1.1, implemented**), `disposal_repository.py` (`DisposalRepository` — DynamoDB write for disposal records only, SK-guarded to `#DISPOSAL#`, used exclusively by the Lambda), `custody_sweep_client.py` (`CustodySweepClient` — the S3 per-version tagging sweep and the cross-phase `ttl_disposal_at` removal/restore on other phases' DynamoDB records; operation-guarded, not SK-guarded — see Section 5.2; **A1.2/A1.3 scope**), `service.py` (`RetentionService` — hold placement/release orchestration, depends on **both** `HoldRepository` and `CustodySweepClient`; **A1.2/A1.3 scope**), `identity.py` (ID generation, tag-key constants, SK-namespace constants), `commands.py` (new `rcp retention hold place|release|status` CLI group), `disposal_recorder.py` (Lambda handler logic invoked by the new Lambda, depends on `DisposalRepository` only). The `HoldRepository`/`DisposalRepository`/`CustodySweepClient` three-way split, and the mutually exclusive guards on each, are a direct fix for the write-path contradiction identified in architecture review — see Section 5.2 (amended following A1.1 QA validation to name `CustodySweepClient` explicitly; A1.1 itself implemented only `HoldRepository`/`DisposalRepository`, correctly deferring the sweep).
- Every existing phase write path that persists to `RawResultsBucket` or `MetadataTable` gains: (a) S3 object tagging (`rcp-legal-hold=false`, `rcp-evidence-class={class}`) at `PutObject` time; (b) `custody_expires_at` / `ttl_disposal_at` computation at DynamoDB item-write time. This touches every phase's write call sites but adds fields/tags only — no existing field, record shape, or write condition is altered. Confirmed by direct code inspection, the touched write paths are:
  - **Phase 1/2/3 raw execution evidence** — `packages/storage/s3_client.py` (`S3StorageClient.write_raw_results_once`, the sole `PutObject` call site for raw evidence) and `packages/storage/dynamodb_client.py` (`DynamoDBMetadataClient.put_started_once`, the sole `PutItem` call site for `RUN` records); both invoked from `apps/backend/orchestrator/service.py` (confirmed call sites at approximately lines 102, 222, 238, and 630). This is the largest and most sensitive evidence class and was the original motivation for Workstream A — see Section 11/17 for the corrected, exhaustive enumeration.
  - **Phase 4 aggregation** — `src/release_confidence_platform/aggregation/repository.py`.
  - **Phase 5 intelligence** — `src/release_confidence_platform/reliability_intelligence/repository.py`.
  - **Phase 6 reporting** — `src/release_confidence_platform/deterministic_reporting/repository.py` (DynamoDB) and `.../publisher.py` (S3).
  - **Phase 7 certification** — `src/release_confidence_platform/audit_platform_integrity/repository.py`.

### Out of Scope

- The exact custody-period duration value(s) (Product Strategy decision, tracked separately).
- Evidence profiles / minimization-at-persistence-time (Evidence Governance Baseline 2.2).
- Backup, replica, or archive storage outside `RawResultsBucket` and `MetadataTable` (none exist today).
- Legal hold *authorization* policy — who may place/release a hold, and under what business process. Only the technical override mechanism is designed here.
- Any change to any phase's business logic, scoring, aggregation, intelligence derivation, reporting, or certification behavior.

### Future Technical Considerations

- A formal Evidence Package artifact incorporating disposal metadata (Evidence Governance Baseline 2.1/2.7) — not designed here.
- A future customer authentication/authorization boundary that legal hold authorization could attach to.
- Differentiated custody periods by customer contract rather than by evidence class alone (Workstream B/C).

## 5. Architecture Overview

### 5.1 Platform Position

`evidence_retention/` is a cross-cutting layer, not a pipeline phase. It sits alongside every phase rather than after any one of them:

```
Phase 1/2 (raw evidence) ─┐
Phase 4 (aggregates)      ─┤
Phase 5 (intelligence)    ─┼──> [tag/TTL fields set at write time] ──> RawResultsBucket / MetadataTable
Phase 6 (reports)         ─┤                                              │
Phase 7 (certificates)    ─┘                                              │
                                                                            ▼
                                                          S3 Lifecycle (daily sweep) / DynamoDB TTL (~48h best-effort)
                                                                            │
                                                     ┌──────────────────────┴──────────────────────┐
                                                     ▼                                              ▼
                                        S3 Event Notification (LifecycleExpiration)     DynamoDB Streams (REMOVE, TTL principal)
                                                     │                                              │
                                                     └──────────────────> evidenceDisposalRecorder <─┘
                                                                            │
                                                                            ▼
                                                                     DisposalRecord (MetadataTable, #DISPOSAL#)

evidence_retention/service.py (RetentionService)
   ├──uses──> HoldRepository (SK-guarded to #LEGALHOLD# only)
   │             place_legal_hold / release_legal_hold  ──> LegalHold + LegalHoldEvent (MetadataTable, #LEGALHOLD#)
   └──uses──> CustodySweepClient (operation-guarded: ttl_disposal_at-only updates; tagging-only S3 calls;
                                   explicitly excluded from #LEGALHOLD#/#DISPOSAL#)
                 ├─ retags S3 object versions across all evidence-class prefixes (rcp-legal-hold tag)
                 └─ removes/restores ttl_disposal_at on other phases' DynamoDB items (RunMetadata, ReportMetadata, etc.)

evidence_retention/disposal_recorder.py ──uses──> DisposalRepository (SK-guarded to #DISPOSAL# only)
   (RetentionService has no dependency on DisposalRepository, and vice versa — see below.
    CustodySweepClient is likewise never imported by disposal_recorder.py.)
```

### 5.2 Read/Write Separation

**Amendment note (post-A1.1 implementation):** an earlier revision of this section attributed the S3 per-version re-tagging sweep and the cross-phase `ttl_disposal_at` removal/restore to `HoldRepository`, while simultaneously specifying that `HoldRepository`'s `_assert_retention_sk()` guard rejects any SK that isn't `#LEGALHOLD#`-shaped. Those two claims are mutually exclusive: the cross-phase sweep is, by construction, a write to `RunMetadata`/`AggregationJob`/`ReportMetadata`/`CertificationMetadata`/etc. SKs — none of which are `#LEGALHOLD#`-shaped — so the guard as specified would reject exactly the operation the section attributed to that class. A1.1 (data models + repository layer) correctly implemented `HoldRepository` scoped strictly to `LegalHold`/`LegalHoldEvent` CRUD, matching §7.1/§7.2 and keeping `_assert_retention_sk()` strict per ADR Non-Negotiable Invariant 6, and QA validated this as the correct call. This section is amended below to name the second, differently-scoped component (`CustodySweepClient`) that A1.2/A1.3 must introduce for the sweep operations — it was always implied by the product requirements (FR-A1-4) but was never given its own name or component boundary in the original revision, which is what produced the contradiction.

- No existing phase's repository or engine code is modified. Only write call sites gain two additional fields/tags at the point of an already-existing write; no existing conditional-write logic, sort key, or record shape changes.
- **`HoldRepository` writes only to the `#LEGALHOLD#` sort-key namespace.** Its write methods call `_assert_retention_sk()` before every `PutItem`/`UpdateItem`, which raises `AssertionError` if the target SK contains `#DISPOSAL#` (or anything other than `#LEGALHOLD#`) — mirroring `_assert_phase7_sk` in `audit_platform_integrity/repository.py:49`, which guards Phase 7's writes against straying outside `#CERTJOB#`/`#CERT#`. `HoldRepository` has no method capable of touching S3 or any other phase's DynamoDB SK. This is exactly what A1.1 implemented.
- **`CustodySweepClient` (new in this amendment — A1.2/A1.3 scope) is the second, differently-scoped access path `RetentionService` needs.** It performs: (a) the S3 per-version tagging sweep (`ListObjectVersions`/`GetObjectTagging`/`PutObjectTagging` across every S3 prefix under an audit identity, spanning all evidence classes — `raw-results/`, `intelligence/`, `reports/`, `integrity/`), and (b) the cross-phase DynamoDB query + `UpdateItem` to remove/restore the `ttl_disposal_at` attribute on *other phases'* records (`RunMetadata`, Phase 4/5 job and metadata records, `ReportMetadata`, `CertificationMetadata`, etc.). It is deliberately **not** a "repository" in the SK-guarded sense used elsewhere in this design — it legitimately must write to SKs outside any single namespace, so an SK-shape guard like `_assert_retention_sk`/`_assert_disposal_sk` would be the wrong tool and would incorrectly reject its normal operation (this is precisely the contradiction being corrected). Its safety boundary is enforced differently, by operation shape rather than SK shape: `_assert_custody_field_only_update()` inspects every DynamoDB `UpdateExpression` it is about to issue and raises `AssertionError` if the expression touches any attribute other than `ttl_disposal_at`, or if the target SK contains `#LEGALHOLD#` or `#DISPOSAL#` (those two namespaces remain exclusively `HoldRepository`'s and `DisposalRepository`'s respectively — `CustodySweepClient` must not touch them either, even though it may touch everything else). On the S3 side, the class exposes only tagging-API methods (`ListObjectVersions`, `GetObjectTagging`, `PutObjectTagging`) — it has no `put_object`/`delete_object` method at all, so it cannot write or delete evidence content by construction, not merely by IAM restriction.
- **`RetentionService` (A1.2/A1.3 scope) depends on both `HoldRepository` and `CustodySweepClient`** — two distinct dependencies, not one. `place_legal_hold()`/`release_legal_hold()` write `LegalHold`/`LegalHoldEvent` via `HoldRepository`, then invoke `CustodySweepClient` for the S3 re-tagging sweep and the cross-phase `ttl_disposal_at` removal/restore. `RetentionService` has no dependency on `DisposalRepository`.
- **`#DISPOSAL#` is written exclusively by `evidenceDisposalRecorder`**, via a separate `DisposalRepository` class that neither `RetentionService` nor `CustodySweepClient` ever imports. `DisposalRepository`'s write method calls the symmetric guard `_assert_disposal_sk()`, which raises `AssertionError` if the target SK contains `#LEGALHOLD#`. `evidenceDisposalRecorder` never deletes, updates, or reads any evidence content itself (S3 event payloads and DynamoDB stream `OLD_IMAGE` payloads carry everything needed); its only DynamoDB write is a conditional `PutItem` of a new `DisposalRecord`.
- This is now a three-component split — `HoldRepository` (SK-guarded to `#LEGALHOLD#`), `DisposalRepository` (SK-guarded to `#DISPOSAL#`), and `CustodySweepClient` (operation-guarded to `ttl_disposal_at`-only updates and tagging-only S3 calls, explicitly excluded from both guarded namespaces) — and is the code-level enforcement of Non-Negotiable Invariant 6 in the companion ADR. As with Phase 7's `_assert_phase7_sk`, every one of these guards is a programming-error guard, not an IAM-enforced boundary — DynamoDB IAM cannot condition `PutItem`/`UpdateItem` on sort-key substrings or on which attribute an `UpdateExpression` touches, only on the partition key. IAM is configured as defense-in-depth (Section 12) but the primary guarantee is structural, at the code level.

## 7. Data Models

### 7.1 `LegalHold` (current-state record)

**Purpose:** Authoritative current hold status for a given audit identity. Analogous in pattern to `ReportMetadata` (one current-state record per identity, updated in place).

**Primary Key:**
- PK: `CLIENT#{client_id}`
- SK: `AUDIT#{audit_id}#LEGALHOLD`

**Fields:**

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `PK` / `SK` | String | Yes | As above |
| `record_type` | String | Yes | `legal_hold` |
| `client_id` / `audit_id` | String | Yes | Scoping identity |
| `status` | String | Yes | `ACTIVE` \| `RELEASED` |
| `hold_id` | String | Yes | Identifies the current hold episode (prefix `hold_`); constant across that episode's `PLACE` and `RELEASE` (§19.5.2). Combined with `hold_version` (§19.1), references the specific most-recent `LegalHoldEvent`. |
| `placed_at` | String | Yes | UTC ISO-8601, first placement |
| `placed_by` | String | Yes | Opaque operator identity string (authorization policy out of scope) |
| `reason` | String | Yes | Free-text operator-supplied justification |
| `released_at` | String | No | UTC ISO-8601; present when `status = RELEASED` |
| `released_by` | String | No | Present when `status = RELEASED` |
| `hold_count` | Number | Yes | Count of place/release cycles; starts at `1` |

**Ownership:** One record per `(client_id, audit_id)`. Written on first placement via conditional put; updated on every subsequent place/release cycle.

**Lifecycle:** Created `ACTIVE` on first `place_legal_hold`. Transitions to `RELEASED` on `release_legal_hold`. May be re-placed (`RELEASED` → `ACTIVE`) any number of times; `hold_count` increments each cycle. Never deleted; never subject to `ttl_disposal_at` (a hold record is a governance artifact, not evidence).

### 7.2 `LegalHoldEvent` (immutable log)

**Purpose:** Immutable audit log of every place/release action, mirroring the platform's existing Job-log convention (`ReportJob`, `CertificationJob`, `IntelligenceJob`).

**Primary Key:**
- PK: `CLIENT#{client_id}`
- SK: `AUDIT#{audit_id}#LEGALHOLD#{hold_id}`

**Fields:** `record_type` (`legal_hold_event`), `hold_id`, `client_id`, `audit_id`, `action` (`PLACE` \| `RELEASE`), `actor`, `reason`, `timestamp`, `s3_versions_retagged_count` (Number, populated after the re-tagging sweep completes), `dynamodb_items_updated_count` (Number).

**Ownership:** Scoped to `client_id`. Written once per action via conditional put. Never mutated after write.

**Lifecycle:** Write-once, append-only. Never deleted; never subject to `ttl_disposal_at`.

### 7.3 `DisposalRecord`

**Purpose:** Durable, queryable evidence that a specific disposal action occurred — the FR-A1-5 / AC-A1-6 requirement. One record per disposed S3 object-version or DynamoDB item.

**Primary Key:**
- PK: `CLIENT#{client_id}`
- SK: `AUDIT#{audit_id}#DISPOSAL#{disposal_id}`

**Fields:**

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `PK` / `SK` | String | Yes | As above |
| `record_type` | String | Yes | `disposal_record` |
| `disposal_id` | String | Yes | Opaque ID (prefix `disp_`) |
| `client_id` / `audit_id` | String | Yes | Scoping identity, extracted from the disposed item/object key |
| `evidence_class` | String | Yes | `raw_evidence` \| `aggregate_metadata` \| `intelligence` \| `report` \| `certificate` \| `metadata_generic` |
| `disposal_mechanism` | String | Yes | `S3_LIFECYCLE_EXPIRATION` \| `S3_LIFECYCLE_NONCURRENT_VERSION_EXPIRATION` \| `DYNAMODB_TTL` |
| `disposed_identity_ref` | String | Yes | S3 key (+ version id, if noncurrent) or DynamoDB `PK#SK` of the disposed item |
| `source_created_at` | String | No | Original record/object creation timestamp, when available from the event payload (`OLD_IMAGE` for DynamoDB) |
| `custody_period_days_applied` | Number | No | The custody-period value in effect at disposal, when derivable from the event payload |
| `disposed_at` | String | Yes | UTC ISO-8601; AWS's own best-available deletion timestamp (from the stream/event record) |
| `recorded_at` | String | Yes | UTC ISO-8601; when `evidenceDisposalRecorder` wrote this record (always ≥ `disposed_at`, may lag by the eventual-consistency window) |

**Ownership:** Scoped to `client_id`/`audit_id`, derived from the disposed item's own identity fields. Written once via conditional put **exclusively by `DisposalRepository`, used only by `evidenceDisposalRecorder`** — no other code path in this design (including `RetentionService`/`HoldRepository`) has a method capable of constructing this write; see Section 5.2 for the enforcing SK-write guard. Never mutated after write. **Never carries a `ttl_disposal_at` attribute** — see Non-Negotiable Invariant 1 in the companion ADR.

**Lifecycle:** Write-once, append-only, permanent (or subject to a separate, independently governed compliance-record retention policy — not the evidence custody-period mechanism this ADR defines; explicitly out of scope for A1).

### 7.4 Modified Fields on Existing Records (No Schema-Breaking Change)

Every existing DynamoDB record type that persists to `MetadataTable` (`RunMetadata`, `AggregationJob`/`AggregateSetCompletion`/aggregate records, `IntelligenceJob`/`IntelligenceMetadata`, `ReportJob`/`ReportMetadata`, `CertificationJob`/`CertificationMetadata`, and any others) gains two **additive, optional** fields:

| Field | Type | Description |
| --- | --- | --- |
| `custody_expires_at` | Number (epoch seconds) | `created_at + custody_period_seconds` for the record's evidence class; computed once at write time, never mutated by hold state changes |
| `ttl_disposal_at` | Number (epoch seconds) | The DynamoDB TTL attribute. Equal to `custody_expires_at` under normal conditions; `REMOVE`d while a legal hold is active; restored to `MAX(custody_expires_at, now)` on release |

This is additive-only per `docs/architecture/naming_and_schema_versioning.md`'s existing versioning discipline — no existing field is renamed, removed, or reinterpreted, and no existing `report_version`/`aggregation_version`/`intelligence_version`/`cert_version` schema boundary is crossed. No new record version is required for this change.

## 8. API Contracts

A1 introduces CLI commands only (no HTTP API exists in this platform). Each is documented using the platform's CLI-as-API convention (parser + dispatch, following `audit_platform_integrity/commands.py`).

### Command: `rcp retention hold place`

**Purpose:** Place a legal hold on an audit identity, exempting its evidence from automatic disposal.

**Authentication / Authorization:** Operator CLI access only (same trust boundary as all existing `rcp` commands). Legal hold *authorization policy* (who may invoke this) is explicitly out of scope for A1 per the Product Spec; this command performs no additional authorization check beyond existing CLI access.

**Request Parameters:** `--client-id` (required), `--audit-id` (required), `--stage` (required, `dev`\|`staging`\|`prod`), `--reason` (required, free text), `--actor` (required, opaque operator identity string).

**Request Body:** N/A (CLI arguments only).

**Response Body:** JSON/human summary: `hold_id`, `status=ACTIVE`, `placed_at`, `s3_versions_retagged_count`, `dynamodb_items_updated_count`.

**Success Status Codes:** Exit code `0`.

**Error Status Codes:** `INVALID_IDENTIFIER` (client_id/audit_id fail `validate_identifier`), `HOLD_ALREADY_ACTIVE` (idempotent no-op with a warning, not a hard failure — re-placing an active hold is safe), `STORAGE_ERROR` (DynamoDB/S3 infrastructure failure during the re-tagging sweep — see Reliability).

**Validation Rules:** `client_id`/`audit_id` validated via the existing `validate_identifier` utility. `reason` must be non-empty.

**Side Effects:** Via `HoldRepository` — writes `LegalHoldEvent` (immutable) + upserts `LegalHold` (current-state) to `ACTIVE`. Via `CustodySweepClient` — re-tags every extant S3 object version under the audit identity's key prefixes (`raw-results/`, `intelligence/`, `reports/`, `integrity/`, each scoped by `{client_id}/{audit_id}/`) to `rcp-legal-hold=true`; `UpdateItem REMOVE ttl_disposal_at` (via `_assert_custody_field_only_update()`) on every other-phase DynamoDB item under `PK=CLIENT#{client_id}`, `SK begins_with AUDIT#{audit_id}`.

**Idempotency / Duplicate Handling:** Re-invoking `place` while already `ACTIVE` is a safe no-op that re-runs the re-tagging sweep (self-healing if a prior sweep was interrupted) and writes a new `LegalHoldEvent`, incrementing `hold_count`.

### Command: `rcp retention hold release`

**Purpose:** Release an active legal hold, resuming custody-period enforcement for the audit identity's evidence.

**Authentication / Authorization:** Same as `place`.

**Request Parameters:** `--client-id`, `--audit-id`, `--stage`, `--actor` (all required).

**Response Body:** `hold_id`, `status=RELEASED`, `released_at`, counts as above.

**Success Status Codes:** Exit code `0`.

**Error Status Codes:** `INVALID_IDENTIFIER`, `HOLD_NOT_ACTIVE` (no active hold exists — hard failure, since releasing a non-existent hold is an operator error worth surfacing, not silently ignored), `STORAGE_ERROR`.

**Validation Rules:** As above.

**Side Effects:** Via `HoldRepository` — writes `LegalHoldEvent` + updates `LegalHold` to `RELEASED`. Via `CustodySweepClient` — re-tags S3 object versions back to `rcp-legal-hold=false`; restores `ttl_disposal_at = MAX(custody_expires_at, now)` on every matching other-phase DynamoDB item.

**Idempotency / Duplicate Handling:** Re-invoking `release` when already `RELEASED` returns `HOLD_NOT_ACTIVE` — not silently accepted, since a second release attempt likely indicates operator confusion about current state and `hold status` is available to check first.

### Command: `rcp retention hold status`

**Purpose:** Read-only lookup of current hold state for an audit identity.

**Authentication / Authorization:** Same as `place`/`release`; read-only, no write side effects.

**Request Parameters:** `--client-id`, `--audit-id`, `--stage` (all required).

**Response Body:** `status`, `hold_id`, `placed_at`, `released_at` (if applicable), `hold_count`.

**Success Status Codes:** Exit code `0` (including the "no hold ever placed" case, returned as `status=NEVER_HELD`, not an error).

**Error Status Codes:** `INVALID_IDENTIFIER`, `STORAGE_ERROR`.

**Side Effects:** None (read-only).

**Idempotency:** N/A — pure read.

## 10. Backend Logic

### 10.1 Responsibilities

- Ensure every write to `RawResultsBucket`/`MetadataTable`, regardless of originating phase, carries the fields/tags the disposal mechanism depends on (`rcp-legal-hold`, `rcp-evidence-class`, `custody_expires_at`, `ttl_disposal_at`).
- Orchestrate legal hold placement/release as a bulk, potentially long-running operation across both storage systems, with idempotent, resumable semantics.
- React to AWS-native disposal events (never poll or assume synchronous deletion) and produce exactly one `DisposalRecord` per disposed item/version.

### 10.2 Validation Flow

- CLI-boundary validation (`validate_identifier` on `client_id`/`audit_id`) before any `RetentionService` call, consistent with every existing CLI command in this platform (`audit_platform_integrity/commands.py`, `deterministic_reporting/report_retrieve_commands.py`).
- `evidenceDisposalRecorder` validates event provenance before writing a `DisposalRecord`: for DynamoDB Streams, only `REMOVE` events with `userIdentity.principalId == "dynamodb.amazonaws.com"` are processed (application-initiated deletes, if any exist in the future, are explicitly excluded from this path); for S3, only `s3:LifecycleExpiration:*` event names are processed.

### 10.3 Business Rules

- A `DisposalRecord` is never itself subject to `ttl_disposal_at`.
- `custody_expires_at` is set once at write time and never recomputed by hold state changes; only `ttl_disposal_at` is mutated by hold placement/release.
- S3 legal-hold tagging must cover every extant object version, not only the current version, because S3 object tags are per-version.
- Legal hold release restores `ttl_disposal_at` clamped to `MAX(custody_expires_at, now)`, never silently skipping already-elapsed custody.

### 10.4 Persistence Flow

**Sequence — evidence write path (any phase), custody fields added:**

```
Phase N repository.write_X(...)
  │
  ├─ compute custody_expires_at = created_at_epoch + custody_period_seconds[evidence_class]
  ├─ set ttl_disposal_at = custody_expires_at
  ├─ PutItem(..., custody_expires_at=..., ttl_disposal_at=...)     [DynamoDB records]
  └─ PutObject(..., Tagging="rcp-legal-hold=false&rcp-evidence-class={class}")  [S3 objects]
```

**Sequence — legal hold placement:**

```
rcp retention hold place --client-id C --audit-id A --reason "..." --actor "..."
  │
  ├─ validate_identifier(client_id, audit_id)
  ├─ RetentionService.place_legal_hold(...)   # uses HoldRepository + CustodySweepClient — no dependency on DisposalRepository
  │    ├─ HoldRepository.write_hold_event(...)   [_assert_retention_sk(sk) before write] → LegalHoldEvent (PLACE)
  │    ├─ HoldRepository.upsert_hold(...)        [_assert_retention_sk(sk) before write] → LegalHold (status=ACTIVE)
  │    ├─ CustodySweepClient.remove_ttl_disposal_at(client_id=C, audit_id=A)
  │    │    ├─ Query MetadataTable: PK=CLIENT#C, SK begins_with AUDIT#A   (other phases' SKs — RunMetadata, ReportMetadata, etc.)
  │    │    └─ for each item with ttl_disposal_at present:
  │    │         └─ _assert_custody_field_only_update(sk, expr)  →  UpdateItem REMOVE ttl_disposal_at
  │    └─ CustodySweepClient.retag_s3_versions(client_id=C, audit_id=A, legal_hold=True)
  │         └─ for each S3 prefix in {raw-results, intelligence, reports, integrity}/C/A/:
  │              └─ ListObjectVersions → for each version: PutObjectTagging(rcp-legal-hold=true)
  └─ return summary (counts)
```

**Sequence — disposal recording (TTL path):**

```
DynamoDB TTL sweep deletes item (async, best-effort, ~within 48h of ttl_disposal_at)
  │
  ▼
DynamoDB Streams REMOVE event (userIdentity.principalId = dynamodb.amazonaws.com)
  │
  ▼
evidenceDisposalRecorder Lambda
  ├─ filter: is TTL-driven REMOVE? (else discard)
  ├─ extract client_id/audit_id/evidence_class/created_at from OLD_IMAGE
  ├─ generate disposal_id
  └─ DisposalRepository.put_disposal_record(...)
       ├─ _assert_disposal_sk(sk)   # raises if sk does not target #DISPOSAL# or targets #LEGALHOLD#
       └─ PutItem DisposalRecord (conditional; disposal_mechanism=DYNAMODB_TTL)

  # on failure after exhausting MaximumRetryAttempts: event routes to evidenceDisposalRecorderDLQ
  # (DestinationConfig.OnFailure) → evidenceDisposalRecorderDLQAlarm fires on nonzero queue depth
```

**Sequence — disposal recording (S3 Lifecycle path):**

```
S3 Lifecycle daily sweep expires/deletes object (current or noncurrent version)
  │
  ▼
S3 Event Notification (s3:LifecycleExpiration:Delete / :DeleteMarkerCreated) → EventBridge
  │
  ▼
evidenceDisposalRecorder Lambda
  ├─ extract client_id/audit_id/evidence_class from S3 key path segments
  ├─ generate disposal_id
  └─ DisposalRepository.put_disposal_record(...)
       ├─ _assert_disposal_sk(sk)
       └─ PutItem DisposalRecord (conditional; disposal_mechanism=S3_LIFECYCLE_EXPIRATION | ..._NONCURRENT_VERSION_EXPIRATION)

  # on failure: EventBridge target DeadLetterConfig routes to evidenceDisposalRecorderDLQ
```

### 10.5 Error Handling

- Partial failure during a legal hold sweep (e.g., S3 re-tagging fails partway through a large object set) does not roll back already-completed steps; `place`/`release` are designed to be safely re-invoked (idempotent) to resume/complete the sweep. `LegalHoldEvent` records the counts actually achieved, not just attempted, so partial completion is observable.
- `evidenceDisposalRecorder` failures (e.g., a malformed event payload) are logged via structured logging (per `docs/architecture/structured_logging.md`) and do not block the Lambda's event source mapping from processing subsequent events; a conditional put (`attribute_not_exists`) on `DisposalRecord` guards against duplicate records if an event is redelivered (at-least-once delivery is standard for both DynamoDB Streams and EventBridge).

## 12. Security

- **No new external attack surface.** All new CLI commands are operator-only, at the same trust boundary as every existing `rcp` command. No customer-facing or network-exposed interface is introduced.
- **Correction (architecture + security review):** the four bullets below describe a *logical* least-privilege scope for each component's DynamoDB/S3 actions — the minimal action set each component's own code path actually exercises. They previously read as if this scope were IAM-enforced. It is not, and the codebase's actual IAM architecture makes that gap concrete rather than theoretical: `infra/serverless.yml` defines IAM almost entirely under one shared `provider.iam.role.statements` block; only two existing functions (`auditFinalization`, `auditAggregation`) have dedicated per-function roles (`Fn::GetAtt` to `AuditFinalizationLambdaRole`/`AuditAggregationLambdaRole`, defined in `infra/resources/phase4-aggregation-iam.yml` — genuine per-function-role precedent exists in this codebase, it is simply not used by every function). `coreEngineOrchestrator` and `scheduledExecution` — the two functions where §19's corrected RunMetadata and raw-evidence write paths actually run — have no dedicated role and fall back to the shared one. Under today's architecture, adding `dynamodb:TransactWriteItems` (§19.4/§19.8) the natural, minimal-diff way means adding it to that shared role, granting it to every function using that role, not only the RunMetadata write path. `HoldRepository`/`CustodySweepClient` are not Lambda-resident at all in this design — they run wherever `RetentionService`/the `rcp retention` CLI commands run, under whatever AWS credentials that operator session holds, which `provider.iam.role.statements` does not govern at all. The bullets below are retained as a statement of *intended minimal scope per component*, useful for a future per-function-role subphase (a real option, given the existing `auditFinalization`/`auditAggregation` precedent, but not adopted as part of this amendment — see §19.10 for where such a subphase would fit if authorized) — they are not a claim that AWS IAM currently, or will by default, enforce this separation.
- **IAM scope for the new Lambda (logical, not currently IAM-enforced unless a dedicated role is added — see correction above):** `evidenceDisposalRecorder` needs only `dynamodb:GetRecords`/`GetShardIterator`/`DescribeStream`/`ListStreams` on `MetadataTable`'s stream ARN, `dynamodb:PutItem` scoped to `MetadataTable` (for `DisposalRecord` writes only), `sqs:SendMessage` scoped to `evidenceDisposalRecorderDLQ`, and no S3 permissions. As a genuinely new, dedicated Lambda (unlike `HoldRepository`/`CustodySweepClient` below), this is the strongest candidate in this design for a dedicated per-function role following the `auditFinalization`/`auditAggregation` precedent — if added to the shared role instead, it inherits every other action already granted there (including, once §19's corrections land, `dynamodb:TransactWriteItems`), not only the actions it needs.
- **`#DISPOSAL#`/`#LEGALHOLD#` write-exclusivity — code-level guard, not an IAM boundary (this was already stated accurately and is unaffected by the correction above; restated for contrast).** IAM's `dynamodb:PutItem`/`UpdateItem` grants are scoped to the table as a whole; DynamoDB IAM fine-grained access control conditions on the partition key (`dynamodb:LeadingKeys`) but cannot restrict a call to items whose sort key contains a given substring, and cannot restrict an `UpdateItem` call to touching only one named attribute. The actual write-exclusivity guarantees — that only `evidenceDisposalRecorder` (via `DisposalRepository`) writes `#DISPOSAL#` items, only `RetentionService` (via `HoldRepository`) writes `#LEGALHOLD#` items, and `CustodySweepClient` may touch neither namespace while touching everything else only via `ttl_disposal_at`-only updates — are therefore enforced at the code level by `_assert_retention_sk()`, `_assert_disposal_sk()`, and `_assert_custody_field_only_update()` respectively (Section 5.2/6), mirroring `_assert_phase7_sk` in `audit_platform_integrity/repository.py:49`. This is the same honesty standard the correction above now applies consistently to every IAM-adjacent claim in this section, not only this one.
- **Logical scope for `HoldRepository` (not a Lambda execution role — see correction above):** its code exercises only `dynamodb:GetItem`/`PutItem`/`UpdateItem` scoped to `MetadataTable`, used only for `LegalHold`/`LegalHoldEvent` items, and no S3 action at all. Whatever AWS credentials actually invoke it (an operator's CLI session today; a future dedicated `RetentionService` execution context if one is ever built) are not scoped to only these actions by anything this design specifies.
- **Logical scope for `CustodySweepClient` (not a Lambda execution role — see correction above):** its code exercises only `dynamodb:Query`/`UpdateItem` on `MetadataTable` and `s3:ListBucketVersions`/`s3:GetObjectTagging`/`s3:PutObjectTagging` scoped to `RawResultsBucket` — never `s3:DeleteObject`/`s3:PutObject` or `dynamodb:PutItem`/`DeleteItem`, enforced by the class's own method allowlist (§5.2), not by IAM. Same caveat as `HoldRepository` above: the invoking credentials are not scoped to only this action set by anything in this design.
- **No sensitive data introduced.** `DisposalRecord`/`LegalHold`/`LegalHoldEvent` fields are identifiers, timestamps, and free-text operator justification — no raw request/response bodies, headers, tokens, or PII, consistent with `phase_6_report_schema.md` §8.3's sensitive-data exclusion pattern, which this design follows by extension.
- **Sanitization boundary compliance (`adr_sanitization_boundary.md`).** `client_id`, `audit_id`, and all fields used to construct `PK`/`SK` or S3 key paths in `LegalHold`, `LegalHoldEvent`, and `DisposalRecord` are canonical identifier fields. Per that ADR, `sanitize()` must never be applied to these fields before persistence — the same incident class (UUID-substring false-positive PII redaction corrupting a persisted key) that ADR documents for Phase 3/4 applies identically here if `evidence_retention/hold_repository.py` or `evidence_retention/disposal_repository.py` were to call `sanitize()` on an item dict before `PutItem`. Both repository classes must follow the same convention already established in `audit_platform_integrity/repository.py` and `deterministic_reporting/repository.py`: `sanitize()` is reserved for structured log output and human-readable CLI rendering only, never for persistence-bound dicts.
- **Misuse risk — hold sweep as a resource-exhaustion vector.** A hold placed on an audit with an extremely large evidence footprint triggers a potentially large number of `PutObjectTagging`/`UpdateItem` calls. This is bounded by the same operator-only trust boundary as all other CLI commands; no additional rate limiting is designed here, but Reliability (Section 13) flags the operational latency characteristic this creates.

## 13. Reliability

- **DynamoDB TTL deletion is best-effort, typically within 48 hours of `ttl_disposal_at`, not synchronous.** `DisposalRecord.recorded_at` will lag `DisposalRecord.disposed_at` (and both may lag the true deletion instant) by this window. Any consumer of `DisposalRecord` data must treat timestamps as approximate.
- **S3 Lifecycle evaluates once per day**, not continuously. An object crossing its expiration threshold may wait up to ~24 hours before the next lifecycle evaluation cycle picks it up.
- **Legal hold placement/release on large evidence sets is not instantaneous.** The S3 re-tagging sweep is O(number of object versions under the audit identity); very large audits may take non-trivial wall-clock time. The `LegalHold`/`LegalHoldEvent` write (the authoritative "hold is active" signal) completes immediately and atomically — the sweep is best-effort follow-up work that `place`/`release` can be safely re-invoked to complete if interrupted.
- **At-least-once event delivery.** Both DynamoDB Streams and EventBridge deliver at-least-once; `evidenceDisposalRecorder` uses a conditional put (`attribute_not_exists(PK) AND attribute_not_exists(SK)`) on `DisposalRecord`, matching the existing `_put_once` pattern in `audit_platform_integrity/repository.py`, to make redelivery idempotent.
- **Failure isolation.** A failure in `evidenceDisposalRecorder` never blocks or delays the underlying disposal (TTL/Lifecycle deletion already happened by the time the event fires) — only the disposal *record* is at risk of delay/retry, never the disposal *action* itself. This bounds the blast radius of any bug in the recorder to observability, not to evidence-retention correctness.
- **Dead-letter queue and failure destination on both event sources (Finding 4 fix).** Neither event source mapping relies on default retry-then-drop behavior:
  - The DynamoDB Streams event source mapping sets a bounded `MaximumRetryAttempts`, `BisectBatchOnFunctionError: true` (so one malformed record cannot block or silently discard the rest of a batch), and `DestinationConfig.OnFailure` pointing at `evidenceDisposalRecorderDLQ` (SQS). A batch that exhausts its retry budget lands on the DLQ instead of being silently dropped.
  - The EventBridge rule delivering S3 `LifecycleExpiration` notifications configures a `DeadLetterConfig` on its Lambda target, pointing at the same `evidenceDisposalRecorderDLQ`.
  - `evidenceDisposalRecorderDLQAlarm` (CloudWatch) alarms on `ApproximateNumberOfMessagesVisible > 0` for the DLQ, so a dropped disposal-recording attempt is an alerted, operator-visible condition — closing the gap where FR-A1-5's durable-record guarantee could otherwise silently fail for a specific item while structured logs alone go unreviewed.
  - The DLQ itself is not further processed by an automated redrive in this design (out of scope for A1); an operator inspects and manually redrives or investigates DLQ contents. This is noted as a manual-intervention step, not a fully automated recovery path.
- **Monitoring:** structured log events (per `docs/architecture/structured_logging.md`) for every `evidenceDisposalRecorder` invocation, every `RetentionService.place_legal_hold`/`release_legal_hold` call, and every write failure, consistent with the platform's existing structured-logging convention.

## 15. Assumptions

**Assumption requiring confirmation (backlog handling — AC-A1-8, Open Question #2):** This design recommends the enforcement mechanism apply **prospectively at minimum**, with pre-existing (pre-Workstream-A) evidence brought under enforcement via a **separate, explicit, one-time backfill migration** (a new `rcp retention backfill-custody --stage <stage>` operator-invoked command, not an automatic on-deploy action), rather than either (a) silently grandfathering the backlog indefinitely, or (b) retroactively applying the full custody period clocked from each record's *original* `created_at` (rejected — see companion ADR Alternative 5, since this could trigger a mass simultaneous disposal event the moment the mechanism activates). The recommended backfill approach clocks the backlog's custody period from **backfill-execution time**, not original creation time, so existing evidence gets the full custody-period duration from the point enforcement actually begins, giving operators a predictable, bounded window rather than an immediate mass-deletion event. **This is a recommendation only. Per the Product Spec's own Section 12 assumption, backlog handling is a distinct migration decision requiring confirmation from Architect / Product Strategy before implementation proceeds.**

## 16. Risks / Open Questions

- **Risk:** Cross-cutting change touching every phase's write path is the largest-blast-radius part of A1. Even though each change is additive (new optional fields/tags, no existing behavior altered), the sheer number of touched call sites raises regression risk. Mitigation: implementation should be sequenced phase-by-phase with the existing regression suite re-run after each phase's write-path change, not as one large cross-cutting commit.
- **Risk:** S3 per-version tagging at legal-hold time (`CustodySweepClient`) is not atomic across all versions of all objects under an audit identity; a hold could theoretically be "active" (per the `LegalHold` record, written by `HoldRepository`) while the S3 re-tagging sweep is still in progress, leaving a narrow window where an already-elapsed-custody object version has not yet been re-tagged and could be swept by the next daily Lifecycle evaluation before re-tagging completes. Given S3 Lifecycle only evaluates once per day, and the re-tagging sweep is expected to complete in well under 24 hours for realistic evidence volumes, this window is small but not zero; it should be explicitly covered in QA/Test Strategy for A1.
- **Risk (symmetric to the above, DynamoDB side):** the same class of race exists on the DynamoDB leg of hold placement. `LegalHold.status` is written `ACTIVE` atomically and immediately by `HoldRepository`, but `CustodySweepClient`'s subsequent `Query` (`PK=CLIENT#{client_id}`, `SK begins_with AUDIT#{audit_id}`) + per-item `UpdateItem REMOVE ttl_disposal_at` loop is not atomic across the full item set. An item whose `ttl_disposal_at` has already elapsed, and which DynamoDB's background TTL sweep reaches before this loop reaches that same item, could still be deleted despite the hold being logically "active" at the `LegalHold`-record level. Given DynamoDB TTL deletion is itself best-effort within ~48 hours (not instantaneous), and the removal loop is expected to complete in well under that window for realistic item counts, this window is small but not zero — documented here symmetrically with the S3-side race rather than omitted, and should be covered by the same QA/Test Strategy item as the S3 case.
- **Open dependency:** the exact custody-period value(s) (tracked separately, out of scope here).
- **Open dependency:** legal hold authorization policy (Workstream B/C).
- **Open question:** whether `DisposalRecord` retention itself should be time-bounded by an independent, longer-lived compliance-record retention policy, or retained permanently. Not resolved by this design; flagged for Product Strategy alongside the custody-period decision. **Related, not resolved by implication:** canary markers (a different governance-metadata artifact) were subsequently found to require purpose-limited, not indefinite, retention (§19.5.8) — an architecturally similar question, resolved for markers specifically because Product Strategy's correction was scoped to them. This does not extend to `DisposalRecord`; that question remains open here, on its own, exactly as stated above.
- **Resolved (this amendment):** the §5.2/§6 internal contradiction QA surfaced during A1.1 validation — `HoldRepository` described as performing S3 tagging and cross-phase DynamoDB updates while simultaneously being SK-guarded to reject exactly those writes. Closed by introducing `CustodySweepClient` as the named, differently-scoped component for those two operations (see Section 5.2/6/11/12). No ADR change was required — the ADR's Non-Negotiable Invariant 6 is what the strict `_assert_retention_sk()` guard was correctly upholding; only the TD's component boundaries needed naming.

## 18. Governed-Record Boundary and Write-Path Governance (Amendment — A1.3 Execution Authorization Withheld Pending This Section)

**Status of this amendment:** Product Strategy withheld A1.3 execution authorization after an independent, ground-truth investigation of the actual repository found §11's write-path table — which called itself "confirmed, exhaustive" — materially incomplete (7 rows / 2 fully-specified methods versus 32 actual write call sites). §11 above has been replaced with the corrected inventory. This section is the governed revision Product Strategy required before A1.3 can be re-proposed: it defines which of the 32 call sites are actually in scope for custody-field treatment, resolves three concrete correctness gaps the fuller inventory exposed (regeneration semantics, an unconstrained update method, a dual-tree write path), and revises the implementation estimate accordingly. This is architecture work, not implementation — no code, infrastructure, or already-merged A1.1/A1.2 file is touched by this amendment.

### 18.1 Governed-Record Boundary — Six Categories

**Terminology boundary:** `evidence_class` (the bounded `EVIDENCE_CLASSES` set in `evidence_retention/constants.py` — `raw_evidence`, `aggregate_metadata`, `intelligence`, `report`, `certificate`, `metadata_generic`) is the operational evidence/retention classification used by this custody design for governed-record identification, retention-policy enforcement, legal-hold/disposal processing, and Evidence Manifest construction. It must not be represented as, or treated as a substitute for, the broader Evidence Governance Baseline's Evidence Taxonomy (Initiative 2.4) unless and until an authoritative mapping between the two is explicitly established — that mapping is out of scope for Workstream A and has not been attempted here. Every DynamoDB record and S3 object classified into Category 1 or Category 2 below must persist this attribute explicitly, at write time — it must not depend on key-shape inference, repository-internal knowledge, a parent-record lookup, or reconstruction by a downstream consumer.

The Product Spec's original scope language ("all objects in `RawResultsBucket` and all records in `MetadataTable`, regardless of which phase wrote them") reads, taken literally, as if every DynamoDB record sharing an audit partition should receive `custody_expires_at`/`ttl_disposal_at`. §11's fuller inventory makes clear this cannot be the intended meaning: it would mean disposing of `AuditMetadata` — the canonical record that anchors an audit's existence and that every other record's SK partially depends on for interpretation — on the same clock as a single `RunMetadata` record, or disposing `ScheduleOccurrenceClaim` (a pure duplicate-delivery guard with no evidentiary content) on an "evidence" clock it was never designed to have. This is the ambiguity Product Strategy flagged. It is resolved here by classifying every record/object type found in §11 into exactly one of six categories:

**Category 1 — Governed evidence.** The four S3 evidence-class prefixes' raw content (`raw-results/`, `intelligence/`, `reports/`, `integrity/` — items 3, 16, 21, 27) plus the DynamoDB records that ARE the evidentiary payload itself, not a pointer to it: the five record kinds inside `put_records_once` (item 8 — lineage manifests, audit/endpoint/failure-classification aggregates, aggregate-set-completion marker; `4 + 3N` items total per transaction, §19.16) and `LineageManifestPage` (item 10). These are write-once, never updated after creation, and their content is the thing an audit reviewer or compliance reviewer would actually need to inspect. **Receives:** `custody_expires_at`, `ttl_disposal_at` (DynamoDB rows) or `rcp-legal-hold`/`rcp-evidence-class` tags + S3 Lifecycle rule coverage (S3 objects), `evidence_class = aggregate_metadata` for the Phase 4 DynamoDB rows, matching the already-built `EVIDENCE_CLASSES` bounded set in `evidence_retention/constants.py`.

**Category 2 — Evidence-derived artifact.** DynamoDB "pointer/summary" records whose entire content exists to reference and summarize one specific Category-1 S3 artifact, and nothing else: `RunMetadata` (items 1–2, points at the raw result envelope), `IntelligenceMetadata` (item 13–15, points at the intelligence artifact), `ReportMetadata` (item 19–20, points at the report artifact), `CertificationMetadata` (item 26, points at the certificate artifact). **Receives:** `custody_expires_at`/`ttl_disposal_at`. **Clarified per Product Strategy observation (post-§18 approval):** each Category 2 record computes `custody_expires_at` **independently, at its own write time**, from `custody_period_days.<evidence_class>.${stage}` — the same governing custody-period policy that governs the Category 1 artifact it points to — rather than reading, copying, or otherwise inheriting the sibling S3 artifact's already-computed value. This preserves deterministic behavior: each write derives its custody fields solely from its own timestamp and the shared, externally-supplied policy, with no dependency on write ordering or on a cross-write read of the other record. In ordinary operation the two independently-computed values will be effectively identical (both writes happen within the same generation event, against the same `evidence_class`), but the DynamoDB record's value is never sourced *from* the S3 object — the two are computed in parallel from the same policy, not chained. §18.4 specifies exactly how this applies on regeneration, since that is where the correctness gap this workstream exists to close actually lives.

**`evidence_class` must be persisted explicitly on every Category 2 record, at write time, as a plain DynamoDB attribute — not left implicit or reconstructible only via key-shape/repository knowledge (see the Terminology Boundary note above §18.1).** Per this section's own "matches the pointed-to artifact's class" rule, applied explicitly rather than left generic:

| Category 2 record | Points to | `evidence_class` value |
| --- | --- | --- |
| `RunMetadata` (items 1–2) | Raw result envelope (`raw-results/`) | `raw_evidence` |
| `IntelligenceMetadata` (items 13–15) | Intelligence artifact (`intelligence/`) | `intelligence` |
| `ReportMetadata` (items 19–20) | Report artifact (`reports/`) | `report` |
| `CertificationMetadata` (item 26) | Certificate artifact (`integrity/`) | `certificate` |

Each value is a member of the already-built, bounded `EVIDENCE_CLASSES` set in `evidence_retention/constants.py`, and matches exactly the `rcp-evidence-class` S3 tag value already hardcoded on the corresponding Category 1 artifact's write path (e.g., `RunMetadata`'s `raw_evidence` matches `write_raw_results_once`'s already-implemented `EVIDENCE_CLASS_TAG_KEY: "raw_evidence"` tag) — the two are computed independently (per the independent-computation rule above) but must always agree in value, since both derive from the same fixed, per-write-path evidence-class constant, not from each other.

**Known gap in already-merged A1.3b (disclosed, not resolved by this amendment):** `RunMetadata`'s CREATE path (`packages/storage/dynamodb_client.py::_run_metadata_custody_fields`) persists `custody_expires_at`/`ttl_disposal_at` but does not persist `evidence_class`. This is out of compliance with this section's requirement as now made explicit. Correction is tracked as a separate, narrowly-scoped subphase (A1.3b.1) — this Technical Design is not being retroactively weakened to match the incomplete implementation.

**Category 3 — Operational coordination metadata.** Job-log / pipeline-state / idempotency records whose purpose is entirely operational and whose content has no standalone evidentiary value once their pipeline stage completes: `AggregationJob`/`AggregationJobIntent` (items 4h–4i, 6–7), `IntelligenceJob` (11–12), `ReportJob` (17–18), `CertificationJob` (22–25), `ScheduleOccurrenceClaim` (4j–4k). **Receives:** nothing from this mechanism — no `custody_expires_at`, no `ttl_disposal_at`, no `rcp-legal-hold`, no `rcp-evidence-class`. This is a governed exclusion, not an oversight (§18.3).

**Category 4 — Governance metadata.** Records about the retention/disclosure governance mechanism itself: `LegalHold`, `LegalHoldEvent`, `DisposalRecord` (items 28–30), and any future A2 disclosure-governance records. **Receives:** nothing from this mechanism, permanently and structurally, per ADR Non-Negotiable Invariant 1 and the SK/operation guards already built in A1.1/A1.2 (§18.3).

**Category 5 — Configuration/input artifact.** `configs/*` S3 objects (item 5 — `client_config.json`, `audit_config.json`, `endpoints.json`). **Receives:** nothing from A1.3 — see §18.6 for why this must not be silently folded into scope.

**Category 6 — Explicitly excluded / separately governed.** `AuditMetadata` (items 4a–4g) and `AuditExecutionIdentity` (item 9) — the canonical audit anchor and the durable execution-identity record. Both are structurally load-bearing for every other record's referential integrity (every Category 1/2 record's SK embeds `audit_id` and/or `audit_execution_id`), and disposing either while descendant evidence survives would orphan that evidence's context. **Receives:** nothing from A1.3. Whether either should ever be disposed — and if so, under what cascading rule (e.g., "only after all descendant Category 1/2 records under this audit identity have themselves already been disposed") — is a distinct, higher-stakes decision than ordinary evidence custody and is **not decided here**.

**Assumption requiring confirmation:** Category 6's exclusion is this document's recommendation, not a settled Product Strategy decision. `AuditMetadata`/`AuditExecutionIdentity` could plausibly be argued into Category 3 (purely operational, same treatment, same non-disposal) instead of a standalone category — the practical outcome (no A1.3 custody fields) is identical either way, so this ambiguity does not block A1.3, but the *future* question of whether these records should ever be disposed under a cascading rule is explicitly unresolved and requires Product Strategy confirmation before any later workstream attempts it.

### 18.2 Why This Classification, Not a Simpler One

An earlier framing (Product Strategy's own phrasing of the ambiguity) posed the question as binary — "does X count as evidence, or is it operational?" A binary split does not survive contact with the inventory: `RunMetadata`/`IntelligenceMetadata`/`ReportMetadata`/`CertificationMetadata` are neither pure evidence (they contain no raw content) nor pure operational metadata (their entire existence is to summarize evidence for retrieval, and their custody genuinely should track the evidence they summarize) — they need their own category (2), distinct from both the raw content (1) and the job logs that produced them (3). Collapsing Category 2 into Category 1 would mean computing `custody_expires_at` independently at each of the four record types' own write time, which is exactly the design the fuller inventory shows is unsafe on regeneration (§18.4) — the pointer and the artifact it points to would drift out of lockstep. Collapsing Category 2 into Category 3 would mean these four record types never get disposed at all, silently reintroducing indefinite retention for `RunMetadata`/`IntelligenceMetadata`/`ReportMetadata`/`CertificationMetadata` — the exact defect Workstream A exists to close, and one that would be easy to miss precisely because it would look like "conservative, minimal scope" rather than a gap.

### 18.3 Structural Exclusion — Enforceable in Code, Not Convention

Category 4 (`LegalHold`/`LegalHoldEvent`/`DisposalRecord`) is **already** structurally excluded, confirmed by direct re-read during this amendment: `DisposalRepository.put_disposal_record`'s method signature has no `ttl_disposal_at` parameter at all — the exclusion is enforced by the method not accepting the field, not merely by a docstring. `HoldRepository`'s `upsert_hold`/`write_hold_event` likewise never construct an item containing `ttl_disposal_at`. No further work is needed for Category 4.

Categories 3 and 6 (job logs, `AuditMetadata`, `AuditExecutionIdentity`) have **no equivalent structural guard today**, because their write methods (items 4a–4k, 6–7, 11–12, 17–18, 22–25) are existing, locked Phase 1–7 code that this workstream does not modify (per this document's own out-of-scope statement) — retrofitting a runtime assertion into every one of those existing methods would mean touching Phase 4/5/6/7 internals for a governance concern that Category 3/6's own semantics already prevent by simple omission (these methods have never set, and under A1.3 will continue to never set, `custody_expires_at`/`ttl_disposal_at`). Adding a runtime guard to code that structurally cannot violate the invariant (because A1.3 is defined to never touch those write paths) would be exactly the kind of premature, speculative hardening this project's stated bias warns against.

**The chosen enforcement is therefore test-level, not runtime-level, for Categories 3/5/6:** a negative unit test per Category-3/5/6 write method, asserting the item constructed by that method never contains a `custody_expires_at` or `ttl_disposal_at` key. This is real, checkable enforcement (a regression in any of those methods that started setting the field would fail the test immediately) without adding a runtime assertion to code this workstream has no other reason to touch. §18.9 scopes this test list explicitly.

**One additional structural point confirmed during this amendment's re-verification:** `CustodySweepClient.remove_ttl_disposal_at`/`restore_ttl_disposal_at` (items 31) query *every* item under an audit identity's partition with no record-type allowlist at all — confirmed directly in the already-merged code (`_query_audit_items`'s own docstring states this explicitly) — and act on whatever it finds carrying (or not carrying) `ttl_disposal_at`/`custody_expires_at`. This design is **correct, not a gap**, but only on the precondition that §18.1's write-time classification is honored everywhere: `CustodySweepClient` never needs to know a record's category because Category 3/5/6 records will structurally never carry the field it looks for, by construction of their write paths never setting it. This is stated explicitly here because it is the load-bearing assumption underneath `CustodySweepClient`'s existing "no allowlist" design — if a future change ever caused a Category 3/5/6 write path to start setting `ttl_disposal_at` for an unrelated reason, `CustodySweepClient` would silently start sweeping it, with no guard to catch the mistake. The negative-test coverage in §18.9 is this precondition's actual enforcement mechanism.

### 18.4 Regeneration Semantics — One Governed Rule Across Phase 5, 6, and 7

This is a real correctness gap in the mechanism as previously scoped, not a hypothetical. §11's inventory shows three different regeneration mechanics for Category 2 records — Phase 5's `update_intelligence_metadata` (unconditional full `put_item`, item 14), Phase 6's `update_report_metadata_fields` (unconditional partial `SET`, item 20), and Phase 7's `write_cert_metadata_complete` (unconditional full `put_item`, no condition at all, item 26) — and none of them currently has any awareness of `custody_expires_at`/`ttl_disposal_at` at all, because those fields do not exist in the codebase yet. Without a single governed rule, three independent implementations of "what happens to custody fields on regen" would very likely diverge, and the specific failure mode Product Strategy called out — a full-overwrite regen silently reintroducing `ttl_disposal_at` on a record whose evidence is currently under legal hold — is exactly the kind of defect that would not surface until an actual regen-under-hold scenario occurred in production.

**The governed rule, applying identically to items 14, 20, and 26 regardless of each phase's own write mechanics (full-overwrite vs. partial-update, which this amendment does not change):**

1. **`custody_expires_at` is always freshly computed on regeneration**, from the regeneration event's own timestamp — not preserved from the prior generation. This is the correct default, not an accidental extension, because every regeneration produces a genuinely new S3 artifact at a new key with its own genuine creation time (confirmed: no Category 1/2 S3 write path ever overwrites an existing key outside the one `configs/*` exception in Category 5). A fresh `custody_expires_at` keeps the DynamoDB pointer's clock in lockstep with the new artifact it now points to, consistent with Category 2's own definition (§18.1).
2. **`ttl_disposal_at` is set conditionally on the audit identity's *current* legal-hold status, read fresh at regeneration time** (`HoldRepository.get_legal_hold(client_id, audit_id).status`), not carried forward from whatever the prior generation's value happened to be:
   - If a hold is currently `ACTIVE`: the regenerated item must **omit** `ttl_disposal_at` entirely — this is the direct fix for "a regen must never silently reintroduce the field while held."
   - If no hold is active: `ttl_disposal_at = custody_expires_at` (the freshly computed value from rule 1), identical to a first-time write.
3. **Partial-update paths (Phase 6, item 20) must explicitly include both fields in their `SET`/updates dict on every regen call** — today, Phase 6's regen path touches only `report_job_id`/`generation_count`/`status`/`updated_at`; per this rule it must be extended (in A1.3 implementation) to also explicitly set `custody_expires_at` and (conditionally) `ttl_disposal_at` on every regeneration, exactly as rules 1–2 specify. This removes the asymmetry Product Strategy flagged versus Phase 5/7's full-overwrite regen — not by making Phase 6's write mechanics match Phase 5/7's (that would mean changing Phase 6's own locked design, out of scope), but by making the *retention-field outcome* of all three phases' regen paths identical regardless of how each phase's own write mechanics get there. A partial-update path that simply never mentions `ttl_disposal_at` at all (as Phase 6's does today) is a safe default *only* for the "don't accidentally restore a removed TTL" half of the problem (DynamoDB `UpdateItem` never touches unlisted attributes) — it is not a safe default for the "the record needs a fresh custody clock reflecting its new content" half, which is why explicit inclusion is required, not merely reliance on partial-update's own not-touching-unlisted-fields behavior.
4. **Full-overwrite paths (Phase 5 item 14, Phase 7 item 26) must construct their replacement item using rules 1–2 above, every time** — since a full `put_item` replaces the entire item, omitting `ttl_disposal_at` from the new item dict when a hold is active is both necessary and sufficient (there is no "unlisted attribute" safety net the way partial-update has; a full-overwrite that forgets to omit the field will set it).
5. **Prior/superseded S3 artifacts require no special handling.** Because every S3 write is to a unique, never-reused key (confirmed across items 3, 16, 21, 27, and the one Category 5 exception), a superseded artifact continues aging off on its own original `custody_expires_at` clock, computed at its own original write time, entirely unaffected by any later regeneration of the DynamoDB pointer that now points elsewhere. No cross-referencing between the current and prior artifact is needed or proposed — this is a clean emergent property of the existing "new key per regen" design, not something this amendment has to build.
6. **Retries stay idempotent under the existing conditional-write semantics, unchanged by this rule.** For Category 1/2 CREATE paths guarded by `attribute_not_exists` (items 1, 3, 8, 9, 10, 13, 19), a retry before the first write succeeded is a fresh write with fresh custody fields — correct. A retry after a genuinely completed first write is rejected by the existing condition (`ConditionalWriteError`), leaving the original, successful write's custody fields authoritative — also correct, and this rule introduces no new retry-handling requirement beyond what items 1/3/8/9/10/13/19 already do today.

This rule is proposed as a Non-Negotiable Invariant candidate for the companion ADR — see §18.10.

### 18.5 The Dual-Tree Hazard — Resolved for A1.3, Flagged for the Future

§11's re-verification (the correction noted at the top of that section) narrows this from how it was originally framed. The genuinely dual-tree, both-live write path is `AuditMetadataRepository` (items 4a–4g, 4c specifically confirmed dual-tree-live) — but every record type that class governs is Category 3 or Category 6 (§18.1), and Categories 3/6 receive **no** custody-field treatment in A1.3 at all. `RunMetadata` — the one Category-2 record type anywhere near this hazard — was independently traced to a single live write path (`packages/storage/dynamodb_client.py`/`s3_client.py`, via `apps/backend/orchestrator/service.py`, wired exclusively by `apps/backend/handlers/orchestrator_handler.py`); the `src/release_confidence_platform/storage/` copies of `DynamoDBMetadataClient`/`S3StorageClient` were not found wired into any live caller for this record type.

**Conclusion: neither tree requires direct modification for A1.3, and no shared custody-calculation helper is justified now.** The dual-tree hazard does not block or require rework of A1.3 as scoped by §18.1, because the one class it genuinely, currently threatens (`AuditMetadataRepository`) governs only Category 3/6 records, which A1.3 does not touch. Proposing a shared component to solve a problem that does not arise for any in-scope record type would be exactly the premature abstraction this project has a stated bias against — there is no correctness requirement pulling one into existence today.

This conclusion is conditional, not permanent: if a future workstream ever decides `AuditMetadata` (or another `AuditMetadataRepository`-governed record) should move from Category 6 into a custody-bearing category, the dual-tree hazard becomes immediately load-bearing, and at that point a shared custody-calculation helper (or consolidating the two trees into one) would need to be justified on correctness grounds — both trees would need to compute identical `custody_expires_at`/`ttl_disposal_at` values from identical inputs, and two independently-maintained near-duplicate implementations are a documented risk for silent divergence. **This is flagged here as a tracked risk (§18.11), not resolved, and not acted on now.**

Separately, and outside this amendment's scope but worth recording since it surfaced during verification: `packages/storage/audit_metadata_client.py` and `src/release_confidence_platform/storage/audit_metadata_client.py` are near-byte-identical duplicate implementations of the same class today, for reasons unrelated to retention — this is a pre-existing structural characteristic of the codebase (confirmed the `rcp` CLI entrypoint is `release_confidence_platform.operator_cli.main:main`, the `src/` tree; Lambda handlers use `packages/`), not something Workstream A introduced or is positioned to fix.

### 18.6 Classifying `configs/` — Audit Input, Not Evidence, Not A1.3 Scope

`configs/*` (Category 5: `client_config.json`, `audit_config.json`, `endpoints.json`, item 5, CLI-only via `AuditCreationService.create_from_files` → `S3StorageClient.write_json`) is an **audit input artifact**, not evidence of an audit's execution outcome — it is the configuration an audit was run *against*, not a record of what happened when it ran. Confirmed by direct inspection: `evidence_retention/constants.py::S3_EVIDENCE_CLASS_PREFIXES` (the already-built, already-merged bounded list `CustodySweepClient` sweeps) does not include `configs`, and no `LifecycleConfiguration` rule in `infra/resources/s3.yml` references it. `configs/*` is also the **one confirmed same-key-overwrite case** in the entire inventory (`write_json(..., overwrite=force)`), meaning it genuinely produces noncurrent S3 versions under `--force` — a materially different lifecycle-management problem than any of the four write-once-per-key evidence classes A1.2 already built rules for.

**This document does not fold `configs/` into A1.3 scope**, per Product Strategy's explicit instruction. If `configs/*` is later judged to need its own retention/lifecycle treatment, it requires its own Lifecycle rule (a fifth rule, or a decision that configuration artifacts follow a different retention model entirely — e.g., "retained for the life of the audit, disposed only when `AuditMetadata` itself is," which would tie its disposal to the Category 6 question in §18.1 rather than to any evidence-class custody period), and its own explicit Product Strategy authorization. Not deciding this now is itself the correct scope boundary, not an oversight.

### 18.7 Constraining `AggregationRepository.update_job`

Item 7 (`update_job`) accepts a caller-supplied `dict[str, Any]` and builds a dynamic `UpdateExpression` from its keys with **no field allowlist whatsoever** — confirmed by direct re-read of `aggregation/repository.py` during this amendment: every key in the caller's dict becomes a `SET` target, unconditionally. This is Phase 4's own existing, locked update path (`AggregationJob`, Category 3 — an operational coordination record, per §18.1, that must never carry `custody_expires_at`/`ttl_disposal_at` at all), and its current design means nothing today stops a future caller — accidentally or otherwise — from passing `{"ttl_disposal_at": ...}` through this method and having it silently accepted and written.

**The required fix does not move Phase 4 update logic into the retention module** (per Product Strategy's explicit instruction to preserve Phase 4's ownership of its own update path) and does not change `update_job`'s existing signature, callers, or behavior for any field Phase 4 itself uses. It adds one thing: a **field-name rejection guard**, local to `aggregation/repository.py`, checked before the existing `UpdateExpression` is built:

```
_RETENTION_GOVERNED_FIELD_NAMES = frozenset({"ttl_disposal_at", "custody_expires_at"})

def update_job(self, key, updates):
    if _RETENTION_GOVERNED_FIELD_NAMES & updates.keys():
        raise AssertionError(
            "AggregationJob.update_job must never set retention-governed "
            f"fields {sorted(_RETENTION_GOVERNED_FIELD_NAMES & updates.keys())!r}; "
            "AggregationJob is Category 3 (operational coordination metadata) "
            "and is permanently excluded from custody-field treatment."
        )
    # ... existing UpdateExpression construction, unchanged ...
```

This is a rejection guard, not an allowlist of every legitimate field `_complete_job` and other Phase 4 callers already use — it does not need to enumerate Phase 4's own field vocabulary (which this module already owns and controls) to close the specific gap raised (retention-field smuggling through an unrestricted `dict[str, Any]`). It mirrors the existing SK-shape/operation-shape guard pattern (`_assert_phase7_sk`, `_assert_retention_sk`, `_assert_disposal_sk`, `_assert_custody_field_only_update`) already established across this codebase and this workstream, applied here as a two-item denylist rather than an allowlist, since a denylist is the minimal change that closes the gap without taking on ownership of Phase 4's full field vocabulary.

This is the only proposed code change to any existing Phase 1–7 repository method anywhere in this amendment — every other Category 1/2 write path (items 1, 3, 8, 9, 10, 13, 14, 15, 19, 20, 26) is proposed to gain fields additively (new fields, no behavior change to existing fields), which is a materially smaller-risk change than `update_job`'s unrestricted `dict[str, Any]` pattern warrants a denylist for.

**Clarified per Product Strategy observation (post-§18 approval):** this denylist is a **tactical, local protection scoped to the specific gap `update_job`'s unrestricted `dict[str, Any]` pattern creates for A1.3** — it is not intended to become a general governance-field enforcement mechanism, is not a precedent for retrofitting similar guards onto other update methods absent a comparable structural gap, and does not establish a reusable "governance field denylist" abstraction elsewhere in the codebase. If a future write path is found with the same class of defect (an unrestricted attribute dict with no allowlist, touching a Category 3/4/5/6 record type), that is a new, separately evaluated finding, not an automatic application of this pattern.

### 18.8 Backlog Migration Remains Explicitly Out of Scope

Restated, again, as Product Strategy requested: A1.3 scope excludes bulk backfill, retroactive TTL assignment, migration commands, and historical-record mutation. Nothing in this amendment changes that. §15's existing "Assumption requiring confirmation" on backlog handling (prospective-only enforcement, backfill clocked from backfill-execution time, a separate `rcp retention backfill-custody` command) stands as previously documented and is not re-litigated here — it remains a distinct, separately authorized Product Strategy decision, not something this governed revision folds into A1.3's write-path work.

### 18.9 Revised Implementation Estimate and Sequencing

**Scope correction from the file list this document previously proposed:** the prior revision implied all of Phase 1–7's write paths needed the tag/TTL-field change (7 rows). ## 19. Legal Hold Temporal Coverage — Authoritative Hold State and Write-Time Coordination (Deployment-Blocking Amendment)

**Status of this amendment:** Product Strategy identified a structural defect — the highest-priority open issue in Workstream A — in the already-merged legal-hold mechanism (A1.1/A1.2) and its already-merged RunMetadata integration (A1.3b/A1.3b.1). No rollback is required (the capability is non-deployed; custody configuration is unwired; no hold operation has ever been invoked against real evidence). **All Workstream A retention functionality is deployment-blocked, and A1.3c is withheld, until this section's mechanism is implemented and validated.** This section does not reopen §18's governed-record boundary or regeneration rule — it is additive to both, and amends §18.4's regeneration rule at §19.9 to close the identical race class for regeneration writes.

**The defect, precisely:** `CustodySweepClient` (already built, A1.2) and `HoldRepository.upsert_hold` (already built, A1.1) implement legal hold as a snapshot-in-time sweep — placing a hold flips `ttl_disposal_at`/`rcp-legal-hold` on every record/object that exists *at the moment the sweep runs*. Nothing addresses records or objects created *after* that point. Audits execute over an extended, EventBridge-scheduled window (confirmed: `docs/architecture/execution_lifecycle.md`, "Finalization is triggered by an EventBridge schedule at the end of the audit window"; `SCHEDULE_TYPE_REPEATED` in `audit_scheduling/constants.py` confirms RUN records arrive via repeated, separately-scheduled invocations, not atomically) — a legal hold can be placed mid-window, and every governed record created after that point today receives `ttl_disposal_at = custody_expires_at` unconditionally, with no check of current hold status at all. This already affects the merged A1.3b/A1.3b.1 RunMetadata CREATE path (§19.8).

**Governing invariant (Product Strategy's exact language, restated as the acceptance bar for this section's design):** *"Once an audit is under active legal hold, every existing and subsequently created governed record or object associated with that audit must remain ineligible for automated disposal until the hold is released."*

### 19.1 Authoritative Active-Hold State Model

`LegalHold` (existing record, `PK=CLIENT#{client_id}` / `SK=AUDIT#{audit_id}#LEGALHOLD`, owned exclusively by `HoldRepository`, SK-guarded by the existing `_assert_retention_sk`, all unchanged) gains two new fields, both additive to the existing schema (`status`, `hold_id`, `placed_at`, `placed_by`, `reason`, `hold_count`, `released_at`, `released_by` are all unaffected):

| Field | Type | Description |
| --- | --- | --- |
| `hold_version` | Number | Monotonically incrementing optimistic-concurrency token. Starts at `1` on the first-ever `PLACE`. Incremented by exactly `1` on **every** subsequent write to this record — every `PLACE` and every `RELEASE`, with no exception, including a `PLACE` following a prior `RELEASE` (re-holding an audit does not reset it). Never reused, never derived from `status`, never decremented. |
| `sweep_status` | String, bounded (`PENDING` \| `IN_PROGRESS` \| `COMPLETE` \| `FAILED`) | Tracks completion of the *current* hold episode's pre-existing-record sweep (§19.6), independent of `status`. Reset to `PENDING` at the start of every `PLACE` and every `RELEASE` (each has its own sweep — placement's removes/tags-true, release's restores/tags-false). |

**Why a dedicated counter, not a reuse of `status`:** a `PLACE → RELEASE → PLACE` cycle returns `status` to `ACTIVE` twice with an identical value, but the two episodes are governance-distinct events. An optimistic-concurrency check conditioned on `status` alone would not detect that a transition happened in between if the value happened to match at both ends. `hold_version`, monotonic and incremented on every write with no exception, cannot alias in this way.

**Why `sweep_status` is a separate field, not folded into `status`:** `status=ACTIVE` answers "is this audit currently held" — true from the instant `upsert_hold`'s `ACTIVE` write commits. It does **not** answer "has every record that existed before that commit been brought into compliance" — that is a separate, independently-progressing fact, and conflating the two would let a caller (an operator running `rcp retention hold status`, or a future automated check) treat an in-progress sweep as if it had already finished. See §19.6 for the precise semantics this distinction protects.

**Effective ordering — preserved, made load-bearing:** placement is effective *before* the sweep begins, not during or after it. This was already the existing sequence (Technical Design §10.4: `HoldRepository` writes precede `CustodySweepClient` calls) — this amendment does not reorder anything; it makes that ordering a Non-Negotiable Invariant (companion ADR Invariant 13) rather than an incidental consequence of sequential code, because it is the property every other guarantee in this section depends on: every write whose own hold-state read happens after `upsert_hold`'s `ACTIVE` commit observes `ACTIVE`, regardless of whether the sweep of pre-existing records has finished.

**How concurrent writers detect a state change:** by reading `HoldRepository.get_legal_hold(client_id, audit_id)` and comparing the returned `hold_version` (or its absence, for an audit never held) against what a `TransactWriteItems` `ConditionCheck` verifies has not changed between that read and the writer's own commit — the full protocol is §19.4.

### 19.2 Hold-Placement Sequence

1. Operator invokes `rcp retention hold place --client-id C --audit-id A --reason "..." --actor "..."`.
2. `RetentionService` reads current `LegalHold` via `HoldRepository.get_legal_hold(C, A)`.
3. **If no record exists, or the existing record's `status = RELEASED`:** this is a genuine new hold episode. `RetentionService` generates a fresh `hold_id` (§19.5.2's corrected identity model — this `hold_id` identifies the episode and is reused, unchanged, by this episode's eventual paired `RELEASE`) and computes `hold_version = (current value, or 0 if none) + 1`, writes a new `LegalHoldEvent` (`PLACE`, append-only, unchanged from the existing design), then calls `HoldRepository.upsert_hold` with `status=ACTIVE`, the new `hold_id`, the new `hold_version`, `sweep_status=PENDING`. **This write must be confirmed durably committed before step 4 begins** — this commit is the moment the hold becomes authoritative (§19.1).
4. **If the existing record's `status` is already `ACTIVE`:** this invocation is a re-run of an already-placed hold. `RetentionService` does **not** call `upsert_hold` again (no new `hold_version`, no new `LegalHoldEvent`). **Its next action depends on `sweep_status` (correction — session-continuation verification found the unconditioned form of this step unsafe, not previously flagged):**
   - **If `sweep_status != COMPLETE`** (`PENDING`, `IN_PROGRESS`, or `FAILED`): this is a genuine resumption of an interrupted sweep (§19.6) — proceed directly to step 5 using the *existing* `hold_version`.
   - **If `sweep_status == COMPLETE`:** this is a stale re-invocation with nothing left to resume. Treat as a pure no-op at the governance-state level and **return immediately, without proceeding to step 5 at all.** **Correction (real, concrete defect found on verification, not assumed safe): the prior text proceeded to step 5 unconditionally.** That is unsafe once the original marker has been disposed per its purpose-limited retention (§19.5.8) or has aged out early (the residual §19.5.8 already flags) — the conditional `PutObject` would then succeed as a *fresh* first write (the key is genuinely absent from S3), producing a new, later `marker_confirmed_last_modified` and silently overwriting the historically accurate confirmation already durably recorded on this transition's `LegalHoldEvent` — corrupting the exact compliance-facing record ADR Invariant 22's disposal justification depends on. §19.5.3 additionally hardens marker establishment itself against this same class of defect (checking `LegalHoldEvent.marker_status` before ever touching S3); this gate and that hardening are two independent, mutually reinforcing closures of the same root issue — see ADR Invariants 23–24 and §19.11 item 21.
5. **Revised (marker mechanism, §19.5.3):** `RetentionService` writes and confirms the `PLACE` canary marker (§19.5.1–19.5.3) — this establishes `marker_confirmed_last_modified`, an S3-domain timestamp, as the reconciliation pass's boundary reference, in place of the prior revision's Lambda-wall-clock `sweep_started_at`. Only once `marker_status = CONFIRMED` does `sweep_status → IN_PROGRESS` and step 6 begin. If the marker cannot be established, this sequence fails closed here (§19.5.6) — it does not proceed to the sweep on an unconfirmed boundary.
6. `CustodySweepClient.remove_ttl_disposal_at(C, A)` and `CustodySweepClient.retag_s3_versions(C, A, legal_hold=True)` run — existing, unchanged methods, enumerating records/objects that exist as of their own `Query`/`ListObjectVersions` calls.
7. **New:** the S3 reconciliation pass (§19.5.5) runs immediately after step 6's `retag_s3_versions`, scoped to `LastModified >= (marker_confirmed_last_modified - 5s)` from step 5, re-tagging any object matching that window still carrying `rcp-legal-hold != true`.
8. On full success of steps 5–7: `sweep_status → COMPLETE`; counts recorded on the current hold episode (extending `LegalHoldEvent`'s existing `s3_versions_retagged_count`/`dynamodb_items_updated_count` fields with a new `s3_reconciliation_versions_retagged_count` field, kept distinct for auditability of which mechanism caught what).
9. On partial failure of steps 5–7: `sweep_status` remains `IN_PROGRESS` (or transitions to `FAILED` for a detected non-retriable error, including marker-establishment failure — §19.5.6/§19.6). `rcp retention hold place` must be safely re-invocable (step 4's path) to resume, reusing an already-confirmed marker rather than re-writing one (§19.5.7).

### 19.3 Hold-Release Sequence

**Correction (Product Strategy, post-review): the claim in the prior revision of this section — that release needs no reconciliation pass because "fresh reads normally produce the correct result" — is wrong and is retracted.** It addressed only writes whose hold-state read happens after release commits; it did not address a write whose read happened *before* release (observing `ACTIVE`) but whose `PutObject` completes *after* the release-sweep has already run. Precisely: (1) an S3 writer reads hold state and observes `ACTIVE`; (2) release becomes authoritative; (3) the release-sweep runs, clearing tags/restoring `ttl_disposal_at` on everything that exists *at that moment*; (4) the writer's `PutObject` completes afterward, carrying `rcp-legal-hold=true` derived from its now-stale pre-release observation. Because the release-sweep is itself a snapshot of what exists when it runs, this object — which didn't exist yet when the sweep ran — is never touched by anything afterward, and remains tagged `true` indefinitely. **This is the same structural class of race the whole amendment exists to close, reached from the opposite direction, and the fix is symmetric: `RELEASE` gets the identical canary-marker-plus-reconciliation mechanism `PLACE` already has (§19.5), not a proof that it can be safely omitted.**

1. Operator invokes `rcp retention hold release --client-id C --audit-id A --actor "..."`.
2. `RetentionService` reads current `LegalHold`. **Three cases (correction — session-continuation verification found the original two-case form of this step incomplete, not previously flagged):**
   - **`status = ACTIVE`:** a genuine new release — proceed to step 3.
   - **`status = RELEASED` and `sweep_status != COMPLETE`:** this is a resumption of *this same episode's own* interrupted release-sweep, symmetric with §19.2 step 4's `PLACE` resume branch. `RetentionService` does **not** call `upsert_hold` or write a new `LegalHoldEvent` again — it proceeds directly to step 4 using the *existing* `hold_id`/`hold_version`. **Correction (real, concrete gap found on verification): the original text of this step required `status = ACTIVE` unconditionally, else `HOLD_NOT_ACTIVE`.** That correctly rejects the case below but also incorrectly rejected this one — an interrupted release-sweep had no documented way to resume via the operator-facing `release` command at all, contradicting §19.6's claim that release remains "safely re-invocable to resume." This branch closes that gap.
   - **`status = RELEASED` and `sweep_status == COMPLETE`, or no record exists:** raise `HOLD_NOT_ACTIVE`, exactly as originally specified (existing design's idempotency contract, §8: "a second release attempt likely indicates operator confusion... worth surfacing, not silently ignored"). This case never reaches step 4, so it is inherently immune to the marker-disposal defect §19.2 step 4 required a fix for — there is nothing further to correct here.
3. `RetentionService` writes a new `LegalHoldEvent` (`RELEASE`, using the **same** `hold_id` this episode's `PLACE` already established — §19.5.2's corrected identity model; no new `hold_id` is generated for a release), then calls `HoldRepository.upsert_hold` with `status=RELEASED`, the unchanged `hold_id`, `hold_version` incremented by `1`, `sweep_status=PENDING` (this episode's release-sweep). This commit remains the moment release becomes authoritative for the DynamoDB leg and for any write whose hold-state read happens after it — that part of the original reasoning was correct and is unchanged. Reached only via step 2's first case (genuine new release).
4. **New, symmetric with placement (§19.2 step 5):** `RetentionService` writes and confirms a `RELEASE` canary marker (§19.5.1–19.5.3, same mechanism, `action: "RELEASE"`) — establishing its own `marker_confirmed_last_modified` for this transition. Only once confirmed does `sweep_status → IN_PROGRESS` and step 5 begin. Marker-establishment failure fails this sequence closed exactly as it does for placement (§19.5.6).
5. `CustodySweepClient.restore_ttl_disposal_at(C, A, now)` and `CustodySweepClient.retag_s3_versions(C, A, legal_hold=False)` run — existing, unchanged methods (`MAX(custody_expires_at, now)` clamping already handled).
6. **New, symmetric with placement:** a release-side reconciliation pass runs immediately after step 5, scoped to `LastModified >= (marker_confirmed_last_modified - 5s)` **and** current `rcp-legal-hold` tag `== true` (the inverse filter direction from placement's pass, §19.5.5) — these are objects written using a stale pre-release `ACTIVE` observation, still incorrectly tagged held; re-tag them `false`.
7. `sweep_status → COMPLETE` only once the marker, the primary sweep, and the reconciliation pass have all completed without error — same standard as placement (§19.6).

**Does the DynamoDB leg need the same fix?** No — confirmed by re-examining §19.4's mechanism specifically for this direction: a DynamoDB writer's `TransactWriteItems` `ConditionCheck` re-verifies `hold_version` at the transaction's actual commit instant, not at the preceding read's instant. If release commits between a writer's read and its transact-write attempt, the `ConditionCheck` fails and forces a retry, which then correctly observes `RELEASED` — DynamoDB was already immune to this exact race by construction, which is precisely why the new required correction is S3-specific.

**Nature of the defect being closed, stated per Product Strategy's own framing:** unlike the original placement-side defect (which risked *under*-protection — evidence disposed while it should have been held), this release-side gap risks *over*-retention — an object stuck tagged held indefinitely, satisfying ADR Non-Negotiable Invariant 14's "ambiguous outcomes resolve toward retention" in the narrow technical sense, but this is not a reason to leave it open: indefinite unintended over-retention is its own real defect (evidence that should become disposable per a legitimate custody period never does), and Invariant 14 was never meant to excuse a known, fixable mechanism gap merely because its failure direction happens to be the safer one. It is closed here, not merely tolerated.

### 19.4 DynamoDB Concurrency Protocol

Every Category 1/2 governed-record write (CREATE per §18.1, and regeneration per §18.4 as amended by §19.9) is a `TransactWriteItems` call with two logical parts, reusing this codebase's existing transactional pattern (`AggregationRepository.put_records_once`) and its existing optimistic-concurrency idiom (`AuditMetadataRepository.append_lifecycle_transition`'s `lifecycle_state = :expected_state`) rather than introducing new infrastructure:

1. **Read:** `HoldRepository.get_legal_hold(client_id, audit_id)` → `None`, or a dict with `hold_version` and `status`.
2. **Compute:** `custody_expires_at` is always freshly computed (unchanged from the existing design). `ttl_disposal_at` is set equal to `custody_expires_at` **only if** the read in step 1 returned `None` or `status != ACTIVE`; **omitted** if `status == ACTIVE`.
3. **Commit, as one `TransactWriteItems` call:**
   - **Item A — `ConditionCheck` against the `LegalHold` key:** `attribute_not_exists(PK)` if step 1 read `None`; `hold_version = :n` (the exact value read) if step 1 read a record. This item performs no write of its own — it is a pure assertion that aborts the entire transaction if false.
   - **Item B — the governed record's own `Put` (or, for Phase 4's `put_records_once`, the existing variable-length, `4 + 3N`-item governed set — N = distinct endpoint count, §19.16 — extended to include Item A as one additional appended transact-item in the *same* transaction rather than a separate one) — with whatever condition that write already carries today (e.g., `attribute_not_exists(PK) AND attribute_not_exists(SK)` for a CREATE), unchanged. §19.16 governs the resulting transaction's item-count and byte budget specifically for `put_records_once`, since it is the one write path in this table whose governed-item count is not fixed.**
4. **On `TransactionCanceledException`:** inspect the response's `CancellationReasons` array — DynamoDB returns one entry per transact-item, in the same order the items were submitted, each with a `Code` of either `None` (that item's own condition passed) or a failure code such as `ConditionalCheckFailed`. Because both items can fail in the same attempt (e.g., a genuine duplicate-write race that happens to coincide with a concurrent hold-state change), **precedence is explicit and checked in this fixed order, not inferred from which failure is noticed first:**
   - **Check the governed record's own item (Item B) first.** If its `CancellationReasons` entry is *not* `None` (its own condition — e.g., `attribute_not_exists(PK) AND attribute_not_exists(SK)` — failed), surface the existing, unchanged error for that write path (`DuplicateRunIdError`, `ConditionalWriteError`, etc.) **regardless of whether Item A (the `LegalHold` `ConditionCheck`) also failed in the same attempt.** A genuine duplicate-write condition is a real bug or a genuine race on the governed record's own identity, independent of hold state, and must never be masked behind a hold-version retry loop — retrying would not fix a duplicate-write condition, it would only obscure it behind repeated, confusing hold-state churn.
   - **Only if Item B's condition passed** (its `CancellationReasons` entry is `None`) **and Item A (the `LegalHold` `ConditionCheck`) failed**, treat this as a genuine hold-state race: **retry from step 1** (fresh read, fresh compute, fresh transact-write), up to 3 attempts (an engineering reliability choice, not a product tradeoff — recommended, not flagged for confirmation).
   - If neither item's condition failed but the transaction was still cancelled (e.g., a transient throttling or capacity cancellation reason unrelated to either condition), retry the whole transaction unconditionally, bounded by the same 3-attempt cap, without re-deriving custody fields (the read-compute step does not need to re-run for a non-condition-related cancellation).
5. **On retry exhaustion:** fail closed — raise a new `StorageError` (`HOLD_STATE_CONCURRENCY_EXCEEDED`) rather than falling back to an unconditioned write. This is the direct enforcement of ADR Non-Negotiable Invariant 11 (no write may commit `ttl_disposal_at` without an atomic version check) and Invariant 14 (ambiguity resolves toward retention — here, toward refusing to write at all rather than guessing).

**Symmetry:** this single mechanism handles both directions without special-casing — a hold placed concurrently with a "no hold" write forces that write to retry and correctly observe the new `ACTIVE` state (never silently committing `ttl_disposal_at` on a now-held audit); a hold released concurrently with a "held" write forces that write to retry and correctly observe `RELEASED` (or, if it doesn't retry in time and the transaction still succeeds against the stale-but-not-yet-changed version, it simply omits `ttl_disposal_at` on a record that will then need the *next* release-sweep's write-time correctness to catch — which is symmetric with, not worse than, the existing accepted TOCTOU risk in §16).

### 19.5 S3 Concurrency and Reconciliation Protocol — Canary-Marker Mechanism (Default), Buffer (Defense-in-Depth)

**Amendment (Product Strategy directive, post-review):** the prior revision of this section made a 5-second Lambda-wall-clock-vs-`LastModified` buffer the *sole* correctness mechanism for the S3 leg, with a canary-marker approach documented only as a rejected-for-now, provably-tighter alternative. Product Strategy's reasoning: legal hold is a constitutional evidence-integrity control, and a known, avoidable, formally-unprovable uncertainty must not be the *primary* correctness mechanism when a more rigorous alternative exists and hold placement/release are low-frequency, operator-invoked, non-hot-path operations — the additional coordination cost is justified. **The canary-marker mechanism specified below is now the default, primary S3 coordination protocol. The 5-second buffer is retained, but only as defense-in-depth around the marker boundary — not as the mechanism correctness depends on.** S3 still has no transactional primitive spanning a DynamoDB item and an S3 object, so cross-store atomicity is still not attempted (see companion ADR Consequences) — each store still achieves correctness independently; what changes here is *how* the S3 leg achieves it.

#### 19.5.1 Marker Identity and Storage Location

**Correction (Product Strategy — real, concrete defect): the key format in the prior revision, `retention-markers/{client_id}/{audit_id}/{hold_id}.marker`, was found not to guarantee `PLACE` and `RELEASE` get distinct keys.** The key format is corrected below to append `{hold_version}-{transition}`, whose non-collision is provable from `hold_version`'s monotonicity alone (§19.5.2) — independent of `hold_id`, which (per the corrected identity model, §19.5.2) identifies the episode and is constant across a `PLACE`/`RELEASE` pair, not a second uniqueness source.

**Required key shape:** `retention-markers/{client_id}/{audit_id}/{hold_id}/{hold_version}-{transition}.marker`, where `{transition}` is `PLACE` or `RELEASE`. **Corrected identity model (Product Strategy — required correction, not accepted as previously stated): `hold_id` identifies one legal-hold *episode* from placement through release, and is constant across that episode's `PLACE` and `RELEASE` — it is never regenerated per transition.** The immutable per-transition identity is supplied by `hold_version` and `transition` together, not by `hold_id` changing. A later, independent hold episode on the same audit identity may receive a new `hold_id` (a design freedom this document does not need to resolve — see §19.5.2), but the key format's non-collision guarantee never depended on that freshness in the first place. Concrete worked example for one full `PLACE` → `RELEASE` episode on the same audit identity:

```
PLACE  (1st transition, hold_version=1):
  retention-markers/client_abc/audit_xyz/hold_4f5a/1-PLACE.marker

RELEASE (2nd transition, hold_version=2):
  retention-markers/client_abc/audit_xyz/hold_4f5a/2-RELEASE.marker
```

Note `{hold_id}` is **identical** between the two (same episode) — only `{hold_version}-{transition}` differs, and that alone is sufficient for non-collision (§19.5.2 proves this from `hold_version`'s monotonicity alone). `{hold_id}` in the key path groups a `PLACE`/`RELEASE` pair under one S3 prefix for traceability and browsability — that is its purpose here, not uniqueness. Explicitly **not** one of the four evidence-class prefixes (`raw-results/`, `intelligence/`, `reports/`, `integrity/`; confirmed absent from `S3_EVIDENCE_CLASS_PREFIXES`), and therefore never subject to any evidence-class Lifecycle rule and never enumerated by `CustodySweepClient`'s own evidence-retagging sweep. The marker is **governance metadata (Category 4, §18.1)** — analogous in kind to `LegalHoldEvent`/`DisposalRecord`, just on the S3 side of the store boundary rather than the DynamoDB side — not evidence content. Content: `{"hold_id": ..., "hold_version": ..., "action": "PLACE"|"RELEASE", "client_id": ..., "audit_id": ...}` — enough to make an orphaned marker (§19.5.7) self-describing without a lookup, and redundant with the key's own components for defense-in-depth.

**Does it need a corresponding DynamoDB record?** Yes, for queryability and audit trail, but as an *extension of the existing `LegalHoldEvent` record*, not a new record type — consistent with this design's standing bias against introducing a new abstraction where an existing one already fits (§18.9's dual-tree reasoning, §19.10's subphase-consolidation reasoning). `LegalHoldEvent` gains three additive fields: `marker_s3_key`, `marker_status` (`PENDING` \| `CONFIRMED` \| `FAILED`), `marker_confirmed_last_modified` (the S3-domain timestamp read back after the marker write, §19.5.4). `LegalHold` (the current-state record) also gains `marker_s3_key`/`marker_confirmed_last_modified` for the *current* transition, mirroring how it already denormalizes `sweep_status` from the latest episode, so `rcp retention hold status` can report marker state without a separate query.

**Required consequence of the corrected identity model — `LegalHoldEvent`'s existing SK must gain a transition-discriminating component (flagged here, implemented in Legal-Hold Correction B1's "transition-safe `LegalHoldEvent` persistence" scope item, not in this document):** `HoldRepository.legal_hold_event_key`/`write_hold_event` (already merged, A1.1) construct the SK as `AUDIT#{audit_id}#LEGALHOLD#{hold_id}` and write via a conditional `attribute_not_exists(PK) AND attribute_not_exists(SK)` put. Under the corrected identity model, `hold_id` is constant across a `PLACE`/`RELEASE` pair — so, unchanged, this SK would make `RELEASE`'s event write collide with `PLACE`'s already-written event at the identical key, failing every `RELEASE` unconditionally. **Fix: the SK must incorporate `hold_version` as the per-transition discriminator** — `AUDIT#{audit_id}#LEGALHOLD#{hold_id}#{hold_version}` — reusing `hold_version` rather than introducing a separate `transition_id` field, since `hold_version` already satisfies exactly the uniqueness property a `transition_id` would need to provide (ADR Invariant 12: monotonic, never reused, one per transition). This requires `legal_hold_event_key`/`get_legal_hold_event`/`write_hold_event` to accept `hold_version` as an additional parameter — a signature change, not a behavior change to the conditional-write semantics themselves. See ADR Invariant 25.

#### 19.5.2 Marker Version/Generation, and Proof That `PLACE`/`RELEASE` Cannot Collide

**Corrected identity model (Product Strategy — required correction; the prior revision's model is not accepted): `hold_id` identifies one legal-hold episode, from its `PLACE` through its eventual `RELEASE`, and is held constant across that pair — it is never regenerated per transition.** `evidence_retention/identity.py::generate_hold_id()` (already merged) is a pure `uuid.uuid4().hex`-based generator with no episode/transition semantics of its own; the previously-open question was how `RetentionService` calls it. **This design's answer, corrected: `RetentionService` generates a `hold_id` once, at the moment a genuinely new episode begins (§19.2 step 3's "no record exists, or status = RELEASED" case), and reuses that same `hold_id` for the paired `RELEASE` that eventually closes the episode.** A later, independent episode on the same audit identity may receive a new `hold_id` — this document does not need to resolve whether it must, since (as proven below) non-collision never depends on it either way.

**Non-collision is proved by `hold_version` alone, not by `hold_id` changing:** ADR Invariant 12 requires `hold_version` to increment by exactly `1` on **every** write to `LegalHold` — every `PLACE` and every `RELEASE`, across the entire lifetime of a given `(client_id, audit_id)` identity, with no reset and no reuse. Because this is a single monotonic counter on one record, no two transitions of the same audit identity can ever share a `hold_version` value — whether the two transitions belong to the same episode (a `PLACE` and its paired `RELEASE`, sharing one `hold_id`) or to different episodes (`PLACE`→`RELEASE`→`PLACE`, spanning one or two `hold_id` values depending on how the next episode's `hold_id` is assigned). `{transition}` (`PLACE`/`RELEASE`) is included in the key as a self-describing, human-readable redundancy, not as a second load-bearing uniqueness source — since `hold_version` alone already disambiguates every transition, an orphaned marker remains directly interpretable without cross-referencing `LegalHoldEvent`, but the key's non-collision guarantee rests on `hold_version` alone. `{hold_id}` in the key path groups a `PLACE`/`RELEASE` pair for traceability (§19.5.1) and plays no role in preventing collision.

**Required consequence for `LegalHoldEvent` (already-merged code, flagged here, fixed in Legal-Hold Correction B1, not in this document):** because `HoldRepository`'s existing `LegalHoldEvent` SK is keyed by `hold_id` alone, and `hold_id` is now held constant across a `PLACE`/`RELEASE` pair, that SK must gain `hold_version` as its own per-transition discriminator (§19.5.1) — otherwise the identical defect this correction closes for the S3 marker would remain open on the DynamoDB side, where it is in fact the more severe of the two (an unconditional write failure on every release, not merely a theoretical race).

**Given the corrected model, the marker key's non-collision holds as follows:**

1. **`PLACE` and `RELEASE` cannot collide.** Every `upsert_hold` call increments `hold_version` by exactly 1, with no exception (ADR Invariant 12) — a `PLACE` and its paired `RELEASE` are two separate `upsert_hold` calls, hence two different `hold_version` values (`N` and `N+1`) by construction. This holds regardless of `hold_id` (constant across the pair by the corrected model) — `hold_version` alone excludes collision.
2. **Repeated invocation of the *same* transition is idempotent.** Per §19.2 step 4 (unchanged): a resumed `PLACE` attempt for an already-`ACTIVE` hold does not call `upsert_hold` again — it reads the *current* `LegalHold` record, which already durably carries the `hold_id` and `hold_version` `upsert_hold`'s original (possibly-incomplete) commit wrote in step 1 of the *same* transition attempt. The resumed attempt recomputes its marker key from those *same* values, producing an *identical* key to the original attempt's — so `If-None-Match: *` correctly reports "already exists," and §19.5.7's precondition-failure branch correctly reads back the earlier attempt's own marker. **Refined by §19.5.3 step 2's `marker_status` check: if the earlier attempt had already reached `CONFIRMED` before being interrupted, the resumed attempt does not reach the `PutObject` call at all — it reuses the durably-recorded timestamp directly from `LegalHoldEvent`. This is a stronger, S3-existence-independent form of the same idempotency property, not a contradiction of it; the `If-None-Match`/precondition-failure path described above remains exactly correct for the narrower case where the earlier attempt was interrupted *before* reaching `CONFIRMED` (marker written but not yet read back, or genuinely concurrent with another first attempt).**
3. **Different hold generations cannot alias.** A `PLACE`→`RELEASE`→`PLACE` cycle is three separate `upsert_hold` calls: `hold_version = N, N+1, N+2` — three structurally distinct values by construction of Invariant 12 alone, regardless of how many `hold_id` values are involved (one for the first episode's `PLACE`/`RELEASE` pair, a second, independently-generated one for the next episode's `PLACE`, per the corrected identity model above). No aliasing is possible between any two generations, adjacent or not.
4. **Retries discover the correct existing marker.** Identical mechanism to property 2: a retry of an *incomplete* transition re-reads the current `LegalHold` (which already durably recorded that transition's `hold_id`/`hold_version` before the marker step even began, per §19.5.3 step 1 preceding step 2) and recomputes the identical key every time — subject to the same `marker_status` refinement noted under property 2 above.
5. **Reconciliation always references the marker for the exact transition being completed.** The reconciliation pass, run within a specific `place`/`release` invocation, always computes its own key from *that invocation's own* `hold_id`/`hold_version`/transition — the same values just used to establish the marker earlier in the *same* sequence (§19.5.3). There is no code path by which it could read a different transition's key, because the key is deterministically derived from the current invocation's own state, never looked up by an independent means that could resolve elsewhere.
6. **Stale markers cannot be mistaken for the current transition.** An older transition's marker key differs from any later transition's key in `hold_version`-`transition` (since `hold_version` only increases and is never reused, Invariant 12) — structurally invisible to any current-transition key computation, regardless of whether `hold_id` also differs. It remains exactly the harmless orphan §19.5.7 already describes, with a uniqueness guarantee spanning the full generation history, not merely adjacent transitions.

The marker's own JSON content additionally carries `hold_id` and `hold_version` redundantly (§19.5.1), so the marker is self-describing and cross-referenceable from either identifier even without parsing its key — consistent with this codebase's existing pattern of carrying redundant identity fields for traceability (e.g., Phase 7 certificate artifacts carrying both `certjob_id` and the full audit-identity tuple).

#### 19.5.3 Creation and Finalization Ordering

Applies identically to both `PLACE` and `RELEASE` (§19.5's whole point is that this must be symmetric — see the release-side correction below and the revised §19.3):

1. `HoldRepository.upsert_hold` commits (the DynamoDB `LegalHold` write — `status`/`hold_version`/`sweep_status=PENDING` — unchanged from §19.1/§19.2/§19.3). This remains the authoritative moment for DynamoDB-side hold state and for the `TransactWriteItems` mechanism (§19.4); the marker does not replace or duplicate that authority.
2. **Before attempting any S3 operation for this transition, check the current transition's own `LegalHoldEvent.marker_status`** (durably written by step 1's commit as `PENDING`, or already `CONFIRMED`/`FAILED` from an earlier attempt of this exact transition). **Correction (real, concrete defect found on session-continuation verification, not previously specified): the original text of this step attempted the conditional `PutObject` unconditionally on every invocation, including a resumed one.** That is unsafe once the marker object no longer exists in S3 — whether disposed per its purpose-limited retention (§19.5.8) or aged out early per that section's already-flagged residual — because the conditional write would then succeed as a *fresh* first write (the key is genuinely absent), producing a new, later `marker_confirmed_last_modified` and silently overwriting the historically accurate confirmation already durably recorded on this same `LegalHoldEvent`. Checking DynamoDB's own durable record before ever touching S3 closes this regardless of the marker object's continued physical existence (ADR Invariant 24).
   - **If `marker_status` already reads `CONFIRMED`:** reuse the durably-recorded `marker_confirmed_last_modified` directly. Skip the conditional `PutObject` and the `HeadObject` read-back (step 3) entirely — proceed straight to step 4.
   - **If `marker_status` reads `PENDING` or `FAILED`:** write the marker object (§19.5.1) to its key via a **conditional `PutObject` (`If-None-Match: *`), never a plain unconditional write** (§19.5.7 — this is the atomic, first-write-wins mechanism that closes the orphan-marker TOCTOU, and remains the operative mechanism for genuinely concurrent overlapping first attempts, both observing `PENDING` — see §19.5.10 test 6). `marker_status` remains/becomes `PENDING` before the write, and remains `PENDING` if the write fails (§19.5.6); proceed to step 3.
3. **Immediately after** a step-2 write attempt resolves (whether this attempt's own conditional `PutObject` succeeded, or it failed with a precondition failure indicating an existing marker to reuse — §19.5.7), perform a `HeadObject` on the key and record its returned `LastModified` as `marker_confirmed_last_modified`; `marker_status → CONFIRMED`. If this read-back fails, treat it as a marker-establishment failure (§19.5.6) — an unconfirmed marker cannot anchor a reconciliation boundary.
4. Only **after** `marker_status = CONFIRMED` does `sweep_status → IN_PROGRESS` and the primary sweep begin (`CustodySweepClient.remove_ttl_disposal_at`/`retag_s3_versions(legal_hold=True)` for `PLACE`; `restore_ttl_disposal_at`/`retag_s3_versions(legal_hold=False)` for `RELEASE` — both unchanged).
5. The reconciliation pass (§19.5.5) runs after the primary sweep, using `marker_confirmed_last_modified` (not any Lambda wall-clock value) as its primary boundary.
6. `sweep_status → COMPLETE` only once the marker is confirmed **and** the primary sweep **and** the reconciliation pass have all completed without error (§19.6, updated).

#### 19.5.4 Writer Behavior — What Changes, and the Related Fix This Redesign Surfaced

**No change to the per-object write-time tagging decision itself:** every Category 1 S3 write (items 3, 16, 21, 27) still reads `HoldRepository.get_legal_hold(client_id, audit_id)` and tags `rcp-legal-hold` accordingly, exactly as the prior revision specified. **The marker is consulted by the reconciliation pass, not by each individual object write** — this is a deliberate design choice, stated explicitly because Product Strategy's review asked precisely what reads the S3 clock domain: DynamoDB's `LegalHold` record remains the sole source of truth for *what hold state currently applies*; the marker's sole purpose is to give the *reconciliation pass* a same-clock-domain reference point for *when* the transition became effective, so that pass's time-based filtering isn't comparing across two independently-clocked systems. Folding a marker read into every individual writer's own hot path would add S3 round-trips to the evidence-write critical path for no corresponding correctness benefit, since DynamoDB is already authoritative for the state decision itself.

**A related, independently-identified fix this redesign surfaced, not explicitly requested but closing a real gap:** the writer's `HoldRepository.get_legal_hold()` `GetItem` call, as specified in the prior revision, did not specify `ConsistentRead`. DynamoDB `GetItem` defaults to eventually consistent reads; a writer's read could, in principle, fail to observe a very recently committed `upsert_hold` write. For the DynamoDB write path (§19.4), this is harmless — `TransactWriteItems`' `ConditionCheck` re-verifies the *actual current* `hold_version` at commit time regardless of how stale the preceding read was, so a stale read only costs an extra retry, never an incorrect commit. **Precisely because this is already harmless there, `ConsistentRead` is not required on the DynamoDB write path's pre-transaction read — requiring it there would double read-capacity cost on every Category 1/2 DynamoDB write, including Phase 1's critical path, for a benefit this reasoning itself shows is not a correctness requirement in that case (architecture + security review correction: an earlier revision over-scoped this fix to both paths).** For the **S3 write path, there is no equivalent transactional backstop** — a stale eventually-consistent read would silently produce an incorrect tag with nothing to catch it. **Fix, scoped to the S3 write paths only (items 3, 16, 21, 27): every `HoldRepository.get_legal_hold()` call made as part of these writes' custody-field computation must use `ConsistentRead: true`.** This is a standard, already-available DynamoDB primitive (2x read-capacity cost on these reads specifically, the same cost-tradeoff shape as `TransactWriteItems`' 2x write cost, §12), not new infrastructure. This closes a distinct staleness source (DynamoDB's own consistency model) from the one the marker closes (cross-service clock skew) — both are now addressed, for different reasons, and only where each is actually needed.

#### 19.5.5 Reconciliation Boundary — Marker-Primary, Buffer-Secondary

Filter: `LastModified >= (marker_confirmed_last_modified - 5s)` **and** current `rcp-legal-hold` tag inconsistent with the transition just completed (`!= true` for a `PLACE` reconciliation pass; `== true` for a `RELEASE` reconciliation pass — see §19.3 step 6 for the release-direction application) — re-tag those. Mechanically this reuses `CustodySweepClient`'s existing `_list_object_versions` helper (no new S3 API surface for the reconciliation pass itself; `ListObjectVersions` responses already include `LastModified`).

**Why this is a materially stronger closure than the prior wall-clock-only design, precisely characterized rather than overclaimed (correction: "eliminates cross-service clock skew entirely" overstated the prior wording of this claim — softened below):** the marker and every evidence object are now timestamped by the *same* clock authority (S3's own internal infrastructure), eliminating cross-service (Lambda-vs-S3) clock skew — the significant, open-ended, AWS-undocumented quantity that was the prior design's primary exposure — as a source of error. This does not formally rule out sub-clock-domain discrepancy *within* S3's own distributed internal infrastructure (no SLA is published for that either, though it is expected to be negligible compared to the Lambda-vs-S3 skew this mechanism removes). What remains is a much narrower, better-characterized quantity: the latency of the marker's own `PutObject` + `HeadObject` round trip (typically tens to low hundreds of milliseconds for a single small S3 object, now additionally bounded by the wall-clock cap in §19.5.6), plus the ~2-second worst-case second-granularity truncation term already reasoned in the prior revision (still real, since `LastModified` truncation applies regardless of which clock produced the underlying instant). The marker's `LastModified` therefore approximates the true hold-commit instant to within *that write's own latency*, not to within an unbounded cross-service skew. **The 5-second buffer is retained unchanged in value, now serving a narrower, smaller-magnitude purpose (marker-write latency + truncation) than before (open-ended clock skew + truncation) — it was already conservative for the harder problem, so it remains comfortably conservative for the easier one.**

**Honest characterization of remaining rigor (per this project's established standard against overclaiming):** this is now bounded by a *characterizable, single-operation latency window* rather than an *open-ended, cross-service skew term with no documented bound* — a substantially stronger argument than the prior revision's, and one a reviewer can evaluate against a concrete, boundable quantity (S3 API latency) rather than an unknowable one (inter-service clock drift). It is not, however, identical in kind to the DynamoDB leg's guarantee: `TransactWriteItems` has *zero* timing dependency — the ConditionCheck is evaluated atomically against the transaction's own commit, with no window of any size, however small. The marker mechanism still has a window — just a much smaller, better-understood one (single S3 round-trip latency, not cross-service clock drift). Stated plainly: **the S3 leg is now very tightly, characterizably bounded; the DynamoDB leg is provably exact.** These are both strong guarantees, but not identical ones, and this document does not claim otherwise.

#### 19.5.6 Marker Write Failure and Retry

If the marker `PutObject` fails: retry up to 3 attempts (consistent with §19.4's retry count elsewhere in this design), matching the existing S3 error-handling pattern (`StorageError` on exhaustion) already used by `S3StorageClient`/`CustodySweepClient`. If the `HeadObject` read-back fails after a successful `PutObject`: retry the `HeadObject` alone a few times (S3 reads are strongly consistent, so this should succeed near-immediately; a repeated failure indicates an infrastructure problem, not a consistency-timing issue).

**Correction (architecture + security review): a retry-count cap alone is insufficient — the sequence must also be capped by total wall-clock time, not attempts alone.** The 5-second reconciliation buffer (§19.5.5) is sized against *typical* single-attempt marker-write latency. Nothing previously bounded how long establishing the marker could take if multiple retries were each individually slow-but-not-failing (e.g., three attempts each taking 2–3 seconds before eventually succeeding) — the true gap between the hold's DynamoDB commit and the marker's eventual confirmation could then exceed the margin the buffer was reasoned against, silently invalidating §19.5.5's sizing assumption. **Fix: marker establishment (the full sequence of `PutObject`/`HeadObject` attempts, across all retries, for both `PLACE` and `RELEASE`) is additionally capped at a total wall-clock budget of 5 seconds — the same reasoned value already established for the reconciliation buffer, reused rather than independently justified a second time, since the relationship is direct: if establishing the marker itself consumes as much time as the buffer's own margin, the buffer's sizing assumption (a typical, fast marker write) no longer holds, and continuing would silently accept a marker that can no longer be trusted to anchor the boundary within its stated margin.** The wall-clock cap and the retry-count cap are independent triggers — either one being exceeded ends the attempt sequence; retries are abandoned early if the wall-clock budget is exhausted first, even if attempts remain.

**On exhaustion of either the retry-count cap or the wall-clock cap: fail the entire hold placement/release operation closed.** `marker_status → FAILED` is recorded on the current transition's `LegalHoldEvent` at this point (the one write of this value anywhere in this design — closing a gap noted on targeted re-review: §19.5.3 step 2 branches on `FAILED` as a real, reachable state, so this is where it becomes reachable). `sweep_status → FAILED` (never `IN_PROGRESS` with an unconfirmed marker — an unconfirmed marker cannot anchor a reconciliation boundary, so proceeding to the sweep without one would silently regress to no rigorous S3-side protection at all). `RetentionService` surfaces a distinct error (`HOLD_MARKER_ESTABLISHMENT_FAILED`, §19.14) to the operator. The operator re-invokes `rcp retention hold place`/`release`, which re-attempts the full sequence including re-establishing the marker (§19.5.7 covers what happens to the marker from the failed attempt).

#### 19.5.7 Orphan-Marker Recovery

A marker left behind by an interrupted sweep (the marker itself was written and confirmed, but the process crashed before `sweep_status → COMPLETE`) is **harmless to leave in place beyond its purpose-limited lifetime (§19.5.8) — no dedicated interruption-specific cleanup is proposed beyond the standard disposal mechanism.** Reasoning: each marker is uniquely keyed by *both* `hold_id` and `{hold_version}-{transition}` (§19.5.1/§19.5.2), neither of which is ever reused across transitions, so an orphaned marker can never be mistaken for, or interfere with, a later transition's marker.

**Correction (architecture + security review): the original design for detecting and reusing an existing marker on resume — a `HeadObject` check followed by a conditional `PutObject` only if nothing was found — is an unconditioned check-then-write, and this design does not accept that pattern anywhere else it applies (§19.4's `TransactWriteItems`, §19.5.4's `ConsistentRead`). Two overlapping `rcp retention hold place`/`release` invocations for the same transition (an operator or a retry-wrapper re-invoking before confirming a prior attempt actually failed) could both `HeadObject` and observe nothing, both `PutObject`, and the second would silently overwrite the first marker — advancing its timestamp and narrowing the reconciliation window, exactly the failure mode this section itself warns against. The fix is symmetric with the rest of this design: make marker creation atomically first-write-wins, not check-then-write.**

**Fix — atomic conditional marker write:** the marker write is always attempted as `PutObject` with `If-None-Match: *` (an S3-native conditional-write precondition, generally available since August 2024) — never preceded by a `HeadObject` existence check. Two possible outcomes, both race-safe by construction of S3's own conditional-write guarantee:
- **The conditional `PutObject` succeeds:** this attempt is the first writer for this exact `(hold_id, hold_version, transition)` marker. Proceed to the `HeadObject` read-back exactly as §19.5.3 already specifies, recording `marker_confirmed_last_modified` from this write.
- **The conditional `PutObject` fails with a precondition-failure response (`412 Precondition Failed`, S3's documented response when `If-None-Match: *` finds the key already exists):** a marker for this exact `(hold_id, hold_version, transition)` already exists — either from an earlier attempt of the *same* invocation being resumed, or from a genuinely concurrent overlapping invocation that won the race. Read the *existing* marker's `LastModified` via `HeadObject` and reuse it as `marker_confirmed_last_modified`, exactly as the original design intended — but now this reuse is a direct reaction to an atomically-proven "already exists" outcome, never a racy prior check that could itself be stale by the time the write happens.

This closes the TOCTOU the same way every other race in this design is closed — via an atomic, S3/DynamoDB-native primitive rather than a plain read-then-act sequence — rather than leaving this one component on a structurally weaker pattern than the rest of the mechanism.

#### 19.5.8 Marker Retention and Disposal — Purpose-Limited, Not Indefinite

**Correction (Product Strategy — required, explicit instruction, not a suggestion): "indefinite retention by default" was wrong even for Category 4 governance metadata. The locked Evidence Retention and Disposal Policy applies purpose limitation regardless of which S3 prefix an object lives under — being outside the four evidence-class prefixes is not, by itself, a basis for indefinite retention.** The Category 4 precedent this design previously leaned on (`LegalHoldEvent`/`DisposalRecord` permanently retained, ADR Invariant 8) is *not* overturned by this correction — those two record types are the durable, compliance-facing audit trail, and their permanent retention remains correct — but the marker is not that record; it is a narrower, purely *operational* bootstrapping artifact, and its retention question must be evaluated on its own governance purpose, not inherited wholesale from a different record type in the same broad category. **No duration value is introduced by this correction, consistent with every other custody-period value in this workstream remaining a deferred, externally-supplied parameter.**

**Defined retention end condition (the marker's governance purpose, stated precisely, not "forever"):** a marker exists to serve exactly five purposes — supporting transition idempotency (§19.5.2 properties 2/4), reconciliation/retry (§19.5.5), failure recovery (§19.6), legal-hold verification during the transition's own execution window, and durable disposition traceability. **The first four of these five purposes are fully and permanently served the moment `sweep_status → COMPLETE` is durably recorded for that marker's own transition** (§19.5.3 step 6, §19.6) — after that point, nothing in this design ever reads that marker again (§19.5.2 property 5: a later transition always computes and reads only its *own* marker, never an earlier one). **The fifth purpose, durable disposition traceability, does not require the marker *object* itself to survive** — it requires the *fact* of the marker's existence, key, and confirmed timestamp to survive, which is satisfied independently (see below). Once `sweep_status = COMPLETE`, the marker object has no further governance purpose and becomes eligible for disposal.

**Disposal mechanism specified (mechanism, not schedule — the actual duration is deferred, matching the custody-period pattern):** the `retention-markers/` prefix receives its own S3 `LifecycleConfiguration` rule, structurally simpler than the four evidence-class rules (§18.2, ADR Decision 1/2) because markers are never subject to legal-hold exemption themselves (a marker is never itself "held" — it is metadata *about* a hold) — no tag-filter condition is needed, only a plain age-based `Expiration.Days` rule scoped to the prefix. This reuses the *already-established* mechanism (S3 Lifecycle rules, already built in A1.2) rather than introducing new infrastructure, and follows the identical fail-closed deployment pattern already governing the four evidence-class rules: the rule's `Days` value is sourced from a new `custom.custodyPeriodDays.retention_marker.${stage}` parameter, left unset by this design, with deployment gated on Product Strategy supplying it — exactly ADR Decision 5's existing pattern, extended to a fifth, simpler rule. **One honestly-stated residual, symmetric with an already-accepted characteristic of this entire mechanism, not a new risk:** an age-based Lifecycle rule cannot condition on `sweep_status`; if a transition's `sweep_status` never reaches `COMPLETE` (a permanently abandoned or bugged transition), its marker could still be disposed once it ages past the configured duration, potentially removing a marker a future resume attempt might have used. This is not worse than the existing, accepted characteristic of the primary custody-period mechanism itself (age-based disposal has never claimed awareness of every possible future consumer's need for a given object) and is noted here for completeness, not escalated as a new blocking concern.

**Preservation of durable transition history — confirmed already sufficient, nothing missing:** `LegalHoldEvent` (permanently retained, Category 4, ADR Invariant 8, unaffected by this correction) already durably records everything material about a transition and its marker before the marker object could ever be disposed: `action` (`PLACE`/`RELEASE`), `timestamp`, `s3_versions_retagged_count`, `dynamodb_items_updated_count`, and — per §19.5.1's schema extension — `marker_s3_key`, `marker_status`, `marker_confirmed_last_modified`. All of this is written durably to `LegalHoldEvent` *before or during* the transition's own execution (§19.5.3), independent of whatever later happens to the marker object itself. Disposing the marker object once its operational purpose is served therefore loses no compliance-facing information — the fact that the transition happened, when, its outcome, and the marker's own confirmed timestamp all remain permanently queryable via `LegalHoldEvent` alone. No additional field or record is required to close this gap.

**Relationship to the still-open `DisposalRecord` retention question (§16) — related, but not the same question, and not silently resolved here:** §16 already flags an open question about whether `DisposalRecord` itself should be time-bounded by an independent compliance-record retention policy or retained permanently — architecturally the same *shape* of question (how long should a governance-metadata artifact live), but Product Strategy's correction here is scoped specifically to canary markers, not to `DisposalRecord`. This document does not extend today's marker-retention decision to `DisposalRecord` by implication; that remains the separate, still-open item §16 already tracks, to be resolved on its own if and when Product Strategy addresses it.

#### 19.5.9 IAM and Component Ownership

`CustodySweepClient`'s existing structural allowlist has **no** `put_object`/`delete_object` capability, by design (§18.3/§5.2: "this class cannot write or delete evidence content"). **The marker write is deliberately *not* added to `CustodySweepClient`, and that invariant is not touched, re-scoped, or re-justified — it is fully preserved by keeping this responsibility elsewhere.** `RetentionService` (which already orchestrates `HoldRepository` and `CustodySweepClient` calls) is the component that performs the marker write, via a narrow, dedicated helper distinct from both existing classes. This is the cleanest resolution of "does writing a marker violate `CustodySweepClient`'s invariant" — it does not, because `CustodySweepClient` never gains the capability at all; a different, already-existing orchestration component does, for a purpose (governance bookkeeping, not evidence content) that was never what that invariant was protecting against in the first place.

**Correction (architecture + security review): the marker-write helper was the only write-capable component in this entire design described solely by IAM "logical scope," with no code-level structural guard — inconsistent with the established pattern every other write-capable component here follows (`_assert_retention_sk`, `_assert_disposal_sk`, `_assert_custody_field_only_update`).** Fixed: the marker-write helper calls a new `_assert_marker_key(key, client_id, audit_id, hold_id, hold_version, transition)` before every conditional `PutObject` (§19.5.7) and before every `HeadObject`, asserting the target key is *exactly* `f"retention-markers/{client_id}/{audit_id}/{hold_id}/{hold_version}-{transition}.marker"` — the full reconstructed key for the specific transition the caller is attempting, not a prefix or namespace-membership check the way `_assert_retention_sk`/`_assert_disposal_sk` are (those only need to confirm broad namespace membership across many possible items; the marker's full identity is always known at each call site, so exact-match validation is both possible and the correct level of rigor here). Raises `AssertionError` on any mismatch — the same "programming-error guard, not a user-facing validation" characterization already used for the other three guards, updated to validate all five components (`client_id`, `audit_id`, `hold_id`, `hold_version`, `transition`), not the four the prior key format had. This closes the same class of gap those guards close for their own namespaces: a future code change to this helper cannot accidentally construct a write outside the `retention-markers/` prefix, under a mismatched identity tuple, or — newly relevant under the corrected key format — against the *wrong transition's* own marker, without an immediate, loud failure rather than a silent misdirected write.

IAM (logical scope, subject to the same §12 correction as every other component in this design — not currently enforced by a dedicated role under this codebase's shared-role architecture): `s3:PutObject`/`s3:HeadObject`/`s3:GetObject` scoped strictly to the `retention-markers/` prefix, never any evidence-class prefix. Since `RetentionService` is not Lambda-resident today (it runs wherever the `rcp retention` CLI commands run), this action lands on whatever AWS credentials that operator session already holds — the same caveat already stated for `HoldRepository`/`CustodySweepClient` in §12, not a new gap this mechanism introduces. A forged/fabricated marker is not a new attack surface beyond the existing operator-trust model: an operator with the authority to invoke `rcp retention hold place` already has the authority to place or release holds outright, so the ability to also influence a marker's content is bounded by the same trust boundary as the rest of this operator-only system.

#### 19.5.10 Tests Proving the Marker Closes the Transition Boundary

Outlined here; folded into §19.11's full outline: (1) marker correctly anchors reconciliation for an object genuinely in-flight at the transition boundary, for both `PLACE` and `RELEASE`; (2) marker write/read-back failure triggers fail-closed `sweep_status=FAILED` and a distinguishable error, never a silent fallback to the old wall-clock comparison; (3) orphan-marker reuse on resumed sweep does not advance the reconciliation boundary; (4) two independent reconciliation runs against the same marker are idempotent; (5) the 5-second buffer's defense-in-depth role is verified independently of the marker (i.e., a test asserting the buffer still catches a case where the marker's own confirmation is delayed by a simulated latency spike within the buffer's margin); (6) **(architecture + security review addition) two genuinely overlapping marker-establishment attempts for the same `hold_id`** (simulated concurrent `rcp retention hold place`/`release` invocations) — assert exactly one conditional `PutObject` succeeds, the other receives a precondition-failure response and falls back to reading the winner's marker, and neither invocation ever overwrites the other's confirmed `marker_confirmed_last_modified`; (7) **(architecture + security review addition) marker establishment exceeding the wall-clock cap** (simulated slow-but-eventually-successful retries whose cumulative latency exceeds 5 seconds) — assert the sequence fails closed on the wall-clock cap even with retry attempts remaining, never allowing a marker confirmed after excessive cumulative latency to anchor a reconciliation boundary; (8) **(architecture + security review addition) the marker-write structural guard** (`_assert_marker_key`) — a negative test asserting it raises on any key not matching the exact `retention-markers/{client_id}/{audit_id}/{hold_id}/{hold_version}-{transition}.marker` for the supplied identity tuple and transition, mirroring the existing negative-test pattern already established for `_assert_retention_sk`/`_assert_disposal_sk`/`_assert_custody_field_only_update` — including a case asserting a `PLACE` invocation cannot construct or accept a key bearing a `RELEASE` suffix (or vice versa) even if the rest of the tuple matches.

### 19.6 Sweep and Failure-Recovery Semantics

**Initial sweep behavior:** unchanged existing enumeration logic (`Query` with `LastEvaluatedKey` pagination for DynamoDB; `ListObjectVersions` with `NextKeyMarker`/`NextVersionIdMarker` pagination for S3) — now explicitly scoped, per this amendment, to "everything that exists as of this query/list call," paired with the new `sweep_status` tracking (§19.1) rather than assumed complete the instant `status` flips to `ACTIVE`.

**Retry/pagination:** unchanged — `CustodySweepClient`'s existing pagination is already correct and requires no change.

**Completion recording:** `sweep_status → COMPLETE` only after the marker is confirmed (§19.5.3) **and** the primary sweep (DynamoDB removal/restoration + S3 retagging) **and** the reconciliation pass **all** finish without error — this now applies identically to both `PLACE` and `RELEASE` episodes (§19.3's correction retracts the prior claim that release's sweep needed no reconciliation step). Item/version counts are recorded on the `LegalHoldEvent` for the current episode.

**Failure recovery:** if the marker write, the sweep, or the reconciliation pass fails partway (a transient DynamoDB/S3 error mid-enumeration, or a marker-establishment failure per §19.5.6), `sweep_status` remains `IN_PROGRESS` (or transitions to `FAILED` for a detected non-retriable error, e.g., a permissions failure that will not resolve on retry). `rcp retention hold place`/`rcp retention hold release` must remain safely re-invocable to resume — this is the existing §10.5 idempotency property, unchanged in kind, extended in scope to also cover the marker and the reconciliation step. Every one of `CustodySweepClient`'s existing operations (`remove_ttl_disposal_at`, `restore_ttl_disposal_at`, `retag_s3_versions`) is already naturally idempotent (skips items/versions that no longer carry the field/tag it's looking for), so resumption is simply "call it again" — no new idempotency logic is required in `CustodySweepClient` itself; the marker's own idempotent-reuse behavior is specified in §19.5.7, and orchestration-level `sweep_status` bookkeeping remains `RetentionService`'s responsibility.

**Reconciliation for records written concurrently with the sweep — DynamoDB side needs none beyond §19.4:** because every DynamoDB write after the hold's commit is already correctly protected at write time (§19.4), the sweep's enumeration incidentally revisiting such a record during its own `Query` is a harmless no-op (`remove_ttl_disposal_at` skips items that don't carry `ttl_disposal_at`, which a correctly-created held record won't). The DynamoDB and S3 mechanisms are not symmetric here only because DynamoDB has the transactional primitive that makes write-time correctness airtight and S3 does not (§19.5's reconciliation pass exists specifically to cover that asymmetry).

**How an incomplete sweep prevents a false "hold fully enforced" claim:** `sweep_status` is the queryable answer. `rcp retention hold status` (existing command, §8) must report both `status` and `sweep_status` in its response — this is a corrective addition to that command's existing response body, not a new command. **A caller must never treat `status = ACTIVE` alone as proof that every pre-existing record/object is protected — only `status = ACTIVE AND sweep_status = COMPLETE` is that proof.** This distinction did not exist before this amendment (the original design had no field distinguishing "hold placed" from "hold's sweep finished") and is the direct, queryable answer to Product Strategy's concern about a false "fully enforced" claim.

### 19.9 Amendment to §18.4's Regeneration Rule

§18.4 (rules 1–3) required `ttl_disposal_at` on regeneration to be set or omitted based on the audit identity's legal-hold status "read fresh at regeneration time," but specified only a plain read, not a mechanism to detect the hold state changing between that read and the regeneration write's own commit — the identical race class this section closes for CREATE paths, previously left open for regeneration paths too. **§18.4 rules 1–2 are amended: the hold-status read and the regeneration write must be coordinated through the same `TransactWriteItems` mechanism specified in §19.4** — a `ConditionCheck` against `LegalHold.hold_version`, paired with the regeneration write (full-overwrite for Phase 5/7, the custody-field portion of the partial `SET` for Phase 6) in one atomic transaction. §18.4 rule 3 (Phase 6's partial-update path must explicitly include both fields on every regen call) is unchanged in substance, now understood to mean "include them via the same conditioned transaction," not a plain conditional `UpdateItem`. No other part of §18.4 (rule 4's "no special handling for prior/superseded artifacts," rule 5's retry-idempotency reasoning) requires amendment — both already hold independent of this correction.

### 19.11 Concurrency-Focused QA Strategy — Outline

For the next stage to draft the full strategy against. Test categories, not exhaustive test cases:

1. **Placement racing DynamoDB CREATE:** a governed-record CREATE and a concurrent `PLACE` racing the same audit identity — assert the final committed state always resolves to the invariant (either the CREATE completes with `ttl_disposal_at` correctly omitted because it observed the new hold, or it retries and then observes it, or it fails closed on retry exhaustion — never commits `ttl_disposal_at` on a now-held audit).
2. **Release racing DynamoDB CREATE:** the symmetric case for `RELEASE` — confirm `TransactWriteItems`' `ConditionCheck` closes this direction with the same zero-residual-window guarantee as category 1 (§19.3's "does the DynamoDB leg need the same fix" analysis).
3. **Placement racing S3 creation:** an S3 write whose own hold-state read happens before `PLACE` commits, whose `PutObject` completes after — assert the marker-anchored reconciliation pass (§19.5.5) catches and corrects it to `rcp-legal-hold=true`, and that a second reconciliation run against the same marker is a no-op.
4. **Release racing S3 creation (the new required correction, §19.3):** an S3 write whose own hold-state read observes `ACTIVE` before `RELEASE` commits, whose `PutObject` completes after the release-sweep has already run, carrying a stale `rcp-legal-hold=true` — assert the release-side reconciliation pass (§19.3 step 6) catches and corrects it to `false`. This is the scenario Product Strategy identified as previously unaddressed; it must have dedicated, explicit test coverage, not be assumed covered by category 3's symmetry.
5. **Stale pre-transition observations, both directions:** parameterize categories 3 and 4 across a range of "how stale" the writer's observation was (read immediately before commit vs. read well before commit, with realistic intervening processing delay) — assert correctness holds across the range, not only at the single narrowest-margin case.
6. **Marker creation/finalization failure:** the marker's `PutObject` or `HeadObject` read-back fails on every retry attempt (§19.5.6) — assert the entire placement/release operation fails closed (`sweep_status → FAILED`, `HOLD_MARKER_ESTABLISHMENT_FAILED` raised, §19.15), never silently proceeding to the sweep with an unconfirmed boundary.
7. **Reconciliation interruption and retry:** interrupt the reconciliation pass mid-enumeration (simulated failure) after the marker was already confirmed — assert `sweep_status` remains `IN_PROGRESS`/`FAILED` appropriately, and that re-invocation resumes using the *existing* confirmed marker (§19.5.7 — does not re-write and thereby advance the boundary) and reaches `COMPLETE` without double-counting or erroring on already-corrected items.
8. **Clock disagreement — now a defense-in-depth check, not a primary-correctness check:** with the marker as the primary boundary (§19.5.5), this category's scope narrows to verifying the 5-second buffer still provides margin around marker-write latency specifically (a simulated delay in the marker's own confirmation, not an open-ended Lambda-vs-S3 skew scenario, which is no longer the mechanism's primary concern). Retained because the buffer is still real, default behavior (§19.5.5), not because it is still the primary correctness argument.
9. **Regeneration-path hold-awareness (Phase 5/6/7)** under the same race conditions as categories 1–2, per the §19.9 amendment.
10. **Bounded retry exhaustion, both codes:** force repeated `ConditionCheck` failures (`HOLD_STATE_CONCURRENCY_EXCEEDED`, §19.4) and repeated marker-establishment failures (`HOLD_MARKER_ESTABLISHMENT_FAILED`, §19.5.6) independently — assert each is raised (never a silent unconditioned write, never a silent proceed-without-marker) after its own bounded retry count, and that the two codes are never confused with each other or with an unrelated AWS throttling error (§19.15's distinguishability table).
11. **Absence of partial-success claims:** for every failure category above, assert no caller ever observes a governed record/object reported as successfully persisted when the underlying write did not actually commit — the direct test of §19.14's "no partial governed record may ever be represented as successfully persisted."
12. **`sweep_status` accuracy under partial-sweep conditions:** assert `rcp retention hold status` never reports data consistent with "fully enforced" while `sweep_status != COMPLETE`, for both `PLACE` and `RELEASE` episodes.
13. **Cross-store independent correctness:** a `RunMetadata`/raw-evidence pair created with the DynamoDB and S3 writes deliberately observing the hold-state transition at different moments (test-controlled) — assert each store independently resolves correctly per its own mechanism, with no assumption of cross-store atomicity.
14. **Regression:** the unheld case (no hold ever placed on the audit) behaves identically to pre-amendment behavior for every write path in §19.7's matrix.

**Marker-identity and key-collision scenarios (Product Strategy addition, §19.5.1/§19.5.2):**

15. **`PLACE` followed by `RELEASE` on the same hold:** run a full episode end to end — assert the two transitions share the **same** `hold_id` (corrected identity model, §19.5.2) and produce two structurally distinct marker keys differing only in `hold_version`-`transition` (`1-PLACE` vs. `2-RELEASE`), both markers independently confirmed and readable, and that `RELEASE`'s marker write never collides with, overwrites, or is rejected because of `PLACE`'s already-existing marker. Also assert the corresponding `LegalHoldEvent` writes (now keyed by `hold_id`+`hold_version`, §19.5.1's required consequence) do not collide either — the direct regression test for the defect that motivated this correction.
16. **Repeated `PLACE`, two sub-cases (corrected — session-continuation verification found the original single-case form assumed the wrong mechanism, per §19.5.3 step 2):**
    - **(a) Interrupted before marker confirmation:** interrupt a `PLACE` attempt after the marker `PutObject` succeeds but before the `HeadObject` read-back confirms it (`marker_status` still `PENDING`), then re-invoke — assert the resumed attempt computes the *identical* marker key, receives a precondition failure on its own conditional `PutObject`, and correctly reads back the original attempt's marker (§19.5.7) rather than creating a second one.
    - **(b) Interrupted after marker confirmation, before `sweep_status → COMPLETE`:** interrupt a `PLACE` attempt after `marker_status → CONFIRMED` but before the sweep/reconciliation finish, then re-invoke — assert the resumed attempt's §19.5.3 step 2 check finds `marker_status = CONFIRMED` and reuses the durably-recorded `marker_confirmed_last_modified` directly, **never attempting a conditional `PutObject` at all** (not even one that would receive a precondition failure) — the stronger, S3-existence-independent path this session's correction added.
17. **Repeated `RELEASE`:** both sub-cases of item 16, symmetric for `RELEASE`, per §19.5.2 property 4 and §19.3 step 2's new resume branch (`status = RELEASED` and `sweep_status != COMPLETE`).
18. **`PLACE`→`RELEASE`→`PLACE` generations:** run three transitions in sequence on the same audit identity — assert three structurally distinct marker keys via `hold_version = N, N+1, N+2` alone (the first two transitions sharing one `hold_id` as a paired episode; the third, a new episode, on a second, independently-generated `hold_id` — the specific `hold_id` assignment is a `RetentionService` implementation choice this test must not over-constrain, per §19.5.2), no aliasing between any pair, and each transition's own reconciliation pass only ever reads its own generation's marker (§19.5.2 property 5).
19. **Stale marker rejection:** construct a scenario where an old generation's marker (from a prior, already-`COMPLETE` transition) is still present in S3 when a new transition runs — assert the new transition's reconciliation pass never reads the stale marker's `LastModified` (its key doesn't match the new transition's computed key at all, per §19.5.2 property 6) and produces correct results using only its own marker.
20. **Marker disposal after governed purpose ends:** assert a marker whose transition reached `sweep_status = COMPLETE` is eligible for disposal under the `retention-markers/` Lifecycle rule (§19.5.8) once the rule's `Days` value is supplied, and — independently of whether disposal has actually occurred yet — assert `LegalHoldEvent` alone (without the marker object) is sufficient to answer "did this transition happen, when, and what was its outcome," proving no compliance-facing information is lost when the marker object is eventually removed.
21. **Stale re-invocation after `sweep_status = COMPLETE` and marker disposal (session-continuation finding — verified unsafe as originally specified, then fixed, not merely assumed safe):**
    - **(a) `PLACE` re-invoked after its own episode reached `sweep_status = COMPLETE` and its marker object has been disposed (or deleted, standing in for disposal):** invoke `rcp retention hold place` again for the same, still-`ACTIVE` audit identity — assert §19.2 step 4's `sweep_status` gate returns immediately as a pure no-op: no new `upsert_hold` call, no attempted S3 operation of any kind, no change to `sweep_status`, and — the specific defect this scenario exists to close — **no change to the existing `LegalHoldEvent`'s `marker_confirmed_last_modified`/`marker_status` fields.** Before this session's fix, the unconditioned resume branch would have proceeded to §19.5.3's marker step, found the key absent, succeeded on a fresh conditional `PutObject`, and overwritten the historically accurate confirmation timestamp with a fabricated later one — this test is the direct proof that no longer happens.
    - **(b) `RELEASE` re-invoked after its own episode reached `sweep_status = COMPLETE`, regardless of marker disposal:** invoke `rcp retention hold release` again for the same, now-`RELEASED` audit identity — assert §19.3 step 2's third case raises `HOLD_NOT_ACTIVE` and never reaches the marker step at all. This case was already safe by the existing (unamended) `HOLD_NOT_ACTIVE` precondition; this test exists to confirm this session's other changes to §19.3 step 2 (the new resume branch for the not-yet-`COMPLETE` case) did not inadvertently loosen it.
    - **(c) Regression — `PLACE`/`RELEASE` resumed while `sweep_status != COMPLETE` and the marker is already `CONFIRMED` but not yet disposed (item 16(b)/17):** confirm this still resumes correctly via the `marker_status`-reuse path, not via a rejected no-op — distinguishing "nothing left to resume" (this item) from "resumption still in progress" (item 16(b)/17), which must not be conflated.

**Recommendation for the QA/implementation stage, not adopted here:** a controllable test seam (e.g., an injectable hook invoked between the hold-state read and the transaction/S3-write commit) is the most reliable way to deterministically exercise categories 1–7, 10, and 13 above in CI, since real-world race timing is not reliably reproducible. Whether and how to add such a seam is an implementation-level decision for that stage, not an architecture decision made here.

### 19.12 Corrections to Product Strategy's Framing

Both claims underlying this amendment were verified against source, not accepted on inference, per instruction:

- **"Audits run over an extended scheduled window... RUN records... arrive continuously, not atomically."** Confirmed. `docs/architecture/execution_lifecycle.md`: "Finalization is triggered by an EventBridge schedule at the end of the audit window." `audit_scheduling/constants.py` defines `SCHEDULE_TYPE_REPEATED` alongside `baseline`/`burst`, confirming repeated, separately-scheduled invocations across the window, each producing its own `RUN` records via `orchestrator_handler.py` → `put_started_once`.
- **"Phase 4 may be invoked more than once per audit."** Confirmed, with a precision correction: `apps/backend/handlers/audit_finalization_handler.py::_trigger_aggregation_after_finalization` generates a fresh `aggjob_{uuid4().hex}` on **every** call, including via `_handle_finalizing_retry` — a genuine second invocation path exists. However, this does not multiply the CREATE-time race window for the actual *governed evidence* (item 8's aggregate content): that write remains protected by its own per-`(exec_id, config_version, aggregation_version)` conditional `TransactWriteItems` (unaffected by how many `AggregationJobIntent`/`AggregationJob` job-log records — Category 3, not custody-bearing — a retried trigger produces). "Invoked more than once" is true and real at the trigger/job-log layer; it does not, on its own, mean the governed-evidence write itself faces more than one independent race window per successful aggregation.

### 19.13 Assumptions Requiring Confirmation

**Resolved by Product Strategy decision (previously open, now decided, not merely defaulted):** whether the S3 leg's correctness could rest primarily on the 5-second empirically-reasoned buffer, or must rest on the provably-tighter canary-marker mechanism, was flagged in the prior revision as requiring confirmation. Product Strategy has decided: **the canary-marker mechanism (§19.5.1–19.5.10) is the default, primary S3 coordination protocol; the 5-second buffer is retained only as defense-in-depth around the marker boundary, not as the primary correctness argument.** This is no longer an open assumption in this document.

**Resolved by Product Strategy decision (previously open, now decided):** whether uniform fail-closed behavior should apply without exception to the raw-evidence critical execution path (item 1/3), despite the resulting change to Phase 1's operational availability profile, was flagged in the prior revision as a genuine product/business judgment call. Product Strategy has decided: **uniform fail-closed is retained, with no exception for Phase 1** (§19.14). This is no longer an open assumption in this document; it is now a stated, dedicated rule.

**Architecture decision, not flagged for confirmation (stated here for visibility, since it extends an already-locked record schema):** the marker's DynamoDB-side audit trail is recorded as additive fields on the existing `LegalHoldEvent`/`LegalHold` records (§19.5.1) rather than as a new record type, consistent with this design's standing bias against introducing a new abstraction where an existing one already fits. This is an implementation-style choice within this document's own architectural authority (§18.9 and §19.10 apply the identical reasoning elsewhere), not a product/business tradeoff — the practical outcome (a durable, queryable marker audit trail) is identical either way.

### 19.14 Uniform Fail-Closed Rule (Product Strategy Directive — Elevated to Its Own Explicit Rule)

This was already this design's recommended default (§19.4, §19.13, prior revision); Product Strategy has confirmed it and required it be stated as an explicit, unambiguous rule in its own right, not left as an implication of "every write path in §19.7's matrix behaves the same way." Stated plainly, with no exception clause anywhere in it:

> **No Category 1/2 write — any phase, including RunMetadata and raw-evidence CREATE on Phase 1's critical execution path — may proceed to completion when the audit identity's current legal-hold state cannot be deterministically resolved. No partial governed record or object may ever be represented, to any caller, as successfully persisted. Retry, where applicable, is bounded and deterministic (§19.4: 3 attempts for a detected hold-version race; §19.5.6: 3 attempts for marker establishment). Exhaustion of the bounded retry is fail-closed, unconditionally, with no exception for any write path, any phase, or any position in the execution pipeline — including the raw-evidence write path, despite it being the one write in this entire design positioned on the critical path of every audit execution.**

**What this rule forecloses, explicitly, so it cannot be quietly reintroduced later:** no future implementation may add a "best-effort" or "degrade gracefully" branch to `put_started_once`/`write_raw_results_once` (or any other Category 1/2 write) that proceeds without a resolved hold state under sustained contention, on the reasoning that "audit execution availability matters more here." That trade-off was considered (§19.13, prior revision) and Product Strategy's decision forecloses it — the write must fail, the caller must receive a distinguishable error (§19.15), and the audit's execution orchestration (outside this workstream's scope) is responsible for whatever retry/alerting/operational response that failure triggers upstream.

**Operational consequence, restated plainly rather than left implicit:** sustained DynamoDB throttling or contention on a specific audit's `LegalHold` item is now a real, if narrow, way an audit *execution* can fail — a change to Phase 1's operational risk profile that did not exist before this workstream, since `put_started_once` previously could not fail for hold-related reasons at all (hold-checking did not exist). This is accepted, not hidden: it is the direct, necessary consequence of treating legal hold as a constitutional evidence-integrity control that must never silently degrade, exactly as Product Strategy's Decision 1 reasoning states for the S3 marker mechanism, applied here to the fail-closed posture as a whole.

### 19.15 Governed Error Classification for Retry Exhaustion

Every failure mode this amendment introduces must be distinguishable by an operator or caller from an ordinary AWS API failure — confirmed sufficient using this codebase's **existing, already-established pattern**: a distinct `StorageError` subclass or a distinct string `code` attribute on a common `StorageError` base, exactly as `DuplicateRunIdError`, `ConditionalWriteError`, and `CUSTODY_PERIOD_CONFIG_MISSING` already do elsewhere in this same codebase. No new error-handling architecture, exception hierarchy, or status-code scheme is introduced — this confirms sufficiency of the existing pattern rather than inventing a new one.

| Code | Raised when | Distinguishable from |
| --- | --- | --- |
| `HOLD_STATE_CONCURRENCY_EXCEEDED` (§19.4) | The `LegalHold` `hold_version` `ConditionCheck` fails on every attempt up to the bounded retry limit — a genuine, sustained hold-state race, not a one-off collision. | An ordinary DynamoDB throttling error (`ProvisionedThroughputExceededException`/`ThrottlingException`, surfaced via the existing `storage_error_from_dynamodb_client_error` path, unrelated to hold contention specifically) and a genuine duplicate-write condition on the governed record's own item (surfaced as the write path's existing, unchanged error — `DuplicateRunIdError`, `ConditionalWriteError`, etc. — per §19.4 step 4's explicit precedence order, never conflated with a hold-version retry). |
| `HOLD_MARKER_ESTABLISHMENT_FAILED` (§19.5.6) | The canary marker's `PutObject` or its `HeadObject` read-back fails on every attempt up to the bounded retry limit. | An ordinary S3 error unrelated to the marker (e.g., a failure writing the evidence object itself, which retains its own existing error path and is never reported as a marker failure) and `HOLD_STATE_CONCURRENCY_EXCEEDED` above (a DynamoDB-side condition failure, not an S3-side write failure — these are always distinguishable by which store's operation actually failed). |

Both codes are raised **before** any partial write of the governed record/object is attempted or could be observed by a caller as having succeeded — consistent with §19.14's "no partial governed record may ever be represented as successfully persisted." An operator or an upstream caller inspecting either code knows immediately, without needing to inspect logs or infer from a generic timeout, that the failure is a legal-hold-coordination failure specifically, not an unrelated AWS service degradation.

### 19.16 Phase 4 Transaction Item and Byte Budget (`put_records_once`, `put_lineage_page_once`)

**Correction (Product Strategy — session-continuation verification found the prior "5-item transaction" characterization inaccurate):** §18.1 item 8's "five record kinds" describes five *kinds* of record `put_records_once` writes, not a fixed five-item `TransactWriteItems` call. Direct re-read of `AggregationOrchestrator._build_persisted_records` confirms the actual per-call item count is **`4 + 3N`**, where N is the number of distinct endpoints represented in the aggregation (1 audit lineage manifest + N endpoint lineage manifests + 1 audit aggregate + 1 audit failure-classification + N endpoint aggregates + N endpoint failure-classifications + 1 aggregate-set-completion marker). Even the simplest realistic case (N=1) is 7 items, not 5. §19.4 step 3 Item B and §19.7 item 8 are corrected accordingly; §19.10's item (e) description is corrected to match.

#### 19.16.1 Transaction Item Budget

DynamoDB's `TransactWriteItems` hard cap is 100 items total, counting every item type in the request (`Put`, `ConditionCheck`, or otherwise) — this figure should be independently reconfirmed against current AWS documentation at implementation time, not treated as fixed by this document alone.

Transaction splitting across multiple `TransactWriteItems` calls is **not authorized** (Product Strategy decision): it would weaken aggregate-set atomicity and complicate the deterministic retry and completion semantics `aggregate_set_exists`'s all-or-nothing correctness argument depends on. Instead, one of the 100 slots is permanently reserved for the appended `LegalHold.hold_version` `ConditionCheck` (§19.4 step 3 Item A):

- Maximum governed record items (existing `Put`s, item 8's `4 + 3N`): **99** (`MAX_AGGREGATE_RECORDS` in `aggregation/constants.py`, corrected from its prior value of 100).
- One appended `LegalHold` `ConditionCheck`.
- Maximum total transaction items: **100**.

Solving `4 + 3N ≤ 99` gives **N ≤ 31** — the maximum number of distinct endpoints one aggregation call may cover under the current record shape. 31 endpoints produce 97 governed items (98 total, within budget); 32 endpoints produce 100 governed items (101 total, over budget).

This limit is checked deterministically, client-side, in `put_records_once`, before any AWS request is made — never discovered via an AWS-side rejection. If a future requirement needs more than 31 endpoints in one aggregate transaction, that is its own, separately reviewed architecture decision (e.g., revisiting the no-split constraint above) — not a silent adjustment to this limit, and not something this correction authorizes.

**Error wording:** the rejection error must not suggest an unauthorized remediation. It must not read as "reduce endpoint count or split the aggregation" (the latter clause implies transaction splitting, which this section explicitly forecloses). Approved wording: *"Aggregate set exceeds the governed atomic-transaction limit. Reduce the configured endpoint scope or obtain a separately reviewed architecture decision."*

#### 19.16.2 Post-Augmentation Per-Item Size Validation

`custody_expires_at`, `ttl_disposal_at` (when applicable), and `evidence_class` are merged onto every governed item as part of this workstream's correction (§18.1) — this increases each item's persisted size relative to its pre-amendment shape. The existing per-item size guard (`MAX_AGGREGATE_ITEM_BYTES` in `aggregation/constants.py`) must be evaluated **after** these governance attributes are merged, never before. A pre-augmentation check is insufficient by construction: an item just under the ceiling before augmentation can be pushed over it by the added attributes, and a check performed before augmentation would never observe that.

This requirement applies identically to every item passed to `put_records_once` (all `4 + 3N` governed items) and to the single item passed to `put_lineage_page_once` — both write paths receive the same three governance attributes and are subject to the same post-augmentation per-item guard. Any item exceeding `MAX_AGGREGATE_ITEM_BYTES` after augmentation is rejected deterministically, before any AWS request is made.

#### 19.16.3 Deterministic Conservative Transaction-Size Measurement Contract

The transaction-level byte guard (`MAX_AGGREGATE_TRANSACTION_BYTES` in `aggregation/constants.py`) is evaluated over the **final wire-format transaction actions**, not over the pre-encoding Python record dicts, via one deterministic sequence:

1. Governance fields (`custody_expires_at`, `ttl_disposal_at` where applicable, `evidence_class`) are merged onto every governed record first.
2. Each augmented record is encoded into DynamoDB `AttributeValue` wire format.
3. The final `Put` transact-items are constructed from the encoded items.
4. The `LegalHold.hold_version` `ConditionCheck` transact-item is constructed.
5. The complete final transact-item list — every `Put` and the appended `ConditionCheck` together — is measured through one canonical, deterministic serialization (the same serialization used for every measurement, so repeated evaluation of the same input always yields the same result).
6. If that measurement exceeds `MAX_AGGREGATE_TRANSACTION_BYTES`, the transaction is rejected before any AWS request is made.

**This measurement is an RCP-owned conservative preflight guard, not a reproduction of AWS's internal transaction-size accounting.** It may intentionally count request-structure overhead (attribute names, type descriptors, the `ConditionCheck`'s own structure) that AWS's own internal accounting may compute differently, and may therefore reject a transaction AWS itself would have accepted. This is acceptable: it fails safely, in the direction of rejecting early rather than discovering a violation only after submission. This document does not claim byte-for-byte equivalence with AWS's internal accounting, and no future implementation may claim this measurement is exact proof of AWS acceptance. Operational confirmation against real AWS behavior remains part of the later deployment and acceptance gate — out of scope for this document and for A1.3c's own test suite (§19.16.4), which proves RCP's own guard behavior only.

`MAX_AGGREGATE_TRANSACTION_BYTES`'s existing value (3.8 MB) is not changed by this correction — the governance attributes' and appended `ConditionCheck`'s worst-case combined contribution is small relative to the existing margin below DynamoDB's total-request-size limit — but this document does not assert that margin is sufficient by arithmetic alone; §19.16.4's boundary tests are the authoritative proof, to be run against the corrected measurement sequence above, not against the pre-amendment calculation.

#### 19.16.4 Required Test Coverage

In addition to §19.11's existing categories, extended to Phase 4's variable-length transaction:

- **31-endpoint boundary**: 97 governed items + 1 appended `ConditionCheck` = 98 total — must succeed (subject to the byte guard).
- **32-endpoint rejection**: 100 governed items — must be rejected deterministically before any AWS request; no `transact_write_items` call occurs.
- **Post-augmentation per-item rejection**: an item just below `MAX_AGGREGATE_ITEM_BYTES` before governance-attribute augmentation but above it afterward — must be rejected, with no transaction call made; covering both `put_records_once` and `put_lineage_page_once`.
- **Transaction byte-boundary — below**: a final, fully-constructed transact-item list (post-augmentation, post-encoding, including the appended `ConditionCheck`) just under `MAX_AGGREGATE_TRANSACTION_BYTES` — accepted.
- **Transaction byte-boundary — above**: the symmetric case just over the limit — rejected, with no AWS request made.
- **Governance-attribute inclusion in the transaction measurement**: a record set under budget before governance-attribute merge but over budget only after — must be rejected, proving the measurement is not evaluated against stale, pre-merge sizes.
- **Appended-`ConditionCheck` inclusion in the transaction measurement**: the measurement must include the `ConditionCheck` transact-item's own serialized contribution, not only the `Put` items.
- **Determinism**: repeated evaluation of the identical input transaction produces the identical measurement and the identical accept/reject outcome.
- **Variable cancellation-reason indexing**: parameterized across multiple N (e.g., N=1, N=10, N=31), proving the existing, unmodified `HoldCoordinatedTransactionRunner`'s `CancellationReasons[:len(governed_items)]` slicing correctly isolates governed-item failures from the appended hold-check failure at every size — no change to `hold_coordination.py` is required, since it was never hardcoded to a fixed governed-item count.
- **Governed-condition vs. hold-condition precedence**: both fail in the same attempt — the governed failure must win, per §19.4 step 4's existing, unmodified precedence rule, never masked as a hold-version retry.

This test suite proves RCP's own preflight-guard behavior deterministically. It does not, and is not represented as, proof of AWS's internal `TransactWriteItems` byte-accounting implementation (§19.16.3).

#### 19.16.5 Custody-Period Configuration Source for `aggregate_metadata`

**Correction (Product Strategy — A1.3c.1 pre-implementation verification found no custody-period configuration channel existed for Phase 4's evidence class):** §18.1 and this section both require every governed Phase 4 DynamoDB row to carry `evidence_class = aggregate_metadata` and, per Category 1's custody-field requirement, `custody_expires_at`/`ttl_disposal_at`. Neither this document nor the companion ADR's Decision 5 (prior to its own A1.3c.1 amendment) ever named a configuration source `custody_expires_at` could be computed from for this specific evidence class — the only custody-period environment variable in the codebase, `CUSTODY_PERIOD_DAYS_RAW_EVIDENCE`, is scoped exclusively to RunMetadata (A1.3b/A1.LH3). This is now corrected:

- No Phase 4 governed record (any of the `4 + 3N` items from `put_records_once`, or a `put_lineage_page_once` item) may ever be persisted missing `custody_expires_at` or `evidence_class` — both must be present on every write that succeeds, with no partial-success path.
